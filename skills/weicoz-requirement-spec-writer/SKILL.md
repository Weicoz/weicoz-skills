# Requirement Spec Writer

## 触发规则

本 skill 仅允许手动调用。只有用户明确点名 `$weicoz-requirement-spec-writer`，或明确要求使用本 skill 时才加载并执行。普通的“写需求文档”“生成 PRD”“整理产品定义”等请求不得自动触发。

这个 skill 用来把“想法”变成“可执行文档”。

目标不是写一份好看的空话文档，而是产出一份让产品、设计、开发、测试、运营能对齐范围，并能直接开工的需求文档。

## 适用范围

优先用于以下场景：

- 用户只有一段描述、会议纪要、聊天记录，需要整理成正式需求文档
- 用户已经有草稿，但内容松散，需要补齐结构、边界、验收标准
- 用户明确说要 PRD、需求规格说明书、功能 spec、MVP spec、开发说明
- 用户希望把“做什么”与“怎么验收”写清楚，再进入设计或开发

不适合直接替代这些文档：

- 纯市场调研报告
- 纯技术 RFC / ADR
- 纯交互稿或视觉规范

如果用户实际要的是以上文档，先指出文档类型不完全匹配，再按最接近的 spec 方式组织。

## 工作原则

1. 先收敛文档目标，再展开细节。
2. 先写清“解决什么问题”，再写“做什么功能”。
3. 每个功能都尽量落到可判断对错的验收标准。
4. 对未知项不要假装确定，显式标注 `待确认`、`假设`、`风险`。
5. 不为了显得完整而堆废话；但凡会影响设计、开发、测试、排期、验收的细节，都要写。
6. 生成正式 spec 前必须先追问关键缺口，特别是需求目标、边界条件、业务术语和关键决策。
7. 最终产物默认写入当前工作目录的 `SPEC.md`，除非用户明确指定其他文件名或目录。
8. 一旦需求目标、范围、术语、业务规则、关键决策或验收标准发生变化，必须同步更新 `SPEC.md`。

## 文档完成标准

只有满足以下标准，才算这份 spec 真正可用：

- 读者可以在不追问作者的前提下，复述本期要做什么、不做什么
- 开发可以基于文档拆任务，而不是先开会猜需求
- 测试可以基于文档写主流程、异常流程和验收点
- 设计可以判断页面 / 状态 / 交互是否缺失
- 上线前后需要观察的指标、日志、风险有基本说明

如果只是“结构完整”，但以上几项做不到，说明文档仍不够好。

## 默认流程

### Step 1: 先判定文档类型

先判断用户要的是哪一种：

- `One-pager`：只做高层目标、范围、关键流程
- `MVP Spec`：够产品/设计/开发开工，但不过度展开
- `Build-ready Spec`：默认推荐；功能、状态、流程、接口、验收基本齐全
- `Execution-grade Spec`：交给多人协作开发前使用；需要写到异常、边界、数据结构、权限、失败处理、埋点、测试口径

如果用户没指定，默认按 `Build-ready Spec` 输出。

需要判断的另外两个维度：

- 文档偏产品：更强调用户场景、流程、页面、交互、规则
- 文档偏实现：更强调状态、接口、数据结构、约束、失败处理

如果同时需要，两者都保留，但按“产品目标 -> 功能设计 -> 技术约束 -> 验收标准”的顺序组织。

再额外判断需求属于哪一类：

- 页面 / 交互型：重点补页面结构、状态、交互反馈、空态 / 加载态 / 错误态
- 流程 / 工作流型：重点补入口、节点、状态流转、权限、通知、回退与重试
- 平台 / 后台型：重点补角色、模块边界、列表筛选、批量操作、审计
- AI / LLM 型：重点补 prompt 输入、输出结构、降级、成本、超时、错误兜底
- 数据 / 集成型：重点补字段、映射、同步时机、幂等、错误恢复、兼容性
- 游戏 / 状态机型：重点补回合、分数 / 数值、胜负条件、随机性、防重复触发

根据类型优先读取 `references/spec-routing-guide.md`，不要所有需求都写成一个模板味很重的“通用 PRD”。

### Step 2: 先提取已知信息，形成澄清清单

优先从当前对话、用户给的 spec、仓库上下文里提取：

- 产品目标
- 目标用户 / 角色
- 使用场景
- 关键流程
- 功能列表
- 约束条件
- 已知技术栈
- 用户特别强调的坑、禁区、必须项

提取后先做一个内部信息盘点：

- 已确定：用户已经明确说过的事实
- 推断：从上下文能合理推断但需要标注为假设的内容
- 缺口：会影响 spec 质量、开发范围或验收判断的信息

### Step 3: 追问澄清，问清目标、边界、术语和关键决策

在生成正式 `SPEC.md` 前，必须至少检查这四类信息：

- 需求目标：这次要解决什么问题，成功标准是什么
- 边界条件：第一版做什么、不做什么、异常和限制是什么
- 业务术语：核心名词的定义、角色、状态、对象和流程节点是什么
- 关键决策：已经拍板的方案、待拍板的方案、会影响架构或体验的取舍是什么

如果这些信息缺失或含糊，先追问用户。不要在关键问题没问清时直接生成最终文档。

优先追问以下问题：

- 目标用户是谁
- 成功标准是什么
- 第一版范围到哪里为止
- 哪些内容明确不做
- 是否需要接口 / 数据结构 / 埋点 / 权限细节

提问时一次只问最关键的 3-6 个，按主题分组。问题要能推动决策，不要问“还有什么补充吗”这种低效问题。

如果确实需要补问，优先按这个顺序问：

1. 这次第一版到底要做到哪里
2. 谁在用，谁负责操作，谁负责验收
3. 成功 / 失败 / 不做的边界是什么

更完整的问题库见 `references/question-bank.md`。只有在当前信息不足以支撑文档质量时，才去展开。

追问时使用这种格式：

```markdown
我需要先确认这几个点，确认后再生成 SPEC.md：

## 目标
1. ...

## 边界
2. ...

## 业务术语
3. ...

## 关键决策
4. ...
```

如果用户回答后仍有关键歧义，继续追问一轮。只有当剩余问题不阻塞第一版 spec 时，才把它们放入 `待确认项`。

### Step 4: 整理澄清结果，确认规格假设

根据用户回答，先整理一份简短的规格摘要：

- 已确认目标
- 已确认范围
- 已确认非范围
- 已确认术语
- 已确认关键决策
- 仍待确认但不阻塞写文档的问题

如果用户明显纠正了你的理解，必须以用户最新回答为准。

### Step 5: 先搭骨架，再填细节

默认采用 `references/spec-template.md` 的结构。

至少保证这些核心块存在：

- 背景与问题
- 目标与成功标准
- 范围与非范围
- 用户角色与场景
- 核心流程
- 功能需求
- 关键规则 / 状态 / 边界
- 验收标准
- 风险与待确认项

如果需求包含前后端或 AI 能力，再补这些块：

- 数据结构 / 状态模型
- API / 输入输出契约
- 异常与降级策略
- 权限、安全、限流、成本约束
- 日志、埋点、监控

写每个章节时，不要只写“该节是什么”，要写到“这一节解决的歧义是什么”。

例如：

- 背景：解决“为什么现在做”
- 范围：解决“第一版边界在哪”
- 功能需求：解决“具体行为是什么”
- 规则：解决“系统按什么条件判断”
- 验收：解决“怎么知道做好了”

### Step 6: 控制细节深度

使用 `references/detail-depth-rubric.md` 来决定每节写到多细。

默认要求：

- 不能只写标题，不写判断标准
- 不能只写“支持 XXX”，不写输入、输出、状态变化
- 不能只写“优化体验”，不写什么行为会变化
- 不能只写“处理异常”，不写异常类型和处理方式

一份像样的 spec，至少要让读者回答这些问题：

- 为什么做
- 给谁做
- 第一版到底做哪些，不做哪些
- 用户从哪里进入，到哪里结束
- 每一步看到什么、能做什么、系统怎么响应
- 什么情况下成功，什么情况下失败
- 如何判断已完成

如果文档写到一半你发现：

- 还无法画出主流程
- 还无法列出状态
- 还无法写出至少 3-5 条可测试验收标准

说明你还在“想法描述”阶段，不在“spec”阶段，需要先补结构和决策。

### Step 7: 产出时强制区分“确定项”和“假设项”

文档里显式使用以下标签：

- `已确定`：用户已明确给出或上下文足够确定
- `假设`：为推进文档而做的合理假设
- `待确认`：没有这些信息会影响方案质量或排期
- `风险`：即使当前方案成立，后续仍可能出问题的点

不要把猜测写成事实。

如果用户明确给了事实，优先保留原始约束，不要擅自“优化”掉。

### Step 8: 生成并写入 SPEC.md

默认将最终文档写入当前工作目录的 `SPEC.md`。

执行规则：

- 如果当前目录已经有 `SPEC.md`，先读取现有内容，判断是更新还是重写
- 如果用户是在当前项目里写需求，优先写当前项目根目录的 `SPEC.md`
- 如果用户指定目录或文件名，按用户指定位置写
- 如果没有明确项目目录，写入当前工作目录
- 写入前确保文档标题、范围、术语、关键决策、验收标准齐全

不要只在聊天里贴完整 spec 后结束。聊天里可以给摘要，但最终必须有文件产物。

### Step 9: 需求变更时同步更新 SPEC.md

如果用户后续补充、修正、删除或改变需求，先判断这是否影响现有 spec。

以下情况必须更新 `SPEC.md`：

- 需求目标变化
- P0 / P1 / P2 范围变化
- 明确新增或删除功能
- 业务术语定义变化
- 角色、权限、状态、流程节点变化
- 业务规则、阈值、默认值、限制条件变化
- API、数据结构、外部依赖变化
- 验收标准、测试口径、上线条件变化
- 已拍板关键决策发生变化
- 待确认项被确认或取消

更新流程：

1. 读取当前 `SPEC.md`
2. 定位受影响章节
3. 必要时追问变更细节，尤其是影响范围和验收的问题
4. 更新对应章节，不要只追加零散备注
5. 在 `变更记录` 或 `附录 / 澄清问答摘要` 中记录变更日期、变更来源、变更内容和影响范围
6. 重新运行规格审查，确认目标、范围、术语、关键决策和验收仍一致

如果用户只是聊天里说“这个改一下”，也要判断是否需要写入 `SPEC.md`。不要让聊天里的最新需求和文件里的 spec 分叉。

### Step 10: 输出后做一次规格审查

用 `references/review-checklist.md` 自查，重点检查：

- 是否还有模糊词没有落地
- 功能是否缺边界条件
- 验收标准能否实际判断通过/失败
- 是否把 out of scope 写清楚
- 是否遗漏状态流转、异常、重试、空状态、权限、性能、成本等关键项

如果发现缺口，先补文档，再交付。

### Step 11: 交付时给出文档级别判断

交付时最好顺手说明这份文档当前属于哪个级别：

- 还是 `One-pager`
- 已达到 `MVP Spec`
- 已达到 `Build-ready Spec`
- 已达到 `Execution-grade Spec`

如果还没达到更高一级，要指出缺什么，而不是默认“已经可以开工”。

## 输出要求

默认输出 Markdown，并默认写入 `SPEC.md`。

除非用户另有要求，最终文档应遵循以下协议：

1. 开头先给文档标题与版本定位
2. 主体按模板分节
3. 功能需求优先写成编号列表，便于引用
4. 验收标准写成可以测试的 bullet
5. 文末单独列出 `待确认项`、`风险`、`开放问题`
6. 文件名默认为 `SPEC.md`

聊天回复只需要给：

- `SPEC.md` 路径
- 当前文档等级
- 还剩哪些非阻塞待确认项
- 已做的校验
- 本次是否更新了 `SPEC.md`，以及更新了哪些章节

如果用户让你“直接写一份详细 spec”，默认输出顺序为：

1. 概述 / 背景 / 目标
2. 范围 / 非范围
3. 角色 / 场景
4. 流程
5. 功能需求
6. 规则 / 状态 / 数据 / 接口
7. 异常 / 边界 / 非功能约束
8. 验收 / 测试
9. 风险 / 假设 / 待确认

如果用户让你“review 一份 spec”，默认输出顺序为：

1. 主要缺口
2. 高风险歧义
3. 缺失章节
4. 建议补写内容
5. 当前文档等级判断

## 写作要求

- 用词要具体，少写正确但无用的话
- 尽量避免“提升体验”“更加智能”“更流畅”这类空词，除非后面跟了明确行为变化
- 同一篇文档里术语保持一致，不要一会儿叫“用户”，一会儿叫“玩家”，一会儿叫“访客”
- 对规则型内容，优先写成表格、枚举、状态说明
- 对流程型内容，优先写成步骤序列
- 对接口型内容，优先写字段、类型、约束、示例

补充要求：

- 每节尽量回答“这节解决哪个问题”
- 一条规则尽量只有一种解释
- 涉及比较、阈值、优先级时尽量量化
- 涉及 AI 输出时尽量写结构而不是只写“模型生成内容”
- 涉及外部依赖时尽量写故障后的 fallback

## 常见补强点

如果用户的原始需求里没写，但按经验很容易漏，主动补这些部分：

- 入口和退出条件
- 空状态
- 加载态
- 失败态
- 重试
- 幂等 / 防重复提交
- 数据范围与分页
- 权限角色差异
- 审计 / 日志 / 埋点
- 成本约束（尤其 AI / 第三方接口）
- 降级方案
- 与旧系统兼容或迁移要求
- 默认值与初始值
- 排序与筛选规则
- 文案是否固定、可配置还是模型生成
- 是否需要人工介入或人工兜底
- 是否需要防刷、限频、风控

## 分章节写作动作

写文档时，按下面动作执行，而不是笼统“补充一下需求”：

### 写背景时

- 先写现状
- 再写痛点
- 再写不解决的代价
- 最后写本次切口

### 写范围时

- 先列 P0 必做
- 再列明确不做
- 再列依赖项
- 大需求再拆阶段

### 写流程时

- 先主流程
- 再异常流程
- 再回退 / 重试 / 中断恢复

### 写功能时

- 每个功能按“目标 -> 前置条件 -> 用户动作 -> 系统响应 -> 规则 -> 异常 -> 验收”写

### 写规则时

- 优先写阈值、枚举、条件、优先级、时机
- 避免“系统自动处理”“按业务规则判断”这类空表述

### 写验收时

- 一条验收标准只验证一件事
- 尽量包含触发条件、预期结果、失败判定

## 典型错误

出现以下写法时，默认认为文档质量不够：

- “支持用户进行相关操作”
- “优化体验”
- “智能生成内容”
- “异常时友好提示”
- “后台可管理相关数据”
- “按权限展示”

这些话不是不能写，但后面必须跟清楚“具体怎么支持 / 怎么优化 / 怎么生成 / 怎么提示 / 怎么管理 / 怎么判断权限”。

## 交付格式

如果用户说“直接帮我写”，先判断信息是否足够；信息不足时先追问关键缺口，信息足够时生成并写入 `SPEC.md`。

如果用户说“需求改了”“这里要调整”“这个不做了”“新增一个功能”“按刚才说的更新一下”，默认先读取并更新 `SPEC.md`，再给出变更摘要。

如果用户说“先给模板”，优先给：

- `references/spec-template.md`
- `references/detail-depth-rubric.md`
- `references/review-checklist.md`
- `references/question-bank.md`
- `references/spec-routing-guide.md`
- `references/clarification-workflow.md`

如果用户说“帮我检查这份 spec 行不行”，按以下顺序回复：

1. 先指出主要缺口
2. 再列风险和歧义
3. 最后给建议补写结构
