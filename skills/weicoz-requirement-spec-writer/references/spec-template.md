# 通用需求文档 / Requirement Spec 模板

按需裁剪，但默认不要少于以下骨架。面向 MVP 时可以压缩文字量，面向多人协作开发时应尽量补齐。

## 2. 背景与问题定义

### 2.1 背景

说明这个需求为什么会出现。写业务背景、用户背景或项目背景，不要只写“需要做一个 XX 功能”。

建议补一句：

- 为什么是现在做，而不是以后做

### 2.2 当前问题

明确现状中的问题：

- 现在哪一步有阻塞
- 用户现在怎么做
- 现有方案哪里不够
- 不做会带来什么损失

### 2.3 目标

用 3-5 条写清本次要达成什么。

示例：

- 让用户能在 3 分钟内完成首次配置
- 把人工整理流程缩短到 10 分钟内
- 让开发可以按明确规则实现，不依赖口头补充

建议同时写：

- 成功指标
- 不追求的目标

### 2.4 成功标准

写清什么情况算本需求成功。

建议格式：

- 用户结果：
- 业务结果：
- 系统结果：
- 验收判断：

### 2.5 非目标 / Out of Scope

显式写本次不做什么，防止范围漂移。

示例：

- 不做后台运营系统
- 不做复杂权限体系
- 不做自动化推荐，只做手动选择

这一节越具体，后续越不容易失控。

## 3. 用户与使用场景

### 3.1 目标用户 / 角色

至少写清：

- 谁是主要使用者
- 谁会间接受影响
- 是否有管理员 / 审核人 / 操作员等多角色差异

### 3.2 核心使用场景

每个场景写：

- 触发前提
- 用户目标
- 操作路径
- 期望结果

如果有多个角色，最好拆成多个场景，不要混写。

### 3.3 不处理的场景

列出已知不覆盖的场景，减少误解。

## 4. 范围总览

### 4.1 In Scope

编号列出本期必须交付的模块或能力。

### 4.2 Out of Scope

编号列出明确不在本期内的模块或能力。

### 4.3 依赖项

列出依赖的上游系统、第三方服务、外部数据、设计稿、权限开通等。

建议额外标记：

- 已具备
- 待提供
- 高风险依赖

### 4.4 边界条件

写清第一版必须遵守的边界：

- 数量边界：
- 时间边界：
- 权限边界：
- 成本 / 配额边界：
- 数据边界：
- 异常处理边界：

## 6. 核心流程

用步骤或小节写清主流程。必要时可补充分支流程。

推荐格式：

1. 用户从哪里进入
2. 页面 / 系统展示什么
3. 用户执行什么操作
4. 系统做什么处理
5. 成功时看到什么
6. 失败时如何提示 / 如何恢复

如果存在多个关键流程，按“主流程 / 次流程 / 失败流程”拆开写。

建议至少写 1 条失败流程，否则大多数实现会在异常处理阶段补口头规则。

## 7. 功能需求

这是文档主体。每个功能建议按统一格式写。

### 7.X 功能名称

#### 7.X.1 功能目标

这个功能解决什么问题。

#### 7.X.2 交互 / 行为说明

写清：

- 入口
- 前置条件
- 页面元素 / 输入项 / 按钮 / 状态
- 用户操作
- 系统响应
- 结束条件

如果是后台 / 非页面需求，也要把“操作者动作”和“系统动作”对应写出来。

#### 7.X.3 业务规则

写清规则，不要只写“按业务逻辑处理”。

推荐覆盖：

- 触发条件
- 排序规则
- 优先级
- 限制次数
- 文案规则
- 计算逻辑
- 时间规则
- 状态转换
- 默认值 / 初始值
- 上限 / 下限 / 次数限制
- 配置项是否可变

#### 7.X.4 边界与异常

至少考虑：

- 空输入
- 非法输入
- 重复提交
- 网络失败
- 接口超时
- 无权限
- 数据为空
- 达到上限
- 第三方失败
- 用户中断
- 并发冲突

#### 7.X.5 验收标准

写成可验证条目。

示例：

- 当用户未填写必填项时，提交按钮不可成功提交，并提示具体缺失字段
- 当接口超时超过 15 秒时，页面展示失败提示，并允许用户重试
- 当同一请求重复点击时，系统只处理一次

建议覆盖三类验收：

- 主流程成功
- 关键异常处理
- 规则是否正确生效

## 8. 页面 / 模块 / 信息结构

如果需求涉及前台页面或后台界面，建议列出：

- 页面列表
- 每页职责
- 页面之间跳转关系
- 每页的关键区域

如果不是页面型产品，也可写成模块结构。

如果页面较多，建议补：

- 哪些页面是 P0
- 哪些页面只是后续扩展

## 9. 状态模型与关键规则

适用于有明显状态流转的需求。

建议写：

- 初始状态
- 中间状态
- 结束状态
- 每个状态下允许的操作
- 状态切换条件
- 状态切换失败时的处理

如有必要，建议补一张状态表：

| 状态 | 含义 | 可执行动作 | 下一状态 | 失败处理 |
|------|------|------------|----------|----------|
|      |      |            |          |          |

## 10. 数据结构 / 实体定义

如果需求涉及结构化数据，至少写：

- 核心实体
- 字段名
- 类型
- 是否必填
- 约束
- 示例值

如果字段很多，优先保证核心字段明确，不必为次要字段堆文档长度。

推荐格式：

| 实体 | 字段 | 类型 | 必填 | 说明 | 约束 / 示例 |
|------|------|------|------|------|-------------|
|      |      |      |      |      |             |

## 11. 接口 / 输入输出契约

如果涉及前后端接口、第三方 API、AI 请求，请补这一节。

每个接口至少写：

- 路径 / 名称
- 调用方
- 用途
- 请求参数
- 返回结构
- 错误码 / 错误场景
- 超时 / 重试 / 幂等要求
- 调用频率 / 限流要求（如果重要）
- 降级方式

推荐格式：

### 11.X 接口名称

- Method / Path:
- Purpose:
- Caller:
- Timeout:
- Retry:

#### Request

```ts
// type shape
```

#### Response

```ts
// type shape
```

#### Notes

- ...
- 这个接口失败后，页面 / 流程怎么继续

## 12. 非功能要求

按需写，不要机械全抄。

常见包括：

- 性能：响应时间、并发、吞吐
- 稳定性：超时、重试、降级
- 安全：权限、脱敏、鉴权、审计
- 成本：模型调用、第三方接口、存储
- 可观测性：日志、埋点、告警
- 兼容性：浏览器、设备、历史数据、旧版本

如果不需要某项，可以明确写“不关注”或“本期不要求”，比空着更好。

## 13. 埋点 / 日志 / 监控

如果需求上线后需要观察效果或排障，最好明确：

- 关键事件要不要埋点
- 需要记录哪些日志
- 哪些异常需要告警
- 成功指标如何看

如果是 AI 或自动化流程，日志建议区分：

- 输入日志
- 输出日志
- 错误日志
- 成本 / 耗时日志

## 14. 测试与验收

### 14.1 测试范围

列出本次至少要覆盖的测试项：

- 主流程
- 分支流程
- 异常流程
- 权限差异
- 兼容性

### 14.2 验收口径

明确谁按什么标准判断完成。

最好写清：

- 谁负责验收
- 验收到什么级别
- 发现问题后谁拍板是否上线

### 14.3 冒烟清单

上线前最少要手测哪些内容。

## 15. 风险、假设、待确认

### 15.1 风险

列实现风险、业务风险、依赖风险。

建议按严重度排序。

### 15.2 假设

写当前文档成立依赖了哪些假设。

### 15.3 待确认项

把会影响开发、排期、方案选择的未知项显式列出来。

如果待确认项较多，建议标明：

- 不确认也能先做
- 不确认就不能开工

### 15.4 已关闭待确认项

当用户后续补充信息后，把已确认的问题移动到这里或更新到对应正文，不要让已解决问题长期留在待确认中。

| 原问题 | 结论 | 关闭日期 | 影响章节 |
|--------|------|----------|----------|
|        |      |          |          |

## 16. 里程碑 / 版本切分

如果需求比较大，建议拆：

- P0：必须有
- P1：应该有
- P2：可以后补

或者按 Phase 1 / Phase 2 拆分。

每个阶段最好写清交付闭环，而不是只写功能名。

## 17. 附录

可放：

- 术语定义
- 示例数据
- 默认文案
- 规则表
- 决策记录摘要
- 澄清问答摘要
