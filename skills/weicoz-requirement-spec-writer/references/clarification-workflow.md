# SPEC 澄清问答流程

这个流程用于在生成 `SPEC.md` 前，把需求目标、边界条件、业务术语和关键决策问清楚。

---

## 1. 先做信息盘点

从用户已有输入中提取：

- 已确认目标
- 已确认用户 / 角色
- 已确认核心流程
- 已确认功能范围
- 已确认技术或业务约束
- 已确认不做事项

然后列出缺口：

- 会影响范围的缺口
- 会影响实现的缺口
- 会影响验收的缺口
- 可以后续确认、不阻塞第一版 spec 的缺口

## 2. 四类必须澄清的问题

### 需求目标

目标问题要回答：

- 为什么做
- 给谁做
- 解决哪个具体问题
- 成功后有什么可观察变化

优先问题：

- 这次需求最核心要解决的一个问题是什么？
- 第一版成功的判断标准是什么？
- 谁是主要使用者，谁来验收？

### 边界条件

边界问题要回答：

- 第一版做什么
- 明确不做什么
- 哪些异常必须处理
- 哪些依赖不满足就不能开工

优先问题：

- P0 必须做哪些能力？
- 哪些能力明确不在第一版？
- 哪些失败、异常、极限场景必须处理？

### 业务术语

术语问题要回答：

- 核心对象叫什么
- 每个角色是什么意思
- 每个状态是什么意思
- 关键流程节点如何命名

优先问题：

- 这个需求里有哪些核心名词必须统一叫法？
- 这些名词分别代表什么对象、角色或状态？
- 有没有容易混淆但必须区分的概念？

### 关键决策

关键决策要回答：

- 哪些方案已经定了
- 哪些方案还没定
- 哪些决定会影响技术架构、体验或排期

优先问题：

- 目前哪些方案已经拍板？
- 哪些点还需要你做选择？
- 如果有多个实现方式，优先按什么标准取舍：速度、质量、成本、可扩展性，还是用户体验？

## 3. 提问节奏

不要一次问几十个问题。默认每轮问 3-6 个。

第一轮优先覆盖：

- 目标
- 边界
- 术语
- 关键决策

第二轮再追：

- 流程细节
- 异常和边界
- 接口 / 数据
- 验收标准

如果用户明显想快速推进，可以减少追问，把合理假设写入 `假设`，把风险写入 `待确认项`。

## 4. 提问格式

推荐格式：

```markdown
我需要先确认这几个点，确认后再生成 SPEC.md：

## 目标
1. ...

## 边界
2. ...

## 业务术语
3. ...

## 关键决策
4. ...
```

问题要具体，让用户能直接回答。

避免：

- “请补充更多信息”
- “还有什么需求吗”
- “你希望怎么做”

优先：

- “第一版是否包含后台管理？”
- “这里的‘任务’是指用户提交的一次记录，还是后台生成的一次处理流程？”
- “接口失败时是允许用户重试，还是必须自动降级继续流程？”

## 5. 何时可以停止追问

满足以下条件即可生成 `SPEC.md`：

- 目标能写清
- P0 范围能写清
- 非范围能写清
- 核心术语能统一
- 主流程能写清
- 关键规则能写到可实现
- 验收标准能写出至少 3-5 条

剩余不阻塞的问题放到 `待确认项`。

## 6. SPEC.md 落盘规则

最终必须生成文件：

- 默认文件名：`SPEC.md`
- 默认位置：当前工作目录
- 用户指定路径时：按用户指定路径

写入前检查：

- 是否已有 `SPEC.md`
- 是否需要保留旧内容
- 是否应该更新而不是覆盖

写入后检查：

- 文件存在
- 标题存在
- 至少包含目标、范围、功能需求、验收标准、待确认项

## 7. 需求变更同步规则

后续对话中，只要用户补充或改变需求，就要判断是否需要更新 `SPEC.md`。

必须同步的变更包括：

- 目标变化
- 范围变化
- 功能新增或删除
- 术语定义变化
- 流程、状态、角色、权限变化
- 规则、阈值、默认值变化
- 接口、数据结构、外部依赖变化
- 验收标准变化

同步步骤：

1. 读取现有 `SPEC.md`
2. 找到受影响章节
3. 必要时追问变更细节
4. 更新正文中的对应章节
5. 更新变更记录
6. 清理已关闭的待确认项
7. 做一次 review checklist 校验

不要只把变更写在聊天里。聊天里的结论必须回写到 `SPEC.md`。
