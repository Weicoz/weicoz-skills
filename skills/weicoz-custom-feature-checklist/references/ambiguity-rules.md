# 歧义处理规则

## 1. 不清楚时怎么写
不确定的业务项先并入提问闭环问用户（见 SKILL.md「出错后果与提问闭环」）。下列“转入待确认项”只适用于用户明确说先出初稿、不等回答的草稿版。
- 不确定是否属于定制范围：不要写进主表，转入“待确认项”
- 不确定具体实现方式：写结果，不写实现
- 不确定版本归属：标记到“待确认项”
- 不确定颗粒度：先判断这是独立页面、独立管理模块，还是同一功能的自然组成

## 2. 只保留已确认的最小事实
如果客户只确认了结果，没有确认细节：
- 可以写：`支持用户提交报名信息`
- 不要写：`对接第三方实名接口并自动核保`

## 3. 避免常见过度推断
- 不要把“平台人工审核”自动升级成“系统自动审核”
- 不要把“后台登记处理”自动升级成“第三方接口打通”
- 不要把“以后想做”自动算进“本期要做”
- 不要把“示例产品里的完整模块”默认当成客户全要照抄
- 不要因为“订单 / 支付 / 审核 / 提现 / 结算”这些名字常见，就自动判成现成功能并排除

## 4. 同义词处理
客户表述不稳定时，选一个最稳的模块名，并在描述里兼容原话。

示例：
- 原话混用：`签到 / 百日打卡 / 分享打卡`
- 可统一成：`签到/分享打卡`

## 5. 提问闭环与待确认项问什么
优先问真正影响功能边界的问题，例如：
- 该模块是否属于 1.0 首期范围？
- 该流程是人工处理、半自动处理，还是系统直连？
- 该榜单按次数、里程，还是积分统计？
- 该角色是荣誉展示，还是带分佣/返佣逻辑？
- 该清单要按模块级输出，还是按页面级输出？
- 这块是模板底座即可，还是要把承载业务规则的页面单独列出来？

## 6. 页面级与模块级怎么判断
### 倾向页面级
- 用户明确点名页面或节点，例如：商家列表、商家详情、金额输入、订单确认
- 页面本身就是业务链路里的独立确认节点

### 倾向模块级
- 只是同一功能下的余额、流水、记录
- 后台的列表、详情、处理动作天然属于同一管理闭环

## 7. 遇到“标准能力 + 项目规则”时怎么写
- 不写底座名词本身
- 写这个底座在当前项目中承载的特殊规则、字段或流程

示例：
- 不建议直接写：`订单管理`
- 可写：`商家消费订单管理（含支付金额、积分联动、索券处理结果）`
