# 范围判断规则

## 1. 先锁范围，再写主表
在提功能点前，先确认这几项：
- 当前版本范围：一期 / 二期 / 全量 / 指定阶段
- 输出范围：只要定制部分 / 全量功能 / 指定模块
- 拆分维度：用户端 / 平台后台 或其他
- 颗粒度：模块级 / 页面级 / 混合
- 现成功能是否排除

如果这些信息没锁定，不要急着生成主表。

## 2. 哪些内容可以进主表
满足以下任一条件，可作为“定制功能”候选：
- 客户明确说“这个要做”“必须有”“这里分为几个板块”“这个流程要做”。
- 会议中被反复确认，且被归入“定制部分”“重点流程”“前期先做”。
- 同一模块虽然行业通用，但客户当前项目需要额外定制规则、额外页面、额外角色或额外字段承载。

## 3. 哪些内容默认不进主表
以下内容默认排除，除非用户明确要求写进去：
- 纯底座型标准能力，且客户没有提出额外规则或页面要求
- 明确说“模板里有”“现成的”“直接拿去用”的内容
- 纯视觉/排版意见
- 泛泛方向讨论，例如“以后想做社交”“后续可能做 APP”
- 工期、报价、架构、AI 设想、市场愿景

## 4. 不要只看功能名判断是否现成
以下词本身不能直接判定为“现成能力，不写”：
- 订单
- 支付
- 审核
- 提现
- 结算
- 列表 / 详情

判断口径是：
- 如果它只是模板底座能力，不承载项目特有规则，可以不写
- 如果它承载了项目特有业务规则、输入项、显示字段、流转关系、角色动作，就要写进主表

示例：
- 不写：`标准商品订单列表`
- 可写：`商家消费订单管理（含支付金额录入、索券结果、积分联动）`

## 5. 标准能力 + 局部定制 的处理
如果某模块底座是现成能力，但客户提了额外定制：
- 主表只写定制部分
- 不重复写整套标准能力

示例：
- 不写：`商城首页、商品详情、购物车`
- 可写：`商城内新增领队分佣展示入口`

## 6. 先按业务闭环判断，再按页面落表
优先按业务闭环识别功能，不要先机械抄页面名：
- 用户侧操作链路
- 商家 / 服务方处理链路
- 平台后台配置、审核、管理链路

这样更容易判断：
- 哪些页面只是同一功能的自然组成
- 哪些页面是独立节点，必须单独成行

## 7. 颗粒度拆分规则
### 适合单独成行
- 用户明确点名的独立页面
- 独立入口、独立列表、独立详情、独立输入页、独立确认页、独立支付页
- 独立管理模块，例如：商家管理、报名审核、排行规则管理

### 默认合并成一个功能点
- 余额 + 流水
- 列表 + 处理结果
- 规则说明 + 结果展示
- 同一功能下只是自然连续动作，且用户没有要求页面级清单

### 后台默认口径
- 后台“列表 + 详情 + 处理”通常合并成一个管理功能
- 只有用户明确要求页面级清单时，才拆成多行

## 8. 版本范围处理
- 明确属于当前版本范围的，写入主表
- 明确属于后续阶段的，不写入主表，可放到“待确认项”或备注
- 没说清版本归属的，先放“待确认项”

## 9. 端侧拆分规则
默认按用户视角拆：
- 用户端（默认统一口径，包含小程序端 / App端 / H5端 / Web端）
- 平台后台 / 管理后台 / 商家后台 / 运营后台

如果材料本身没有显式拆端：
- 优先按“用户操作发生在哪一端”划分
- 配置、审核、维护、统计，一般归后台
- 浏览、提交、打卡、报名、查看排行，一般归前台/用户端
