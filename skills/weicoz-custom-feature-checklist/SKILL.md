# Custom Feature Checklist

## 与其他 Skill 的关系
- `weicoz-jy-design-demand-archive` 负责落盘路径、文件命名、交付对象和参数基线；功能清单的表结构、输出模板和 xlsx 生成以本 skill 为准。
- 两个 skill 同时命中时，本 skill 是功能清单主流程；归档 skill 不得再定义功能清单表结构、模块结构树或强制 ASCII。
- 导图、需求文档、报价仍按各自专项 skill 执行。

## 出错后果与提问闭环（强制）

> **出错后果**：功能清单是客户逐行确认的内容，写错影响很大，会失去客户对我们的信任，所以不得出错。任何不确定点都必须问用户，不得脑补、补默认值或用模糊说法带过。

- 提问按 `weicoz-jy-design-demand-archive` 第 4 节「提问闭环」执行：先汇总所有问题，用宿主提问工具一次问完；每题首项是我方建议并标“(推荐)”，至少 5 个可选项（工具上限 4 个时加工具自带的 Other）；回答与之前前提冲突时以用户为准；多轮迭代到全部定值。单独调用本 skill 时同样执行。
- 本 skill 的提问点：版本范围、输出范围、拆分维度、颗粒度、某模块属不属于本期或本次定制、现成能力还是定制、退款功能点是否收录，以及功能描述里的金额、比例、门槛、流程。
- 用户回答“需和客户确认”的项：客户版进「方案确认项」，草稿版进「待确认项」。

## 草稿版与客户版（先判定）

| 模式 | 何时 | 规则 |
| --- | --- | --- |
| 草稿版（默认） | 单独使用本 skill、用户说“先出初稿”、或归档 skill 标明内部版 | 标题带“（初稿）”；先跑提问闭环；用户明确说先出初稿、不等回答时，未答项进「待确认项」 |
| 客户版 | 归档 skill 标明客户版，或用户说“给客户确认/发客户” | 标题去掉“初稿”；不留「待确认项」小节；数值取自同项目「已确认参数表」；用户也定不了的项进「方案确认项」；交付前过归档 skill 的 `check_client_ready.py` 门禁 |

- 客户版遇到参数缺口：回到提问闭环问清，不把缺口写进成品。
- 客户版「方案确认项」：Markdown 放在文末标题 `## 方案确认项` 下，ASCII 核对版作为最后一个一级节点，xlsx 由脚本的 `confirm_items` 生成单独 sheet。每条以 `第N条` 开头，写问题、选项（A/B/C）、我方建议、影响；主表功能描述写 `建议值，见方案确认项第N条`。格式细节以归档 skill 第 4 节为准。
- 本文件中“缺口进待确认项”“先出最小草稿”等规则只适用于草稿版，且只在用户明确说先出初稿、不等回答时适用。

## 适用场景
- 用户让你“根据沟通记录/会议纪要/聊天内容整理功能清单”。
- 用户明确说“只要定制部分”“先出初稿”“按用户端/后台拆”，或原话里使用“小程序端/后台”口径。
- 需要把零散需求整理成客户可确认的 Markdown 清单，而不是完整 PRD。

## 默认目标
- 从杂乱沟通材料中提炼出可交付的功能清单初稿。
- 默认只保留本次范围内的定制部分。
- 把不清楚、未定版、存在多种解释的内容收口到“待确认项”。
- 先锁定范围和颗粒度，再写主表，避免边整理边返工。

## 决策规则
- 主表只写本次范围内的定制部分；现成能力只在说明里提及，除非用户明确要求全量清单。
- 如果材料里同时有标准能力和项目差异，只写差异，不重复写整套底座。
- 如果用户没有说明版本范围、输出范围、拆分维度、颗粒度或落点，并入提问闭环一次问清；只有用户明确说先出初稿时，才按“输入边界判定表”先给最小草稿。
- 如果用户只说“先出初稿”，默认交付 Markdown 草稿即完成；用户已要求其他格式时一并生成。
- 待确认项只收集会影响范围、颗粒度或版本归属的问题，不把实现细节塞进去。
- 退款相关功能点（退款扣回、业绩冲减、奖励追回、身份回退、售后退款流程）默认先问是否收录进主表；未确认前放「待确认项」，既不自行写进主表，也不直接删掉。

## 输入边界判定表

| 场景 | 动作 |
| --- | --- |
| 版本范围、输出范围、拆分维度都清楚 | 直接整理主表，并补“待确认项” |
| 有缺口，用户没说“先出初稿” | 汇总全部缺口，按提问闭环一次问完，答完再出主表 |
| 有缺口，但用户明确说“先出初稿”、不等回答 | 先给最小可用 Markdown 草稿；缺口统一进“待确认项”，同时附上问题清单 |
| 要求直接落客户版正式文件 / xlsx / 截图 | 先跑提问闭环；用户也定不了的项进「方案确认项」，不得带待确认项出客户版 |
| 材料里既有标准能力又有项目差异 | 先切出“差异部分”，主表只保留差异 |
| 某模块是否属于本期、本次定制或页面级粒度不清楚 | 不写死进主表，先放“待确认项” |

## 执行边界
- 不把现成模板能力、标准商城/会员/客服/基础内容管理等默认写进主表，除非用户明确要求。
- 不擅自补全复杂业务规则、接口方案、算法细节、工期和报价。
- 不把“以后可能要做”“2.0 再考虑”的内容混进当前版本主表。
- 如果用户没有指定拆分维度，优先按`用户端 / 平台后台`输出。
- 如果源材料里已经说了“标准能力 + 局部定制”，只提取局部定制，不重复写整套标准功能。

需要更细规则时，按需读取：
- 范围判断：`references/scope-rules.md`
- 输出模板：`references/output-template.md`
- XLSX 样式与生成：`references/xlsx-output.md`
- 歧义处理：`references/ambiguity-rules.md`

## 工作流
1. 读取用户给出的源材料，优先级为：用户明确补充 > 指定文件 > 会议纪要/转写 > 上下文推断。
2. 从请求与材料确定以下适用信息；已有答案不重问，格式与颗粒度采用下述默认值：
   - 当前版本范围：只出一期 / 一期+二期 / 指定阶段
   - 输出范围：只要定制部分 / 全量功能 / 指定模块
   - 拆分维度：用户端 / 平台后台 或其他
   - 颗粒度：模块级 / 页面级 / 混合
   - 现成功能是否排除
   - 是否需要落 Markdown / xlsx
3. 提取候选功能点，只记录客户明确表达过的模块、流程、页面或规则。
4. 将内容分成三类：
   - 定制功能
   - 现成/模板能力
   - 待确认项
5. 只把“定制功能”写入主表；若某模块是“标准能力 + 局部定制”，只写定制部分，不重复写整套底座。
6. 先按业务闭环拆内容，再按端落表。优先识别：
   - 用户侧链路
   - 商家 / 服务方链路
   - 平台后台配置、审核、管理链路
7. 再做颗粒度判断：
   - 用户明确点名的独立页面或独立入口，可单独成行
   - 独立列表、详情、输入、确认、支付页，在页面级输出时可单独成行
   - 余额 + 流水、列表 + 处理记录这类自然组成，默认合并成一个功能点
8. 用 `references/output-template.md` 的格式生成 Markdown 初稿，并补“待确认项”。
8.1 用户要纯文本核对稿时，按「ASCII 核对版」生成树状 `.txt`，模块名下一行缩进写功能描述。
9. 按“导出动作判定表”决定停在 Markdown、继续导出 `.xlsx`，还是继续出截图。
10. 用户要求 Excel / xlsx 时，内部核对主表后直接按 `references/xlsx-output.md` 和 `scripts/create_feature_checklist_xlsx.py` 生成 `.xlsx`。
11. 如果要输出截图，截图内容默认只保留表格本体，不带页面留白；宽度默认不超过 `1000px`；高度应与表格实际高度一致；如果用户指定保存目录，截图与导出文件统一落到该目录。

### 🔴 CHECKPOINT · 范围确认
- 如果当前材料没有明确当前版本范围、输出范围或拆分维度，并入提问闭环问清，不要直接假设主表结构。
- 如果用户补充了范围信息，就在同一份清单上增量更新，不重开一份新表。

### 🔴 CHECKPOINT · 导出确认
- 仅用户明确要求“确认后再导出”时等待。已要求 `.xlsx` 或截图则直接生成；未定业务项单列，不把格式导出当作业务定案。
- 用户只说“先出初稿”时，动作停在 Markdown 草稿，不自动继续导出。

## 失败分支

| 触发条件 | 先做什么 | 如果仍不清楚 |
| --- | --- | --- |
| 材料里只有结果，没有边界 | 先从上下文找范围证据 | 找不到就并入提问闭环；用户明确说先出初稿时，只给最小草稿并把缺口进待确认项 |
| 标准能力和定制要求混在一起 | 只写定制差异 | 不要把底座功能写进主表 |
| 用户说“先出初稿”但没说输出格式 | 默认先出 Markdown 版 | 用户要求时生成 xlsx 或截图 |
| 某个模块是否属于本期不明确 | 并入提问闭环 | 不要脑补到主表；用户也定不了时，客户版进方案确认项，草稿版进待确认项 |
| 用户要求按页面级，但材料只到模块级 | 先按模块级落表 | 只有明确页面名时再拆页面 |

## 命名与措辞规范

模块名和功能描述是客户逐行确认的内容，用业务词，不用系统内部用语。

| 不写 | 改写成 |
| --- | --- |
| 归集、汇总入池 | 统计、汇总 |
| 触发结算、触发条件 | 达标条件、满足条件后结算 |
| 拦截、挂起 | 暂停发放、转人工处理 |
| 重算、重跑 | 重新计算 |
| 序次 | 顺序 |
| 写入、落库、生成快照 | 记入、存为当月业绩数 |
| 校验、稽核 | 核对、复核 |

- 客户自己文档里的行业词照用：计提、扣回、核销、分润、点位。
- 模块名控制在 12 个字以内，用“动词 + 对象”或名词短语，不堆三个以上修饰语。
- 功能描述写“谁能做什么、做完得到什么”，一句话一件事；不写表名、字段名、接口名。
- 同一概念全表只用一个词，不出现“份数 / 份额”“点位 / 坑位”两套说法；与同项目导图、需求文档用同一套词。
- 本节是功能清单措辞的唯一标准；归档 skill 不另定。

## ASCII 核对版（用户要纯文本核对稿时）

按树输出，不排宽表格：

```text
一、模块结构树与功能说明
├─ 用户端｜N 项
│  ├─ 一级模块｜N 项
│  │  ├─ 模块名称
│  │  │    功能描述按 72 列折行，续行缩进对齐。
```

- 结构：标题、元数据、`一、模块结构树与功能说明`、`二、定案口径` 或 `待确认项`、`三、说明`。
- 描述按显示宽度折行（中文算 2 列），标点不落到行首，数字与百分号不跨行断开。
- 与主表同源：模块名称、功能描述、口径条目必须一致；树状排版不按行对齐，不要求和主表行数相同。
- 宽表格只在渲染 `.xlsx` 时由主表生成，ASCII 版不复制表格。

## 输出规则
- 如果用户给了明确目录或源文件路径，默认在同目录输出一份 Markdown 初稿。
- 如果用户只是在对话里讨论，没有明确文件落点，先在聊天中输出，再按需落文件。
- 如果用户要求参考某个 Excel 功能清单的格式和样式，优先复用该 Excel 作为样式模板生成 `.xlsx`；不要只输出 Markdown 或 CSV。
- 如果用户没有明确要求直接导出文件，默认交付聊天版 / Markdown 版，不追加导出问卷。
- 主表列名默认使用：
  `类型 | 类型描述 | 模块名称 | 功能描述`
- 若用户明确要求别的字段顺序或表头，按用户要求覆盖默认格式。
- 如果用户要求截图，默认输出“仅表格内容”的图片，不带额外背景、外边距或整页内容。
- 默认输出口径统一使用`用户端`；如果源材料写的是`小程序端`，在未要求细分端侧时也统一按`用户端`落表。

## 导出动作判定表

| 用户当前要求 | 动作 |
| --- | --- |
| “先出初稿” / “先整理一下” | 只出聊天版或 Markdown 草稿 |
| “帮我落文件”但没指定格式 | 先落 Markdown 草稿 |
| “确认后再导 xlsx / 截图” | 先停在 Markdown，等确认后再继续 |
| 明确要 `.xlsx` | 生成 `.xlsx` |
| 明确要截图 | 生成仅表格截图 |
| 同时要 `.xlsx` + 截图 | 先生成 `.xlsx`，再基于最终表格出截图 |

## 质量标准
- 主表每一行都能追溯到源材料中的明确表达。
- 主表只保留当前范围内的定制部分，不混入标准能力。
- 描述要面向客户可读，不写过深的技术实现细节。
- 模块名和描述用业务语言；出现“归集、触发、拦截、重算、序次、写入、落库”时按「命名与措辞规范」改写。
- 出 ASCII 核对版时与主表一致，无行首标点，数字与百分号不跨行。
- 行数宁少勿滥；不确定就问，不要脑补。
- 不要因为“订单 / 支付 / 审核 / 提现 / 结算”这些名字常见，就自动判成现成能力；先判断它是否承载客户项目特有规则。
- 输出 XLSX 必须用 `scripts/create_feature_checklist_xlsx.py`；禁止用 openpyxl/xlsxwriter 另造表结构。
- 输出 XLSX 时要保留同类单元格合并、标题/表头样式、自动换行、列宽和边框，并验证文件能被读取或渲染。
- 输出截图时要验证裁切范围只包含表格，宽度不超过 `1000px`，且图片高度与表格高度一致。
- 功能点颗粒度要稳定：独立页面/独立管理模块可单独成行；同一功能的列表/详情/记录/规则说明不要为了描述链路拆成多行。

## 反例与黑名单
- 不要把完整 PRD、报价清单、工期排期或接口方案混进功能清单主表。
- 不要把“现成模板底座”直接写成客户这次要做的定制功能。
- 不把待确认业务项写成定案；草稿版导出时可交付明确标记待确认项的文件，客户版不可。客户版只允许用户也定不了的项进「方案确认项」。
- 不要重复输出多个近似版本，先在同一份草稿上增量修正。
