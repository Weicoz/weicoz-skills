# Demand Mindmap Organizer

## 功能边界
- 把需求材料整理成思维导图，或在已有导图中增量补充需求。
- 默认最终交付真实 `.xmind` 文件；Markdown 只作为可选中间稿或用户明确要求的附加文件。
- `.xmind` 必须是有效 ZIP 容器及 XMind 数据包，禁止把 Markdown 改后缀伪装成 `.xmind`。
- 导图分客户版与内部版，规则不同；交付对象是客户时默认客户版，客户版正文不允许出现任何待定内容。
- 客户版必须是一套完整可执行的方案，不是需求草稿、评审稿或待拍板清单。按归档 skill 第4节「保留未知继续」获准保留的项，进一级分支 `方案确认项`。

> **出错后果**：导图写错影响很大，会失去客户对我们的信任，所以不得出错。任何不确定点都必须问用户，不得猜测或补默认值。生成前读取并执行 `weicoz-jy-design-demand-archive` 第4节：共用业务基线前置确认、严格 >90% 把握度、集中工具提问及「保留未知继续」例外均以该节为准。单独调用本 skill 时同样执行；已有确认记录直接复用。
- 优化方向是导图产出质量：结构更贴近用户历史导图风格，模式电商规则表达更清楚，节点层级更稳定。
- 不把本技能扩展成完整 PRD、报价清单、数据库设计、页面原型或接口文档。
- 不为了套模板改变项目原有导图结构；已有导图优先沿用原结构。

## 适用场景
- 用户让你“整理成思维导图”“先给我文字版导图内容”“按层级梳理需求”“更新到导图上”“优化导图”。
- 用户给的是会议纪要、沟通记录、聊天记录、PRD 草稿、录音转写、PDF、零散说明或现有思维导图。
- 用户给了一个导图目录，希望参考其历史导图风格优化输出质量。
- 模式电商、积分商城、拼团、排位、补贴、挂售、返券、链动、分销、代理/经销商分级折扣等业务，默认也使用本技能整理。

## 默认目标
- 把杂乱需求整理成客户一眼能看懂的文字版思维导图。
- 直接生成可由 XMind 打开的 `.xmind` 文件，并返回文件绝对路径。
- 已有客户手改导图时，以其最新保存版为术语、节点顺序和表达风格的首要依据；只补缺口，不回退客户修改。
- 每个关键节点都不是空名词，要有一句解释说明用途、规则、触发条件或业务结果。
- 导图必须包含 `名词解释` 分支；已有客户导图使用 `核心概念` 时沿用该分支承担同一职责。每个术语写清业务定义；内部版另行标注根据哪份材料、是否已确认，客户版不写材料来源与确认状态。没有专用名词时写“暂无专用名词”。
- 导图正文必须用大白话；不要把内部工作词 `边界`、`范围`、`颗粒度`、`主表`、`闭环`、`节点`、`质量阀门` 写给客户，分别改成“这次要做的内容”“拆到什么程度”“功能清单”“从开始到结束的完整流程”“条目”“检查”。
- 导图必须收全源材料里出现的所有业务流程，包括用户操作、后台操作、商家/服务方操作、外部服务对接、审核、取消、退款、结算和异常处理；不清楚的流程：内部版列出并标“待确认”，客户版先问清再写。
- 每条流程按顺序用短句写清：每一步只写“谁做什么”，有判断时标明条件，结束时写明结果。所需字段、详细规则和异常处理放入需求文档，禁止用“处理完成”“进入下一步”等空话。
- 模式电商导图重点说清楚：
  - 完整流程：用户如何消费，获得什么资产，资产如何流转，谁获得奖励，如何复购或结束。
  - 身份体系：有哪些身份、准入条件、等级差异、折扣/权益/权限。
  - 奖励机制：奖励类型、触发条件、发放对象、计算口径、发放资产。
  - 积分券资产：来源、用途、限制、提现/转赠/冻结/抵扣规则。
  - 业务流程：注册、购买、兑换、参团/排队、释放/补贴、核销、提现、复购等主链路。
  - 后台配置：比例、等级、配额、拨比、订单、券、钱包、资金池、审核、统计。
- 导图层级要克制（根节点算第 1 层）：默认 3-4 层，最多 5 层；一级分支默认 5-8 个，每个分支保留最关键的 3-7 条。流程必须全部出现，但只画清流程骨架，不把字段、接口和实现细节塞进导图。
- 导图负责让客户快速看懂，需求文档负责详细说明；“流程全覆盖”不等于“每一步都展开成一大段文字”。
- 如果是在已有导图上补需求，优先把新增内容嵌入原有相关节点，不默认追加“本次新增需求”独立尾部板块。

## 资料读取与取材方式
- 读取优先级：
  - 用户当前明确补充
  - 用户指定文件
  - 同项目最新沟通记录
  - 同项目最新需求文档
  - 现有导图
  - 历史同类导图风格参考
- 如果用户给的是目录，先找同项目名或同业务模式相关的导图、需求文档、沟通记录。
- 读取 `.xmind` 时优先解析 `content.json`；旧格式再解析 `content.xml`。同名 PNG/JPG 只作为视觉辅助，不替代结构读取。
- 图片文字识别不完整时，不要硬编：内部版放入待确认，客户版向用户要原文。
- 导图和需求文档不完全一致时，不要简单合并成重复节点；按最新、最明确材料整理；冲突点内部版写到 `待确认项`，客户版按提问闭环让用户选定。
- 参考历史导图时，只学习结构风格和表达方式，不复制其他项目的具体比例、金额、身份名到当前项目。

## 用户历史导图风格
- 常见风格是“短标题 + 简短规则说明 + 子规则列表”，少用长段落。
- 模式电商导图常见一级分支不是固定三段式，而是围绕业务重点组织，例如：
  - `身份`
  - `推广奖励`
  - `奖励模式`
  - `分红奖励`
  - `业绩奖励`
  - `积分规则`
  - `业务流程`
  - `平台后台`
  - `用户端`
- 客户确认型导图优先用业务语言，不写技术实现细节。
- 功能型导图可以按 `平台后台 / 用户端 / 商家端 / 代理端` 拆，但模式电商规则型导图优先按 `身份 / 奖励 / 资产 / 流程 / 后台配置` 拆。
- 无现成导图时，先在内部形成稳定层级，再写入真实 `.xmind`；不要把 Markdown 当默认最终交付。

## 客户业务说明风格（强制）

- 先继承客户已改用的词和顺序。继续使用客户当前术语，不擅自换成历史文档、通用模板或技术实现中的近义词。
- 一级分支标题使用专业、稳定的项目表达，例如“项目定位与建设目标”“用户下单与配送流程”“平台后台与门店协同”“后续扩展规划”；不要把一级标题写成口语句，也不要堆“交易主链、业务闭环”等过大的词。
- 二级、三级节点使用客户看得懂的大白话，直接说明谁做什么、怎么做、得到什么；标题专业不等于正文复杂。
- 角色分支优先使用“角色关系”，直接列品牌方、用户、合作门店、总部/直营店、配送人员等身份和相互关系；只有客户明确采用“参与身份”时才沿用该名称。
- 一级分支先讲模式，不先讲页面。优先 `身份 / 奖励 / 积分资产 / 流程 / 平台后台`；功能仅放在对应业务分支下，不抢主线。
- 一个节点只说一件事，采用“谁做什么，得到什么，结果怎样”的短句。少用定义式、技术式、审计式长句。
- 每个条目优先回答“谁来用、要做什么、什么时候做、最后得到什么”；客户看不懂的技术词必须紧跟白话解释。
- 算法面向客户时，拆成中文业务步骤：先说明依据什么算、再说明结果如何产生、最后说明结果如何变化。不要显示变量名、等式或开发公式。
- 需要数字时必须说清计算基数、比例范围和结果归属，不写脱离上下文的百分比；同时给一个与客户口径一致的例子。
- 客户导图默认不展开接口、数据结构、审计、风控、合规等实现细节。客户没要求时，用业务结果或后台能力说明；内部评估版才展开技术实现细节。
- 客户主动删掉的分支，不默认加回；客户版也不得把删掉的内容换个说法塞回去。
- 新增规则只有来源明确时才写成定案。来源为参考 PPT、历史模式或推断时，内部版标 `参考`、`后台可配置` 或 `客户需确认`；客户版不得出现这三类标记，必须先问清再写。
- 客户版只写已经定下来的那一套。不写备选方案、不写"两种做法对比"。按共享规则获准保留的未知项，正文写有依据的建议值，并引用 `建议值，见方案确认项第N条`；问题、选项与影响只写在 `方案确认项` 分支里。

## 客户版与内部版分流（强制）

先判定本次交付对象，再决定怎么写。

### 判定
- 用户说"最终给客户""给黄总看""发给客户"，或默认对外交付 → **客户版**。
- 用户说"内部评估""评审版""我们自己看""先评估工作量" → **内部版**。
- 没说清时按客户版处理，并在回复里说明；不要先出一版内部版当成品。
- 内部版必须在文件名或正文首行显式标注"内部版"，并列出还缺哪些参数。

### 客户版规则
- 全文不得出现：`待确认`、`待定`、`未定`、`暂定`、`客户需确认`、`参考`、`以最终为准`、`待客户`、`另行公布`、`后续再定`。
- 白名单（属正常业务用词，不判失败）：订单状态 `待确认收货`、`待确认付款`、`待确认订单`；价格语境 `参考价`、`参考售价`。词表与 `weicoz-jy-design-demand-archive` 的零待定门禁一致。
- 出图前按共享规则集中问清；用户已明确允许保留的未知项进入 `方案确认项`，按已有依据继续出图。
- 尚未答复且未获准保留的业务缺口，先交付问题清单与我方倾向；明确例外不再重复阻塞。
- 提问阶段遇两份材料冲突（会议 / 文档 / 聊天 / 系统现状），把冲突点、双方原文、我方倾向、按 A 或按 B 的后果一起给用户选，不得用"以会议为准"自动裁决；这些内容不进客户版成品。
- 退款类规则（扣回、冲减、追回、身份或点位回退、售后退款流程）先问是否收录：未确认不进客户版导图，内部版放进 `待确认项`；用户确认不收录时，不在导图里留任何退款节点。
- 问不完就继续问下一轮，直到全部定案；按共享规则获准保留的未知项进 `方案确认项`。禁止用"平台另行公布""按行业惯例"这类模糊表述顶替具体规则。
- 客户删掉的节点不复原；客户手改过的措辞沿用。
- 正文不给选项、不给建议、不给风险对比；`方案确认项` 分支除外。测算与副作用可以用事实陈述保留（例如"人数少于 5 人时封顶会让按比例变成按人头等分"），但不写成"建议改成"。
- `方案确认项` 分支格式：放在最后一个一级分支；每个子主题以 `第N条` 开头，N 从 1 连续编号；其下依次写问题、选项（用 A/B/C）、我方建议、影响。正文引用编号与条目必须一一对应，`validate_xmind.py --client` 会核对。没有需客户确认的项时不建该分支。
- 允许保留平台后台可配置的表述，但必须写清默认值和取值范围，不能只写"后台可配"。

### 内部版规则
- 保留 `待确认项` 分支、`参考` 标记、备选方案对比与工作量提示。
- 内部版转客户版时，先按客户版门禁重跑一遍，不得直接改标题交付。

### 定案后的一致性
某参数定案后，全图检索同一参数的其他表述并同步改写或删除。禁止一处已定案、另一处仍写待确认，或导图已定案、沟通记录仍列该项为待定。

参数变更时，同项目目录下的沟通记录、需求文档、功能清单（Markdown + ASCII）与导图（Markdown + ASCII + `.xmind`）必须一起改；改完重跑零待定门禁，并检索旧口径关键词（应为 0 命中）。同轮产出多份文件时，优先从同一份参数数据生成，不手改多份。

## 主干选择规则

### 1. 已有导图增量更新
- 先识别原导图的一级分支和节点命名。
- 先读取磁盘中最新保存的导图；客户手改版优先于旧 Markdown、旧导图和历史交付。若客户端可能仍有未保存修改，先提醒保存，再写回文件。
- 保留客户改过的名称、节点顺序和删减结果。不得因模板要求重新加回客户删掉的一级分支。
- 新增需求放进最贴近的原节点：
  - 术语解释放入 `名词解释`、已有 `核心概念` 或对应概念分支；若均不存在且客户未明确删除，新增 `名词解释` 分支。
  - 身份、等级、折扣、权限放入 `身份体系` 或 `身份`。
  - 奖励、拨比、分润、补贴、释放放入 `奖励机制`、`奖励模式` 或对应奖励分支。
  - 积分、券、钱包、贡献值、算力、福豆放入 `积分规则`、`积分券资产` 或对应资产分支。
  - 参团配额、排队、每日上限、参数放入参团/拼团/后台配置相关节点。
  - UI、文案、互动体验放入 `优化体验` 或前端体验节点。
- 保留原有文字和节点顺序，除非用户明确要求重构。
- 不要为了省事在末尾单独加 `本次新增需求调整`，除非用户明确要求保留新增清单。

### 2. 新建模式电商导图
- 不要机械套 `业务板块 / 用户身份 / 业务流程`。
- 优先根据材料选择 5-7 个最能说明模式的主干：
  - `名词解释`
  - `身份体系`
  - `业务模式`
  - `奖励机制`
  - `积分券资产`
  - `业务流程`
  - `后台管理`
  - `待确认项`（仅内部版）
  - `方案确认项`（仅客户版，且有需客户确认的项时）
- 如果项目本身更像用户历史导图中的某类结构，可改用更贴近的分支名，例如 `身份 / 推荐奖励 / 分红奖励 / 积分规则 / 业务流程`。

### 3. 非模式电商导图
- 如果不是模式电商，仍可使用原通用三主线：
  - `名词解释`
  - `业务板块`
  - `用户身份`
  - `业务流程`
- 用户明确指定 `前台 / 后台`、`商家端 / 用户端 / 平台端`、`业务模块 / 数据流 / 角色分工` 时，按用户指定结构。

## 节点质量规则

### 1. 节点要带信息量
- 差：`代理商`
- 好：`代理商：平台设定的区域/层级代理角色，可按等级享受不同折扣价和区域奖励。`
- 差：`直推奖励`
- 好：`直推奖励：用户推荐下级完成指定订单后，推荐人按订单金额或让利金额获得对应比例奖励。`

### 2. 模式节点要写清闭环
- 消费类节点写清：谁下单、买什么、获得什么资产、是否产生奖励。
- 兑换类节点写清：用什么兑换、兑换成什么、能否转让、是否继续产生权益。
- 释放类节点写清：释放来源、释放条件、释放周期、释放资产、停止/重启条件。
- 出局类节点写清：出局条件、出局奖励、出局后资产状态、是否激活下一轮。
- 挂售/抢购类节点写清：资产来源、上架条件、成交方式、手续费、到账和限制。

### 3. 身份、等级、权益分开
- `身份` 是角色：会员、推广员、代理商、经销商、门店、合伙人、股东。
- `等级` 是档位：V1/V2/V3、省/市/区、普通/高级/顶级。
- `权益` 是可获得的折扣、奖励、分红、核销、配送、提现或后台权限。
- 同一身份只是等级或折扣不同，不拆成多个平级身份；放到身份下的等级节点。

### 4. 奖励机制要可核对
- 奖励节点尽量包含：触发条件、奖励对象、计算口径、发放资产、限制条件。
- 直推、间推、级差、平级、区域、分红、招商、核销、配送、助力、补贴、加速释放等，不要混在一句话里。
- 如果有拨比或成本测算，单独放 `拨比 / 成本测算`，避免比例散落后看不出总盘。
- 用户曾明确纠正过奖励不能缺失；模式电商导图中，奖励机制必须作为重点分支充分展开。

### 5. 积分券资产要讲来源和用途
- 每种资产说明来源、用途、能否提现、能否转赠、是否冻结、是否可抵扣、是否继续产生奖励。
- 常见资产包括积分、消费券、兑换券、购物券、权证、贡献值、算力、福豆、红包、零钱、余额。
- 现金订单、券单、积分订单、复购订单规则不同，要并列说明差异。

### 6. 代理商和经销商
- 经销商和代理商都应表达为：账户身份 + 身份等级 + 不同等级对应不同折扣价。
- 经销商/代理商下单如果不赠送积分或兑换积分，要明确写在身份节点下。
- 代理商如果同时有区域奖励职责，要区分 `下单折扣身份` 和 `区域/层级奖励角色`。
- 不同身份等级对应不同折扣时，写为等级规则，不要误写成奖励比例。

### 7. 参团/排队/配额
- 每日参团配额、按时间顺序放行、每用户每日上限、同用户多券拆分到多天，应放入参团、拼团、出局、排队或后台配置节点。
- 配额是平台控盘参数，应在后台配置中保留管理入口。
- 同一用户多券不应默认同日全部参团，除非需求明确允许。

### 8. 待确认内容处理
- 下列内容不要强行写进主干为已定方案：
  - 是否纳入本期不明确
  - 是系统内做还是线下做不明确
  - 是否接外部系统不明确
  - 奖励比例或拨比冲突
  - 资产能否提现/转赠/继续产生奖励不明确
  - 公司主体、区域归属、订单回滚规则不明确
- 内部版统一放到 `待确认项`、`说明` 或 `后续规划`。
- 客户版不允许留这三类落脚点：先向用户问清并定案，再写成确定规则。按共享规则获准保留的未知项进 `方案确认项`，正文仅写有依据的建议值或已知功能并引用编号；不得静默删掉。

### 9. 拆分粒度：一个主题只放一个结论
- 一张表、一组取值（档位、比例、多身份取值）、一组算例步骤，必须拆成子主题，不要把 5 个档位压进一行。
- 父主题写口径（算什么、按什么基数、什么时候生效），子主题每个只写一个取值或一步计算。
- 算例按“池 / 总份数 / 每份金额 / 各身份结果”这类步骤拆，一步一条，读者能顺着算一遍。
- 拆出来的节点放到三级、四级，不加宽一级分支，也不新增一级分支。
- 两类不拆：一句规则里本来就并列的两三个词（“直推 10%、间推 30%”）属于同一条规则；算例最后的汇总结果（“V1 拿 500 元、V2 拿 1,000 元、V3 拿 1,500 元”）保留一行，拆开反而看不出合计。
- 同一信息只在一个分支写取值，其他分支只写定义并指向取值所在分支，避免一处改了两处没改。

## 工作流
1. 读取源材料，先看用户指定文件，再看同项目需求文档/沟通记录/导图。
1.1 判定客户版还是内部版（见「客户版与内部版分流」）。
1.2 按归档 skill 第4节先确认共用业务基线并复用参数表，再出图；已获准保留的未知项按当前已知内容继续，不重复提问。
2. 判断这份导图用途：
   - 给客户看：偏业务语言、少技术词、强调模式逻辑，且零待定项。
   - 给内部评估看：偏模块边界、规则完整性、待确认项。
3. 判断是否模式电商：
   - 出现积分、券、奖励、代理、分红、补贴、排位、拼团、挂售、释放、滑落、出局等，默认按模式电商质量标准整理。
4. 识别现有导图风格：
   - 已有导图增量更新时，沿用客户最后保存的原结构、词汇和删减结果。
   - 新导图参考用户历史导图风格，但不复制其他项目内容。
5. 提取并合并候选条目，同时逐条登记源材料提到的业务流程：
   - 同类角色合并。
   - 同类流程合并。
   - 同类奖励归类。
   - 同类资产归类。
6. 检查模式电商关键分支是否缺失：
   - 名词解释
   - 身份等级
   - 奖励机制
   - 积分券资产
   - 业务流程
   - 后台配置
   - 待确认项（仅内部版；客户版去掉此项，缺口先在提问阶段闭合；获准保留的未知项改进 `方案确认项`）
   - 对照源材料逐条检查全部业务流程，确认用户、后台、商家/服务方和异常处理流程没有遗漏。
7. 控制导图复杂度：默认 3-4 层，最多 5 层；一级分支默认 5-8 个，每个分支默认不超过 7 条；需要更细的规则时往下加深二三级条目，不加宽一级分支。主题数只统计有实质内容的条目，禁止为凑档位加空节点；按「拆分粒度」拆开取值与算例产生的节点属于正常增长，计入主题数。超过档位上限时把明细外置到需求文档，不把表格压回一行。详细规则、字段、接口和异常说明放入需求文档。
8. 逐项检查计算基数、对象、结果归属和完整流程；客户版将复杂计算改为中文步骤与例子。
9. 在内存或临时 JSON 中形成完整层级，不把中间稿当交付物。
10. 选择 XMind 母版并生成真实 `.xmind` 文件。
11. 验证 ZIP 完整性、必需成员、根节点和一级分支；验证失败不得声称完成。
12. 返回 `.xmind` 文件绝对路径；只有用户明确要求时才额外输出 Markdown。

### ASCII 流程图要求
- 用户要求“ASCII 流程图”“完整流程图”或“流程图文档”时，先在同一项目目录生成 `项目名-ASCII流程图-YYYYMMDD.txt`，再生成 Markdown 或真实 `.xmind`。需要按角色分泳道时改用 `weicoz-tree-swimlane-diagram`。
- ASCII 文件使用从上到下的流程图，不用功能树代替：逐步写出操作人、动作、判断条件、审核人、锁定或等待状态、下一步和结果。
- 多角色、多资产、多审核项目必须逐条覆盖注册归属、采购或下单、付款凭证、审核、资产流转、发货提货、通知、到期和失败处理；材料没有明确的结果：内部版标“待确认”，客户版先问清。
- ASCII 流程图是流程核对稿；真实 `.xmind` 仍是默认最终思维导图文件。

## 强制质量阀门

生成前和交付前都必须执行。任一项不通过，不得把导图称为完成品。

### 1. 源材料覆盖检查

先在工作区列一张不交给客户的覆盖表：`源材料位置 | 提到的角色/流程/规则/页面 | 导图位置 | 已确认/待确认`。逐条登记，至少检查：

- 所有角色：用户、平台、商家/门店、服务人员、推广/合作方及材料中出现的其他身份。
- 所有流程：进入、下单、支付、履约、取消、退款、结算、审核、异常和人工处理；材料未提到的不要编造。
- 所有客户点名模块、页面、数据查看需求、外部系统和后续规划。
- 客户自造词、项目内简称和可能有多种理解的概念；导图一级必须有`名词解释`或`核心概念`，每个词写业务定义（内部版另附材料依据与确认状态）。不要把用户、门店、订单、支付、分成、配送、私域等通用业务词塞进去，除非材料给了该词不同于常规理解的专门规则。
- 所有数值、比例、门槛、时限和归属；不完整时内部版写进 `待确认项`，客户版回到提问闭环。

长会议、需求文档、功能清单或客户明确要求“详细导图”时，禁止只用“业务模式/用户端/后台”三层骨架代替覆盖表。每项必须能定位到导图中的具体分支；找不到位置即视为遗漏。

### 2. 复杂度分档

按源材料选档，不能为了通过检查故意降档：

| 情况 | 档位 | 结构要求与主题数区间 |
| --- | --- | --- |
| 简短单一规则，少于 3 个角色和 2 条流程 | `small` | 3 个一级分支、20-45 个主题、2 层深度 |
| 普通沟通或单模块需求 | `normal` | 5 个一级分支、50-100 个主题、3 层深度 |
| 长会议、多个角色/流程、已有需求文档或功能清单、客户要求细版 | `large` | 7 个一级分支、80-200 个主题、3 层深度 |

`large` 导图还必须独立呈现：名词解释/核心概念、业务目标/模式、角色关系/参与身份、主要业务流程、前台或用户操作、后台或服务方处理、数据/收益或规则、后续规划；内部版另加待确认项。材料没有某类内容时：内部版写“材料未提及”，客户版不建该分支并在回复里说明。

档位主题数是**下限校验**，不是上限配额：按「拆分粒度」拆开取值和算例只会增加主题数，不会因为拆细被卡。上限只用于控制可读性。

超过区间上限时按顺序**外置明细**，不把表格压回一行：

1. 把档位明细、算例步骤、字段级规则移到同项目的需求文档或功能清单。
2. 导图保留父主题，加一行“明细见需求文档 X 节”，保证客户能顺着导图找到细节。
3. 一级分支宽度上限仍是 8 条（脚本 `--max-first-level` 默认 8）；节点数靠二三级条目增长，不靠加宽分支或加空节点。

校验时显式带上限：`--profile large --max-topics 200`。`--max-topics 0` 关闭上限检查。

### 3. 内容密度检查

- 一级分支不能只是空分类；每个关键分支至少有 3 个具体条目。
- 流程分支必须按先后顺序写“谁做什么 -> 判断什么 -> 得到什么”；不能只写“下单、支付、配送”三个名词。
- 页面或后台功能被客户点名时，写清使用者、操作和结果；不要只写模块名称。
- 不把所有细节塞进一个一级分支；角色、流程、规则、后台处理分别放到最接近的分支。
- 不确定规则：内部版放 `待确认项`，客户版先问清；不能因缺少细节把整个流程删掉。

### 4. XMind 包和结构检查

生成后先做覆盖表复核，再运行对应档位的脚本检查；`large` 项目还要显式检查关键一级分支：

```bash
python3 scripts/validate_xmind.py /absolute/path/思维导图.xmind \
  --profile large \
  --require '名词解释' \
  --require '角色关系' \
  --require '业务流程' \
  --client
unzip -t /absolute/path/思维导图.xmind
```

分支名称可按客户术语调整；使用不同名称时，`--require` 必须改为实际名称。`--client` 执行客户版零待定门禁，仅客户版加；内部版改为 `--require '待确认项'`。再核对：`content.json` 可被 `jq empty` 解析、根标题正确、每个一级分支在 XMind 中实际存在、主题/扩展资源在复用母版时仍存在。

### 5. 禁止交付条件

出现下列任一情况，回到整理阶段：

- 只验证 ZIP 能打开，没有核对源材料覆盖和主题数量。
- 长会议导图低于 `large` 档，或用户已指出“内容太少”。
- 客户点名的角色、流程、页面、规则、异常或后续规划没有对应条目。
- 用空概念代替具体动作，例如只写“订单管理”“配送处理”“分成体系”。
- 把不确定内容当成已确认事实，或为减少分支直接删除待确认流程。
- 为了压低主题数，把档位表、多身份取值或算例步骤压回一行。
- 主题数超过档位上限，又没有把明细外置到需求文档。

### 6. 客户版零待定门禁

对客户版导图全文检索：`待确认|待定|未定|暂定|客户需确认|参考|以最终为准|待客户|另行公布|后续再定`。执行方式：`validate_xmind.py --client`；同项目的 Markdown 与 ASCII 稿用归档 skill 的 `check_client_ready.py` 检查。

白名单（属正常业务用词，不判失败）：订单状态 `待确认收货`、`待确认付款`、`待确认订单`；价格语境 `参考价`、`参考售价`。词表与 `weicoz-jy-design-demand-archive` 的零待定门禁一致。

`方案确认项` 分支不查禁词；`--client` 同时核对正文 `方案确认项第N条` 与分支条目 `第N条` 是否一一对应。

命中白名单之外的词时，按共享规则问清或处理已获准保留的例外，再重跑门禁；不得改词绕过，也不得把未问过的业务缺口直接塞进 `方案确认项`。

同时检查三件事：

- 客户手改版里删掉的节点是否被复原。
- 是否新增了备选方案、建议、对比、待拍板类节点。
- 已定案的参数是否还有别处写成待定。

### 7. 规则可复算检查（涉及金额、比例、周期时强制）

每个奖励、分红、结算、分账节点必须能回答五件事：算谁的、按什么基数、算多少、什么时候停、钱从哪来。

- 客户版至少给两组具体数字算例，算例必须用脚本核算，不允许心算或估算。
- 必须给规模敏感度：人数变化或流水变化后结果差多少。
- 规则有副作用必须写出来，例如封顶规则在人数少时会把按比例分配变成按人头等分。
- 客户追加新规则后，受影响的所有数字、算例和主干小结必须重算并同步；禁止只加节点不改数。同项目的沟通记录、需求文档、功能清单也要一起改。
- 算例里的天数、金额必须能对上主公式，交付前用同一段脚本复验一遍。

## 真实 XMind 输出（默认且强制）

### 母版选择

按以下顺序选择样式来源：

1. 用户指定的 `.xmind`。
2. 同项目最新、已由客户修改保存的 `.xmind`。
3. `jy-design` 中业务类型接近、样式完整的 `.xmind`。
4. 没有合适母版时，使用生成器默认主题。

已有导图增量修改时保留原文件，默认生成带日期的新 `.xmind`；除非用户明确要求覆盖。母版含 `theme`、`extensions`、缩略图或其他资源时继续保留主题与扩展，避免生成无主题裸图。

复用母版时，`build_xmind.py` 会自动删除包内旧的 `Thumbnails/` 及 `manifest.json` 对应条目，避免文件列表显示上一个项目的缩略图。手工改包时同样要删。

### 生成器

先把最终导图层级写成 UTF-8 JSON。根节点使用 `title`，下级使用 `children`；子节点可写字符串或 `{ "title": "...", "children": [...] }`。

```json
{
  "title": "项目名",
  "children": [
    {
      "title": "身份体系",
      "children": [
        {
          "title": "代理商",
          "children": ["按等级享受不同商品折扣"]
        }
      ]
    },
    {
      "title": "业务流程",
      "children": ["用户下单：选择商品并支付，订单进入待发货"]
    }
  ]
}
```

对 `content.json` 格式母版，使用技能自带脚本：

```bash
python3 scripts/build_xmind.py outline.json \
  --template /absolute/path/style-source.xmind \
  --output /absolute/path/项目名-思维导图-YYYYMMDD.xmind \
  --markdown /absolute/path/项目名-思维导图-YYYYMMDD.md \
  --ascii /absolute/path/项目名-ASCII树状图-YYYYMMDD.txt
```

无母版时省略 `--template`；不需要 Markdown 或 ASCII 稿时省略对应参数。三份文件来自同一份大纲，改口径时改大纲后重跑，不手改单份。脚本会保留母版主题资源、替换导图内容，并校验生成包。母版只有 `content.xml` 时不要强行套用 JSON 脚本；应结构化解析并更新 `content.xml`，保留原包其他成员后重新压缩。

### 验证

至少执行：

```bash
unzip -t /absolute/path/思维导图-YYYYMMDD.xmind
unzip -l /absolute/path/思维导图-YYYYMMDD.xmind
```

同时确认：

- 包内存在 `content.json + metadata.json + manifest.json`，或旧格式的 `content.xml + meta.xml + META-INF/manifest.xml`。
- 根节点标题与项目名一致。
- 预期一级分支全部存在。
- 复用母版时，主题、扩展和资源仍存在。
- 文件可被 ZIP 读取；不要仅检查扩展名。

## Markdown 例外

- 用户明确要求 Markdown 时才输出 `.md`。
- 其他归档 skill 明确要求 Markdown 备份时，可在 `.xmind` 旁额外生成同名 `.md`。
- 即使生成 Markdown，真实 `.xmind` 仍是本技能默认最终交付物。

## 质量标准
- 功能边界没有跑偏：仍然是需求思维导图整理，不是 PRD、报价或原型。
- 最终存在真实、可解压、结构有效的 `.xmind` 文件，不是改后缀的 Markdown。
- 生成后执行包完整性检查，并核对根节点与一级分支。
- 有合适母版时继承主题样式；已有客户导图增量修改时保留原文件。
- 导图第一眼能看出完整流程。
- 导图必须覆盖源材料提到的全部业务流程；每条流程写清谁来做、先做什么、什么时候判断、最后得到什么。
- 每条流程必须能顺着读懂：有明确负责人、具体动作、必要判断和结果；缺少关键信息时内部版标“待确认”，客户版先问清；详细输入和处理规则放入需求文档。
- 导图不能堆成大段说明书；每条流程用短句表达，细节转到需求文档；超过 5 层或分支过多时必须合并同类内容。
- 节点不是空名词，关键节点都有一句业务解释。
- 必须有 `名词解释` 或 `核心概念` 分支；每个影响理解的术语都包含业务定义；内部版另标根据哪份材料和是否已确认，客户版不写材料来源与确认状态；无专用名词时明确写“暂无专用名词”。
- 成品不得出现内部工作词或只给术语不给解释；先写白话，再补必要的技术名称。
- 身份、等级、权益、折扣、奖励比例互相区分。
- 奖励机制充分展开，不漏掉直推、代理、区域、分红、释放、配额等关键规则。
- 积分券资产讲清来源、用途和限制。
- 后台配置能覆盖关键参数、比例、等级、配额、钱包、订单、券和审核。
- 已有导图增量更新时，新内容嵌入原结构，不集中堆到末尾。
- 客户手改导图后，术语、节点顺序、删减结果必须保留；新增内容只进入最近业务节点。
- 客户版读完应先看懂消费、奖励、积分如何循环；页面、接口、风控不应盖过业务主线。
- 所有比例必须写明计算基数、适用范围和结果归属，避免“总拨比”一类歧义表达。
- 复杂价值、发放、释放、销毁等规则先用中文步骤和客户例子说明；技术公式只在用户明确要内部版时保留。
- 不把其他项目案例的具体比例、门槛、身份名混入当前项目。
- 不把不确定内容写成已确认方案。
- 客户版零待定：交付前全文检索待定类字样，白名单外命中即不交付（白名单见「客户版零待定门禁」）。
- 客户版是一套完整方案：有明确参数、有算例、有停止条件、有钱从哪来，读完能直接执行。
- 客户版正文不出现备选方案和待拍板清单；获准保留的未知项按共享规则引用 `方案确认项第N条`，不强填无依据的建议值。测算与副作用用事实陈述，不写成选项。
- 涉及金额、比例、周期的规则必须给至少两组经脚本核算的算例，并给规模敏感度。
- 一个主题只放一个结论；档位表、多身份取值、算例步骤都拆成子主题，不压在一行。
- 主题数落在档位区间内；超上限时明细已外置到需求文档，导图保留父主题与引用。
