# Demand Mindmap Organizer

## 功能边界
- 把需求材料整理成思维导图，或在已有导图中增量补充需求。
- 默认最终交付真实 `.xmind` 文件；Markdown 只作为可选中间稿或用户明确要求的附加文件。
- `.xmind` 必须是有效 ZIP 容器及 XMind 数据包，禁止把 Markdown 改后缀伪装成 `.xmind`。
- 优化方向是导图产出质量：结构更贴近用户历史导图风格，模式电商规则表达更清楚，节点层级更稳定。
- 不把本技能扩展成完整 PRD、报价清单、数据库设计、页面原型或接口文档。
- 不为了套模板改变项目原有导图结构；已有导图优先沿用原结构。

## 适用场景
- 用户让你“整理成思维导图”“先给我文字版导图内容”“按层级梳理需求”“更新到导图上”“优化导图”。
- 用户给的是会议纪要、沟通记录、聊天记录、PRD 草稿、录音转写、PDF、零散说明或现有思维导图。
- 用户给了一个导图目录，希望参考其历史导图风格优化输出质量。
- 模式电商、积分商城、拼团、排位、补贴、挂售、返券、链动、分销、代理/经销商分级折扣等业务，默认也使用本技能整理。

## 默认目标
- 把杂乱需求整理成客户一眼能看懂的文字版思维导图。
- 直接生成可由 XMind 打开的 `.xmind` 文件，并返回文件绝对路径。
- 已有客户手改导图时，以其最新保存版为术语、节点顺序和表达风格的首要依据；只补缺口，不回退客户修改。
- 每个关键节点都不是空名词，要有一句解释说明用途、规则、触发条件或业务结果。
- 导图必须包含 `名词解释` 分支；已有客户导图使用 `核心概念` 时沿用该分支承担同一职责。每个术语写清业务定义、根据哪份材料、是否已确认；没有专用名词时写“暂无专用名词”。
- 导图正文必须用大白话；不要把内部工作词 `边界`、`范围`、`颗粒度`、`主表`、`闭环`、`节点`、`质量阀门` 写给客户，分别改成“这次要做的内容”“拆到什么程度”“功能清单”“从开始到结束的完整流程”“条目”“检查”。
- 导图必须收全源材料里出现的所有业务流程，包括用户操作、后台操作、商家/服务方操作、外部服务对接、审核、取消、退款、结算和异常处理；不清楚的流程也要列出并标为“待确认”。
- 每条流程按顺序用短句写清：每一步只写“谁做什么”，有判断时标明条件，结束时写明结果。所需字段、详细规则和异常处理放入需求文档，禁止用“处理完成”“进入下一步”等空话。
- 模式电商导图重点说清楚：
  - 完整流程：用户如何消费，获得什么资产，资产如何流转，谁获得奖励，如何复购或结束。
  - 身份体系：有哪些身份、准入条件、等级差异、折扣/权益/权限。
  - 奖励机制：奖励类型、触发条件、发放对象、计算口径、发放资产。
  - 积分券资产：来源、用途、限制、提现/转赠/冻结/抵扣规则。
  - 业务流程：注册、购买、兑换、参团/排队、释放/补贴、核销、提现、复购等主链路。
  - 后台配置：比例、等级、配额、拨比、订单、券、钱包、资金池、审核、统计。
- 导图层级要克制：默认 3-4 层，最多 5 层；一级分支默认 5-8 个，每个分支保留最关键的 3-7 条。流程必须全部出现，但只画清流程骨架，不把字段、接口和实现细节塞进导图。
- 导图负责让客户快速看懂，需求文档负责详细说明；“流程全覆盖”不等于“每一步都展开成一大段文字”。
- 如果是在已有导图上补需求，优先把新增内容嵌入原有相关节点，不默认追加“本次新增需求”独立尾部板块。

## 资料读取与取材方式
- 读取优先级：
  - 用户当前明确补充
  - 用户指定文件
  - 同项目最新沟通记录
  - 同项目最新需求文档
  - 现有导图
  - 历史同类导图风格参考
- 如果用户给的是目录，先找同项目名或同业务模式相关的导图、需求文档、沟通记录。
- 读取 `.xmind` 时优先解析 `content.json`；旧格式再解析 `content.xml`。同名 PNG/JPG 只作为视觉辅助，不替代结构读取。
- 图片文字识别不完整时，不要硬编，放入待确认。
- 导图和需求文档不完全一致时，不要简单合并成重复节点；按最新、最明确材料整理，并把冲突写到 `待确认项`。
- 参考历史导图时，只学习结构风格和表达方式，不复制其他项目的具体比例、金额、身份名到当前项目。

## 用户历史导图风格
- 常见风格是“短标题 + 简短规则说明 + 子规则列表”，少用长段落。
- 模式电商导图常见一级分支不是固定三段式，而是围绕业务重点组织，例如：
  - `身份`
  - `推广奖励`
  - `奖励模式`
  - `分红奖励`
  - `业绩奖励`
  - `积分规则`
  - `业务流程`
  - `平台后台`
  - `用户端`
- 客户确认型导图优先用业务语言，不写技术实现细节。
- 功能型导图可以按 `平台后台 / 用户端 / 商家端 / 代理端` 拆，但模式电商规则型导图优先按 `身份 / 奖励 / 资产 / 流程 / 后台配置` 拆。
- 无现成导图时，先在内部形成稳定层级，再写入真实 `.xmind`；不要把 Markdown 当默认最终交付。

## 客户业务说明风格（强制）

- 先继承客户已改用的词和顺序。继续使用客户当前术语，不擅自换成历史文档、通用模板或技术实现中的近义词。
- 一级分支标题使用专业、稳定的项目表达，例如“项目定位与建设目标”“用户下单与配送流程”“平台后台与门店协同”“后续扩展规划”；不要把一级标题写成口语句，也不要堆“交易主链、业务闭环”等过大的词。
- 二级、三级节点使用客户看得懂的大白话，直接说明谁做什么、怎么做、得到什么；标题专业不等于正文复杂。
- 角色分支优先使用“角色关系”，直接列品牌方、用户、合作门店、总部/直营店、配送人员等身份和相互关系；只有客户明确采用“参与身份”时才沿用该名称。
- 一级分支先讲模式，不先讲页面。优先 `身份 / 奖励 / 积分资产 / 流程 / 平台后台`；功能仅放在对应业务分支下，不抢主线。
- 一个节点只说一件事，采用“谁做什么，得到什么，结果怎样”的短句。少用定义式、技术式、审计式长句。
- 每个条目优先回答“谁来用、要做什么、什么时候做、最后得到什么”；客户看不懂的技术词必须紧跟白话解释。
- 算法面向客户时，拆成中文业务步骤：先说明依据什么算、再说明结果如何产生、最后说明结果如何变化。不要显示变量名、等式或开发公式。
- 需要数字时必须说清计算基数、比例范围和结果归属，不写脱离上下文的百分比；同时给一个与客户口径一致的例子。
- 客户导图默认不展开接口、数据结构、审计、风控、合规等实现细节。客户没要求时，用业务结果或后台能力说明；内部评估版才展开技术实现细节。
- 客户主动删掉的分支，不默认加回。确有业务冲突时，嵌入最近规则节点，以 `客户需确认` 单节点提示。
- 新增规则只有来源明确时才写成定案；来自参考 PPT、历史模式或推断的内容必须标为 `参考`、`后台可配置` 或 `客户需确认`。

## 主干选择规则

### 1. 已有导图增量更新
- 先识别原导图的一级分支和节点命名。
- 先读取磁盘中最新保存的导图；客户手改版优先于旧 Markdown、旧导图和历史交付。若客户端可能仍有未保存修改，先提醒保存，再写回文件。
- 保留客户改过的名称、节点顺序和删减结果。不得因模板要求重新加回客户删掉的一级分支。
- 新增需求放进最贴近的原节点：
  - 术语解释放入 `名词解释`、已有 `核心概念` 或对应概念分支；若均不存在且客户未明确删除，新增 `名词解释` 分支。
  - 身份、等级、折扣、权限放入 `身份体系` 或 `身份`。
  - 奖励、拨比、分润、补贴、释放放入 `奖励机制`、`奖励模式` 或对应奖励分支。
  - 积分、券、钱包、贡献值、算力、福豆放入 `积分规则`、`积分券资产` 或对应资产分支。
  - 参团配额、排队、每日上限、参数放入参团/拼团/后台配置相关节点。
  - UI、文案、互动体验放入 `优化体验` 或前端体验节点。
- 保留原有文字和节点顺序，除非用户明确要求重构。
- 不要为了省事在末尾单独加 `本次新增需求调整`，除非用户明确要求保留新增清单。

### 2. 新建模式电商导图
- 不要机械套 `业务板块 / 用户身份 / 业务流程`。
- 优先根据材料选择 5-7 个最能说明模式的主干：
  - `名词解释`
  - `身份体系`
  - `业务模式`
  - `奖励机制`
  - `积分券资产`
  - `业务流程`
  - `后台管理`
  - `待确认项`
- 如果项目本身更像用户历史导图中的某类结构，可改用更贴近的分支名，例如 `身份 / 推荐奖励 / 分红奖励 / 积分规则 / 业务流程`。

### 3. 非模式电商导图
- 如果不是模式电商，仍可使用原通用三主线：
  - `名词解释`
  - `业务板块`
  - `用户身份`
  - `业务流程`
- 用户明确指定 `前台 / 后台`、`商家端 / 用户端 / 平台端`、`业务模块 / 数据流 / 角色分工` 时，按用户指定结构。

## 节点质量规则

### 1. 节点要带信息量
- 差：`代理商`
- 好：`代理商：平台设定的区域/层级代理角色，可按等级享受不同折扣价和区域奖励。`
- 差：`直推奖励`
- 好：`直推奖励：用户推荐下级完成指定订单后，推荐人按订单金额或让利金额获得对应比例奖励。`

### 2. 模式节点要写清闭环
- 消费类节点写清：谁下单、买什么、获得什么资产、是否产生奖励。
- 兑换类节点写清：用什么兑换、兑换成什么、能否转让、是否继续产生权益。
- 释放类节点写清：释放来源、释放条件、释放周期、释放资产、停止/重启条件。
- 出局类节点写清：出局条件、出局奖励、出局后资产状态、是否激活下一轮。
- 挂售/抢购类节点写清：资产来源、上架条件、成交方式、手续费、到账和限制。

### 3. 身份、等级、权益分开
- `身份` 是角色：会员、推广员、代理商、经销商、门店、合伙人、股东。
- `等级` 是档位：V1/V2/V3、省/市/区、普通/高级/顶级。
- `权益` 是可获得的折扣、奖励、分红、核销、配送、提现或后台权限。
- 同一身份只是等级或折扣不同，不拆成多个平级身份；放到身份下的等级节点。

### 4. 奖励机制要可核对
- 奖励节点尽量包含：触发条件、奖励对象、计算口径、发放资产、限制条件。
- 直推、间推、级差、平级、区域、分红、招商、核销、配送、助力、补贴、加速释放等，不要混在一句话里。
- 如果有拨比或成本测算，单独放 `拨比 / 成本测算`，避免比例散落后看不出总盘。
- 用户曾明确纠正过奖励不能缺失；模式电商导图中，奖励机制必须作为重点分支充分展开。

### 5. 积分券资产要讲来源和用途
- 每种资产说明来源、用途、能否提现、能否转赠、是否冻结、是否可抵扣、是否继续产生奖励。
- 常见资产包括积分、消费券、兑换券、购物券、权证、贡献值、算力、福豆、红包、零钱、余额。
- 现金订单、券单、积分订单、复购订单规则不同，要并列说明差异。

### 6. 代理商和经销商
- 经销商和代理商都应表达为：账户身份 + 身份等级 + 不同等级对应不同折扣价。
- 经销商/代理商下单如果不赠送积分或兑换积分，要明确写在身份节点下。
- 代理商如果同时有区域奖励职责，要区分 `下单折扣身份` 和 `区域/层级奖励角色`。
- 不同身份等级对应不同折扣时，写为等级规则，不要误写成奖励比例。

### 7. 参团/排队/配额
- 每日参团配额、按时间顺序放行、每用户每日上限、同用户多券拆分到多天，应放入参团、拼团、出局、排队或后台配置节点。
- 配额是平台控盘参数，应在后台配置中保留管理入口。
- 同一用户多券不应默认同日全部参团，除非需求明确允许。

### 8. 待确认内容处理
- 下列内容不要强行写进主干为已定方案：
  - 是否纳入本期不明确
  - 是系统内做还是线下做不明确
  - 是否接外部系统不明确
  - 奖励比例或拨比冲突
  - 资产能否提现/转赠/继续产生奖励不明确
  - 公司主体、区域归属、订单回滚规则不明确
- 统一放到 `待确认项`、`说明` 或 `后续规划`。

## 工作流
1. 读取源材料，先看用户指定文件，再看同项目需求文档/沟通记录/导图。
2. 判断这份导图用途：
   - 给客户看：偏业务语言、少技术词、强调模式逻辑。
   - 给内部评估看：偏模块边界、规则完整性、待确认项。
3. 判断是否模式电商：
   - 出现积分、券、奖励、代理、分红、补贴、排位、拼团、挂售、释放、滑落、出局等，默认按模式电商质量标准整理。
4. 识别现有导图风格：
   - 已有导图增量更新时，沿用客户最后保存的原结构、词汇和删减结果。
   - 新导图参考用户历史导图风格，但不复制其他项目内容。
5. 提取并合并候选条目，同时逐条登记源材料提到的业务流程：
   - 同类角色合并。
   - 同类流程合并。
   - 同类奖励归类。
   - 同类资产归类。
6. 检查模式电商关键分支是否缺失：
   - 名词解释
   - 身份等级
   - 奖励机制
   - 积分券资产
   - 业务流程
   - 后台配置
   - 待确认项
   - 对照源材料逐条检查全部业务流程，确认用户、后台、商家/服务方和异常处理流程没有遗漏。
7. 控制导图复杂度：默认 3-4 层，最多 5 层；一级分支默认 5-8 个，每个分支默认不超过 7 条。详细规则、字段、接口和异常说明放入需求文档。
8. 逐项检查计算基数、对象、结果归属和完整流程；客户版将复杂计算改为中文步骤与例子。
9. 在内存或临时 JSON 中形成完整层级，不把中间稿当交付物。
10. 选择 XMind 母版并生成真实 `.xmind` 文件。
11. 验证 ZIP 完整性、必需成员、根节点和一级分支；验证失败不得声称完成。
12. 返回 `.xmind` 文件绝对路径；只有用户明确要求时才额外输出 Markdown。

### ASCII 流程图要求
- 用户要求“ASCII 流程图”“完整流程图”或“流程图文档”时，先在同一项目目录生成 `项目名-ASCII流程图.txt`，再生成 Markdown 或真实 `.xmind`。
- ASCII 文件使用从上到下的流程图，不用功能树代替：逐步写出操作人、动作、判断条件、审核人、锁定或等待状态、下一步和结果。
- 多角色、多资产、多审核项目必须逐条覆盖注册归属、采购或下单、付款凭证、审核、资产流转、发货提货、通知、到期和失败处理；材料没有明确的结果标“待确认”。
- ASCII 流程图是流程核对稿；真实 `.xmind` 仍是默认最终思维导图文件。

## 强制质量阀门

生成前和交付前都必须执行。任一项不通过，不得把导图称为完成品。

### 1. 源材料覆盖检查

先在工作区列一张不交给客户的覆盖表：`源材料位置 | 提到的角色/流程/规则/页面 | 导图位置 | 已确认/待确认`。逐条登记，至少检查：

- 所有角色：用户、平台、商家/门店、服务人员、推广/合作方及材料中出现的其他身份。
- 所有流程：进入、下单、支付、履约、取消、退款、结算、审核、异常和人工处理；材料未提到的不要编造。
- 所有客户点名模块、页面、数据查看需求、外部系统和后续规划。
- 客户自造词、项目内简称和可能有多种理解的概念；导图一级必须有`名词解释`或`核心概念`，每个词写业务定义、材料依据和确认状态。不要把用户、门店、订单、支付、分成、配送、私域等通用业务词塞进去，除非材料给了该词不同于常规理解的专门规则。
- 所有数值、比例、门槛、时限和归属；不完整时写进 `待确认项`。

长会议、需求文档、功能清单或客户明确要求“详细导图”时，禁止只用“业务模式/用户端/后台”三层骨架代替覆盖表。每项必须能定位到导图中的具体分支；找不到位置即视为遗漏。

### 2. 复杂度分档

按源材料选档，不能为了通过检查故意降档：

| 情况 | 档位 | 最低要求 |
| --- | --- | --- |
| 简短单一规则，少于 3 个角色和 2 条流程 | `small` | 3 个一级分支、20 个主题、2 层深度 |
| 普通沟通或单模块需求 | `normal` | 5 个一级分支、50 个主题、3 层深度 |
| 长会议、多个角色/流程、已有需求文档或功能清单、客户要求细版 | `large` | 7 个一级分支、100 个主题、3 层深度 |

`large` 导图还必须独立呈现：名词解释/核心概念、业务目标/模式、角色关系/参与身份、主要业务流程、前台或用户操作、后台或服务方处理、数据/收益或规则、待确认和后续规划。材料没有某类内容时，写“材料未提及”，不能静默省掉。

### 3. 内容密度检查

- 一级分支不能只是空分类；每个关键分支至少有 3 个具体条目。
- 流程分支必须按先后顺序写“谁做什么 -> 判断什么 -> 得到什么”；不能只写“下单、支付、配送”三个名词。
- 页面或后台功能被客户点名时，写清使用者、操作和结果；不要只写模块名称。
- 不把所有细节塞进一个一级分支；角色、流程、规则、后台处理分别放到最接近的分支。
- 不确定规则必须放 `待确认项`，不能因缺少细节把整个流程删掉。

### 4. XMind 包和结构检查

生成后先做覆盖表复核，再运行对应档位的脚本检查；`large` 项目还要显式检查关键一级分支：

```bash
python3 scripts/validate_xmind.py /absolute/path/思维导图.xmind \
  --profile large \
  --require '名词解释' \
  --require '角色关系' \
  --require '业务流程' \
  --require '待确认项'
unzip -t /absolute/path/思维导图.xmind
```

分支名称可按客户术语调整；使用不同名称时，`--require` 必须改为实际名称。再核对：`content.json` 可被 `jq empty` 解析、根标题正确、每个一级分支在 XMind 中实际存在、主题/扩展资源在复用母版时仍存在。

### 5. 禁止交付条件

出现下列任一情况，回到整理阶段：

- 只验证 ZIP 能打开，没有核对源材料覆盖和主题数量。
- 长会议导图低于 `large` 档，或用户已指出“内容太少”。
- 客户点名的角色、流程、页面、规则、异常或后续规划没有对应条目。
- 用空概念代替具体动作，例如只写“订单管理”“配送处理”“分成体系”。
- 把不确定内容当成已确认事实，或为减少分支直接删除待确认流程。

## 真实 XMind 输出（默认且强制）

### 母版选择

按以下顺序选择样式来源：

1. 用户指定的 `.xmind`。
2. 同项目最新、已由客户修改保存的 `.xmind`。
3. `jy-design` 中业务类型接近、样式完整的 `.xmind`。
4. 没有合适母版时，使用生成器默认主题。

已有导图增量修改时保留原文件，默认生成带日期的新 `.xmind`；除非用户明确要求覆盖。母版含 `theme`、`extensions`、缩略图或其他资源时继续保留，避免生成无主题裸图。

### 生成器

先把最终导图层级写成 UTF-8 JSON。根节点使用 `title`，下级使用 `children`；子节点可写字符串或 `{ "title": "...", "children": [...] }`。

```json
{
  "title": "项目名",
  "children": [
    {
      "title": "身份体系",
      "children": [
        {
          "title": "代理商",
          "children": ["按等级享受不同商品折扣"]
        }
      ]
    },
    {
      "title": "待确认项",
      "children": ["代理退款规则待客户确认"]
    }
  ]
}
```

对 `content.json` 格式母版，使用技能自带脚本：

```bash
python3 scripts/build_xmind.py outline.json \
  --template /absolute/path/style-source.xmind \
  --output /absolute/path/思维导图-YYYYMMDD.xmind
```

无母版时省略 `--template`。脚本会保留母版主题资源、替换导图内容，并校验生成包。母版只有 `content.xml` 时不要强行套用 JSON 脚本；应结构化解析并更新 `content.xml`，保留原包其他成员后重新压缩。

### 验证

至少执行：

```bash
unzip -t /absolute/path/思维导图-YYYYMMDD.xmind
unzip -l /absolute/path/思维导图-YYYYMMDD.xmind
```

同时确认：

- 包内存在 `content.json + metadata.json + manifest.json`，或旧格式的 `content.xml + meta.xml + META-INF/manifest.xml`。
- 根节点标题与项目名一致。
- 预期一级分支全部存在。
- 复用母版时，主题、扩展和资源仍存在。
- 文件可被 ZIP 读取；不要仅检查扩展名。

## Markdown 例外

- 用户明确要求 Markdown 时才输出 `.md`。
- 其他归档 skill 明确要求 Markdown 备份时，可在 `.xmind` 旁额外生成同名 `.md`。
- 即使生成 Markdown，真实 `.xmind` 仍是本技能默认最终交付物。

## 质量标准
- 功能边界没有跑偏：仍然是需求思维导图整理，不是 PRD、报价或原型。
- 最终存在真实、可解压、结构有效的 `.xmind` 文件，不是改后缀的 Markdown。
- 生成后执行包完整性检查，并核对根节点与一级分支。
- 有合适母版时继承主题样式；已有客户导图增量修改时保留原文件。
- 导图第一眼能看出完整流程。
- 导图必须覆盖源材料提到的全部业务流程；每条流程写清谁来做、先做什么、什么时候判断、最后得到什么；不清楚的流程放入“待确认项”。
- 每条流程必须能顺着读懂：有明确负责人、具体动作、必要判断和结果；缺少关键信息就标为“待确认”，详细输入和处理规则放入需求文档。
- 导图不能堆成大段说明书；每条流程用短句表达，细节转到需求文档；超过 5 层或分支过多时必须合并同类内容。
- 节点不是空名词，关键节点都有一句业务解释。
- 必须有 `名词解释` 或 `核心概念` 分支；每个影响理解的术语都包含业务定义、根据哪份材料和是否已确认；无专用名词时明确写“暂无专用名词”。
- 成品不得出现内部工作词或只给术语不给解释；先写白话，再补必要的技术名称。
- 身份、等级、权益、折扣、奖励比例互相区分。
- 奖励机制充分展开，不漏掉直推、代理、区域、分红、释放、配额等关键规则。
- 积分券资产讲清来源、用途和限制。
- 后台配置能覆盖关键参数、比例、等级、配额、钱包、订单、券和审核。
- 已有导图增量更新时，新内容嵌入原结构，不集中堆到末尾。
- 客户手改导图后，术语、节点顺序、删减结果必须保留；新增内容只进入最近业务节点。
- 客户版读完应先看懂消费、奖励、积分如何循环；页面、接口、风控不应盖过业务主线。
- 所有比例必须写明计算基数、适用范围和结果归属，避免“总拨比”一类歧义表达。
- 复杂价值、发放、释放、销毁等规则先用中文步骤和客户例子说明；技术公式只在用户明确要内部版时保留。
- 不把其他项目案例的具体比例、门槛、身份名混入当前项目。
- 不把不确定内容写成已确认方案。

## 快速调用模板
- 项目名：
- 源材料路径：
- 是否已有导图增量更新：是 / 否
- 导图用途：客户沟通 / 内部评估
- 输出路径：`/absolute/path/思维导图-YYYYMMDD.xmind`
- XMind 母版：指定文件 / 同项目最新文件 / 同类母版 / 无
- 参考风格：指定导图 / 目录内同类导图 / 默认模式电商风格
- 重点模式：拼团 / 返券 / 补贴 / 挂售 / 排位 / 分销分红 / 积分商城 / 其他
- 是否保留待确认项：是 / 否
- 期望颗粒度：粗版 / 中版 / 细版
