# 小游戏玩法设计

设计产出必须能被测量或试玩验证。“丰富”“有挑战”这类词不算产出，要换成指标和目标范围。

## 0. 设计简报

动手前写 4 行：一句话承诺（玩家在做什么、感受是什么）、单局时长、核心循环（操作 → 反馈 → 奖励 → 加压 → 重开）、本轮不做的项。微信小游戏默认触屏单手、耐心短、单局几分钟。

只有品类名没有参考素材时（如“塔防”“合成”），先按 `references/genres.md` 展开成设计问题，再做第 1 节。

## 1. 参考拆解（有参考游戏、视频或截图时必做）

1. 视频先抽帧：`scripts/ref-frames.sh <视频> reference/frames 1`，得到逐秒帧 `f001.png …` 和分页总览图 `contact-1.png …`（每张 12 帧）。证据列写帧文件名。剔除非游戏画面（系统界面、录屏遮挡）。模型看不了图时用 `modlens`。
2. 写拆解，逐项对应帧号：
   - **核心动词**：玩家做什么操作，操作的即时结果。
   - **规则**：合法 / 非法操作、胜负条件、失败惩罚、计时。
   - **HUD 与外围**：顶栏、底栏、道具、货币入口。逐项标“demo 做 / demo 不做”。
   - **对标指标**：按 `references/benchmark.md` 填参考值与目标范围。
   - 每条分“观察”和“推断”两列：观察是帧里看得到的事实，推断是对本项目的结论。只给 3–7 条最关键的，不写长评。
3. 规则描述有歧义时（如“滑出”是整体平移还是沿轨迹移动），用帧做证据定下来，写进规则。

完成标准：每条规则和每个指标都有帧号证据，对标表的目标范围已填。

拆解时只保留机制与数值，表现层重新设计（见第 5 节）。

## 2. 关卡与生成器

- **可解性**写进生成器，不靠运气：优先“反向构造”（按拆除或求解的逆序放置），并同时输出官方解 `solution`。
- 固定 `seed`，同 seed 同关卡。
- 生成器输出对标指标，测试断言“回放官方解能通关”且“指标在目标范围”。写法见 `references/benchmark.md`。
- 难度只动少数几个受控变量（尺寸、数量、长度、转折、可走步数），每关的变量值写成表。前 1–2 关教学，之后在第 N 关达到参考水平；N 写进表里。
- 随机放置要加约束：先定“规律度”上限（如直线物体占比、相邻同向占比），避免生成结果比参考更整齐、更稀疏。

## 3. 数值

- 先抄参考的数值（命数、时限、道具价格），在对标表里标“来自参考”；没有参考的用整数起步，标“v0 待测”。每个值写单位。
- 每个数值写明它控制什么体验：命数控制试错空间，时限控制压力，提示价格控制卡关时长。
- 改数值只改数据表，不改代码。试玩调参时一次只改一个主参数，并保留一关“已知偏易”和一关“已知偏难”作基线。
- 难度靠收紧余量（速度、密度、反应窗口、资源）提高；不靠看不清的画面、输入延迟或隐藏信息。
- 有货币时写清来源、消耗、上限。核心循环还没验证好玩时，不加经济系统。

## 4. 触控交互与反馈

- 每个操作 100 ms 内要有可见反馈：合法操作立刻开始动画，非法操作抖动 + 音效位 + 扣命提示。
- 点击判定区不小于约 44 pt（手机上约 88 px @2x）。物体细于此时，扩大判定区或支持缩放。
- 动画进行中锁输入；动画时长 0.3–0.6 s，超过会显得拖沓。
- 失败原因要在画面上看得出：被谁挡住就高亮谁。
- 失败或胜利后一次点击就能重开或进下一关。
- 关键点击区离屏幕边缘留出距离，避开系统手势区。强反馈（震屏、粒子）只给高价值时刻。
- 开局 30 秒自检：玩家能否答出“能点什么、点了会怎样、什么危险、怎么重来”。答不出就用布局、动效或安全的首个目标来教，少用文字。

## 5. IP 安全转译

参考的是机制和节奏，不是外观：

- 名称、角色、Logo、配色方案、图标、文案、音乐、具体关卡和波次序列不照搬；关卡由自己的生成器产出。“换个名字的同款”也不行。
- 拿不准时，至少改动两项：题材幻想、视觉语言、系统表现、成长结构、内容语法、音频风格。
- HUD 布局可以沿用品类惯例（顶栏关卡号 + 命 + 计时），但图形重画。
- 拆解文档里写明“沿用的机制”和“重新设计的表现”两列。

## 汇报

汇报设计结果时给出：对标表（含当前值与达标情况）、规则清单、关卡变量表、本轮不做的项及原因。
