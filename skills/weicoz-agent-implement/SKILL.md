# 派给代理实现（weicoz-agent-implement）

你是派单方：写提示词、启动执行方、盯进度、验收产出。实现由执行方完成，你不替它写。

## 选哪个执行方

用户没指定就派 Codex。用户点名哪个就用哪个，点名了模型就换模型。

| 执行方 | 命令 | 默认模型 | 换模型 |
| --- | --- | --- | --- |
| Codex（默认） | `codex exec` | `~/.codex/config.toml` 的默认值 | `-m <模型>`，推理强度 `-c model_reasoning_effort=` |
| Kimi Code | `kimi -p` | `kimi-code/k3`（1M 上下文） | `-m <别名>`，别名见 `~/.kimi-code/config.toml` 的 `[models."…"]` |
| agy | `agy -p` | agy 自己的默认值 | `--model <编号>`，编号用 `agy models` 查；推理强度 `--effort` |
| dsh | `dsh headless` | 由 headless profile 决定 | 命令行没有模型参数，要换就改 profile 或加 `--patch` |

下文说“执行方”的地方对四个都适用；只写 Codex 的地方是 Codex 特有的。各自的启动和续跑命令在第三节。

参数是要实现的票据或规格的路径，可以带范围限定，例如“只做前端以外的开发”。没给路径时，从当前对话里已经确定的票据中取；确定不了再问。

## 一、先读 implement 技能

读 `~/.agents/skills/implement/SKILL.md`，以当时的原文为准。执行方会自己加载这个技能，你读它是为了知道该验收什么，以及提示词里哪些地方需要按项目规则改写。写这份文档时它的要求是：

1. 按规格或票据实现。
2. 在事先约定的接缝上用 `/tdd`。
3. 过程中勤跑类型检查和单个测试文件，完整测试套件只在最后跑一次。
4. 做完用 `/code-review` 审查。
5. 提交到当前分支。

原文变了就跟原文走，不要照抄上面这五条。

## 二、写提示词

提示词第一行必须点名 implement 技能并给出票据路径。implement 技能关闭了模型自动调用，不点名执行方就不会加载它。

Codex 用 `$` 点名：

```
$implement 实现票据 `<票据路径>`。
```

Kimi Code、agy、dsh 点名技能的写法各不相同，也没有逐个实测过，所以统一用读文件的方式，不依赖它们的技能语法：

```
先完整读取 `~/.agents/skills/implement/SKILL.md`，以及它要求用到的 tdd、code-review 技能文件，然后严格按 implement 技能实现票据 `<票据路径>`。
```

后面只补执行方从仓库里读不出来的东西：

- 规格、决策记录、术语表和项目约定文件的路径。
- 你在这次对话里已经查明、它重查要花很久的事实，例如已验证可行的接口和参数。
- 项目规则对技能默认做法的改写，写明这是规则而不是遗漏。常见的有：禁止调用哪些付费服务、哪些目录不能读或不能提交。
- 并行时预先分好的共享资源，例如迁移编号、端口。
- 汇报格式：逐条对照验收项给证据、列出改动文件、完整测试的真实结果、没做到和没验证的地方。

不要在提示词里复述 implement 技能的步骤，也不要替它规定实现方案。

### 提交

按 implement 技能原文，执行方做完后自己提交到当前分支。提交之后必须由你验证和审核，执行方提交不等于验收通过。提示词里写明提交的边界：

```
做完并且完整检查通过后，按技能要求提交到当前分支。只提交这张票自己的改动，提交信息遵守项目约定。
不要跳过提交钩子，钩子失败就修到通过。不要 push、不要部署、不要合并到别的分支。
不要为了让钩子跑得更快或更容易通过而改测试配置、构建配置或钩子本身，改了再恢复也不行。
会话记录只允许本地保存（如 `agit commit`），不要执行 `agit push` 或任何对外发布。
```

派单前复制进 worktree 的未提交文档（规格、票据、样本）不属于这张票的改动，在提示词里点名让它不要一起提交。

### 只做前端以外的开发

用户要求只做非前端部分时，在提示词里加这一段，把括号里的目录换成本仓库的实际前端目录：

```
范围限定：只做前端以外的开发。不创建、不修改前端源码目录（<前端目录>）里的任何文件，也不改前端构建产物。
票据里属于页面和交互的验收项留给派单方，在汇报里逐条列为“未做，属于前端”。
前端需要的接口、字段和错误码要在这次做完，并在汇报里写清楚请求与响应的形状，方便前端对接。
```

验收时用 `git status` 确认前端目录没有被改动。

## 三、启动

### 先看机器撑不撑得住

每次派单和每次续跑之前都检查一遍，不满足就不派，并把情况告诉用户：

```bash
uptime                               # 1 分钟负载
sysctl -n vm.swapusage               # 已用交换空间
df -h /System/Volumes/Data           # 磁盘可用
top -l 1 -o mem -n 5 -stats pid,command,mem   # 有没有单个进程占用异常
```

- 负载明显高于处理器核数时，等它降下来再派。
- 交换空间已经用了很多，或有单个进程内存占用异常大，先告诉用户，不硬跑。交换文件和数据盘共用空间，内存不够会连带把磁盘写满。
- 磁盘可用空间紧张时不并行；非常紧张时不跑完整测试。

运行期间的每次进度汇报带上这几项。


一张票一个新会话，票与票之间不共用上下文。

Codex（默认）：

```bash
timeout 3600 codex exec -C <工作目录> -s danger-full-access \
  -c approval_policy=never --json \
  -o <记录目录>/<票号>-r1.out - < <记录目录>/<票号>.md \
  > <记录目录>/<票号>-r1.jsonl 2> <记录目录>/<票号>-r1.err
```

Kimi Code（`kimi` 在交互式 shell 里是函数，脚本里用完整路径；没有指定工作目录的参数，先 `cd`）：

```bash
cd <工作目录> && timeout 3600 ~/.kimi-code/bin/kimi --auto -m kimi-code/k3 \
  --output-format stream-json -p "$(cat <记录目录>/<票号>.md)" \
  > <记录目录>/<票号>-r1.jsonl 2> <记录目录>/<票号>-r1.err
```

agy：

```bash
cd <工作目录> && timeout 3600 agy --dangerously-skip-permissions \
  --output-format stream-json -p "$(cat <记录目录>/<票号>.md)" \
  > <记录目录>/<票号>-r1.jsonl 2> <记录目录>/<票号>-r1.err
```

dsh：

```bash
cd <工作目录> && timeout 3600 dsh headless --json - < <记录目录>/<票号>.md \
  > <记录目录>/<票号>-r1.jsonl 2> <记录目录>/<票号>-r1.err
```

- 用后台方式运行，结束时你会被唤起；不要前台干等，也不要循环轮询。
- 模型按“选哪个执行方”一节的默认值，用户指定时再加对应参数。
- Codex 的 `danger-full-access`、Kimi 的 `--auto`、agy 的 `--dangerously-skip-permissions` 都是为了让它不停下来等批准、能联网装依赖和查资料。项目不允许时收紧：Codex 改用 `workspace-write`，Kimi 改用 `-y`，agy 加 `--sandbox`。
- 提示词、输出和日志放在会话的临时目录里，不放进仓库。
- 启动后一分钟内看一眼 jsonl：能看到会话编号、并且它确实读过 `implement/SKILL.md`，才算真的按技能在跑。记下会话编号（Codex 是 `thread_id`），续跑要用。
- Kimi Code、agy、dsh 的这几条命令取自各自的 `--help`，还没有在真实票据上跑通过。第一次用某个执行方时，先确认它的输出里有会话编号、文件确实写进了工作目录，再放手让它跑；命令和实际不符就以 `--help` 为准，并回来更正这份文档。

### 进度汇报

运行期间每 10 分钟向用户报一次进度：还在不在跑、已经写出了什么、有没有异常。完成一个阶段或一张票时不等到点，立即汇报。用后台定时唤起自己，不要前台睡眠。

### 新建 worktree 的环境

新 worktree 没有依赖环境，第一次提交往往因此白跑一轮：格式化工具找不到（前端依赖没装），或个别测试缺可选依赖。在提示词里让执行方动手前先把后端依赖（含测试用到的可选依赖组）和前端依赖按锁定版本装齐。

### 并行

有前后依赖的票顺序派。互不依赖的票可以同时派，但每张票用一个独立的 git worktree 和分支，同时运行的执行方会话（不分哪一家）合计不超过三个，多了容易把内存耗尽、拖垮整台机器。完整测试套件很吃内存和磁盘，任何时候只让一个会话在跑完整检查，在提示词里写明这一点；机器吃紧时改为顺序派。工作区里还没提交的规格、票据和样本要复制进 worktree，否则执行方读不到。

### 超时与卡住

单次上限一小时。到点没做完，在同一个会话里续跑，不新开会话重来，也不由你接手收尾：

```bash
cd <工作目录> && timeout 3600 codex exec resume <thread_id> \
  -c sandbox_mode='"danger-full-access"' -c approval_policy=never --json \
  -o <记录目录>/<票号>-r2.out - < <记录目录>/<票号>-r2.md \
  > <记录目录>/<票号>-r2.jsonl 2> <记录目录>/<票号>-r2.err
```

Codex 续跑没有 `-C` 和 `-s` 参数：工作目录靠先 `cd`，沙箱靠 `-c sandbox_mode=`。其他执行方的续跑，都先 `cd <工作目录>`，其余参数和首次启动相同：

- Kimi Code：加 `-S <会话编号>`。
- agy：加 `--conversation <会话编号>`。
- dsh：加 `--session-id <会话编号>`。

续跑指令里写明上一轮是被时限中断的、改动都还在、在此基础上继续，再补上这期间变了的情况。超时会留下它启动的测试进程，续跑前先停掉。

长时间几乎没有产出时（反复断线、没写出文件），停掉它新开会话，并把旧会话已得出的结论和已写的文件写进新提示词。

## 测试只跑该跑的

一张票从实现到合入，完整测试套件只跑一次。每多跑一遍都是实打实的时间，机器吃紧时会被放大很多倍。

- **先看项目的提交钩子是怎么设计的**（读钩子脚本和它调用的构建目标）。很多项目的钩子只跑“受这次改动影响的测试”，本来就是几分钟的事。不要往里塞会让它退回全量的参数；项目文档写了哪些参数会破坏这个机制，就照着避开。
- 这类“受影响测试”机制通常依赖一份本地的测试依赖记录（例如 pytest-testmon 的 `.testmondata`），而且记录和虚拟环境绑定。**新建的 worktree 有自己的虚拟环境，记录对不上，钩子会退回全量**，从主工作区复制记录过去也没用（实测 testmon 会报“环境里的包变了，全部重跑”）。两种应对：
  - 票是顺序派的：让执行方直接在主工作区的开发分支上做，钩子只跑受影响测试，也省掉合并这一步。前提是主工作区里没有别人未提交的改动会被钩子的格式化和构建波及。
  - 必须用 worktree（并行）：既然钩子反正要跑全量，就让钩子那一次充当这张票唯一的一次完整检查。执行方收尾时不再单独跑完整套件，只跑格式、类型检查和相关测试，然后提交；提交时只给钩子加并发，不加会改变测试选择的参数。
- **完整套件**：一张票只跑一次，就是 implement 技能要求的那一次，按上一条决定是执行方单独跑还是由钩子承担。提示词里写明并发数，按机器内存定：先看单个测试进程占多少内存，并发数乘上去不能超过空闲内存，否则会因为换页慢上好几倍。
- **你验收时不重跑完整套件**。读完整改动，跑这张票相关的测试文件，再跑一次受影响测试。只有一批票合并完、准备部署或发布前，才在合并结果上跑一次完整套件。
- 某条用例只在并行负载下失败、单独跑通过时，先怀疑内存或处理器争抢，不要整轮重跑碰运气。把证据记下来告诉用户，由用户决定怎么处理这条用例。

## 四、验收

执行方的汇报是线索，不是证据。你自己做完下面这些才算通过：

1. 读提交里的完整改动，逐条对照票据验收项。
2. 自己跑这张票相关的测试文件、类型检查和受影响测试，以你跑出的结果为准（完整套件见上一节）。
3. 确认技能要求的步骤确实发生了：有先于实现的测试，做过代码审查并处理了发现的问题。
4. 确认边界没被越过（从 jsonl 里查实际执行过的命令，不只看汇报）：没有推送、部署、对外发布和付费调用，提交只落在它自己的分支上、只含这张票的改动、没有跳过提交钩子；限定了范围时，范围外的文件没动。
5. 能真实跑通的路径做一次真实冒烟。

不通过就把具体问题发回同一个会话让它改，不要自己悄悄改掉。审核发现的问题让它在同一会话里修好并追加提交。通过后，并行的票由你把票据分支并回开发分支，再派下一张。

向用户汇报时说清楚：哪些验收项通过、证据是什么、哪些没做或没验证。
