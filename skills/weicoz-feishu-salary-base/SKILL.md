# weicoz-feishu-salary-base

把飞书多维表工资录入做成稳定流程。口径细节与实现坑见 [README.md](README.md)。

> 私有配置（Base token、table id）：`~/.config/weicoz-feishu-salary-base/config.yaml`，
> 结构见 [config.example.yaml](config.example.yaml)。见「第 0 步：读私有配置」。

核心目标：

1. 先读历史记录和字段结构
2. 再产出可核对草稿
3. 用户确认后才写入
4. 写完立即复核结果

不要跳过草稿确认。工资表是高风险数据，默认不能静默写入。

## 适用场景

用户要你：

- 访问飞书 Base 工资表
- 参考前几个月记录生成某个月工资
- 默认按全勤生成
- 指定某些人绩效，其余人清零
- 批量写入工资记录并复核
- 从税务 `.xls` 提取社保、个税并更新已有工资记录
- 把某个月工资结果按固定格式逐条发到飞书
- 用户明确说“发送给我自己”

## 前提检查

先确认本机有 `lark-cli` 且登录态可用：

```bash
which lark-cli
lark-cli auth status
lark-cli base --help
```

至少要有这些权限：

- `base:record:read`
- `base:record:create`
- `base:record:update`
- `base:table:read`
- `base:field:read`

如果 `user` token 过期但可刷新，继续用 `--as user` 真实读一次，通常会自动刷新。

## 第 0 步：读私有配置

**任何读写之前先读配置**。Base token、table id 只存在用户本机，不在本 skill 里。

```bash
CFG="${WEICOZ_SALARY_CONFIG:-$HOME/.config/weicoz-feishu-salary-base/config.yaml}"
[ -f "$CFG" ] || { echo "缺配置：$CFG（模板见 config.example.yaml）"; exit 1; }
sed -n '1,80p' "$CFG"
```

配置就绪后取两个键：

```bash
BASE=$(awk '/^base:/{f=1} f&&/token:/{print $2; exit}' "$CFG")
TABLE=$(awk '/^base:/{f=1} f&&/table:/{print $2; exit}' "$CFG")
```

注意：

- 没有配置文件时**不要猜 token，也不要从历史对话里翻**。用 `config.example.yaml` 让用户填好再继续。
- `base.token` / `base.table` 是密钥级信息：不要写进回复正文、示例、日志、提交信息或任何会外发的文本。
- `fields.writable` 列出的才可写；`fields.formula` 里的一律等飞书自己算。
- 配置缺失或字段对不上时先停下来问用户，不要退回「凭记忆的默认值」。

## 税务 `.xls` 更新社保和个税

用户发送类似 `YYYYMM_税款计算_工资薪金所得.xls` 的文件，并要求更新工资表时，执行本流程。

默认目标：

- Base token、Table ID：**从私有配置读**（见「第 0 步：读私有配置」）
- 匹配键：税款所属月份 + 姓名
- 只更新：`应缴社保`、`个税`

用户指定其他 Base 或表时，以用户指定值覆盖默认值。

### 0. 从微信财税群取得文件（用户没直接给附件时）

用户未直接提供附件、或说文件在微信财税群时，先按 `wx-cli` skill 的统一入口读本机微信：

```bash
bash ~/.agents/skills/wx-cli/scripts/wx.sh sessions --limit 2000 --json
bash ~/.agents/skills/wx-cli/scripts/wx.sh history '<确认的财税群名>' --since <目标月份次月第一天> --type file --json
```

- 从会话列表确认真实群名；结合文件消息的发送者、时间和前后文锁定目标公司的文件。申报通常在次月，不只查工资所属月。
- `wx attachments/extract` 当前只支持图片。文件消息给出精确文件名后，到本机微信 `xwechat_files/*/msg/file/` 下按文件名定位已下载原件；尚未下载时从微信客户端打开该条文件消息并保存，找不到就报告缺失。不拿其他公司的文件替代。
- 微信原件只读；不把工资、报税原文复制进技能仓库、普通索引或 Git。文件名月份只用于定位，最终以工作簿内税款所属期为准。

### 1. 提取税务数据

优先运行 skill 内置脚本：

```bash
python3 scripts/extract_tax_xls.py '<XLS_PATH>'
```

若系统 Python 没有 `xlrd`，使用已有虚拟环境或创建临时虚拟环境安装 `xlrd==1.2.0`。不要用 `openpyxl` 读取 `.xls`。

字段规则固定：

```text
应缴社保 = 本期基本养老保险费
         + 本期基本医疗保险费
         + 本期失业保险费
         + 本期住房公积金

个税 = 应补(退)税额
```

`应补(退)税额` 是工资表要扣除的个税。保留源值正负号，不用累计应纳税额、累计应扣缴税额或已缴税额替代。

月份必须从 `税款所属期起` / `税款所属期止` 读取，不只信文件名。整份文件存在多个所属月份时停止，要求用户确认。

### 2. 读取目标月份现有工资记录

读取字段和全表记录，筛出脚本返回的 `month`：

```bash
lark-cli base +field-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID>
lark-cli base +record-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID> --limit 200 --format json
```

必须同时保留 `record_id_list` 与 `data` 的同序关系，按 `时间 + 姓名` 找到每条记录 ID。不要按排序后数组下标猜 record ID。

### 3. 生成更新草稿

按姓名精确匹配，草稿至少列出：

- 姓名
- 原社保 -> 新社保
- 原个税 -> 新个税
- 当前绩效奖金
- 更新后预计实发薪资

源文件有、工资表没有的人列为“未匹配”，默认不新增工资记录。工资表有、源文件没有的人列为“缺少税务数据”，默认不改。禁止模糊匹配姓名。

仍遵守工资敏感数据确认规则：先给草稿，用户确认后写入。若用户在同条消息明确写了“直接更新”或“确认写入”，可视为已确认。

### 4. 只更新两个字段

每人值不同，按记录逐条调用：

```bash
lark-cli base +record-batch-update --as user \
  --base-token <BASE_TOKEN> \
  --table-id <TABLE_ID> \
  --json '{"record_id_list":["<RECORD_ID>"],"patch":{"应缴社保":<SOCIAL>,"个税":<TAX>}}'
```

更新必须串行执行。不要并行调用多个 `record-batch-update`，否则可能触发 `800004135: OpenAPIBatchUpdateRecords limited`。遇到该错误时，已成功记录不要重复猜测；重新读取目标月份，识别未更新记录，再串行补写。

禁止改动：

- `基本薪资`
- `应上天数`、`实上天数`、`请假小时`、`加班天数`
- `绩效奖金`、`补贴`
- `基本实发薪资`、`加班奖金`、`实发薪资` 等公式列

### 5. 写后复核

再次读取目标月份，逐人核对：

- 社保、个税与 `.xls` 提取结果完全一致
- 公式列 `实发薪资` 已刷新
- 记录条数不变
- 未匹配人员没有被自动新增
- 其他工资输入字段未被改动

最后报告成功条数、未匹配人员、社保合计、个税合计、实发薪资合计。

## 绩效奖金的来源

`绩效奖金` 这一列**不由本 skill 计算**。开发绩效由 `weicoz-feishu-receipt-base` 按月核算后写进来，
本 skill 负责读取、展示、发送，以及在你明确给了规则（例如「绩效都设 0，某人 500」）时覆盖。

两边都可能动这一列时，先确认这次是谁算的，避免互相覆盖。

## 默认工作流

### 1. 锁定目标月份

- 如果用户说“上个月”，必须换算成绝对月份，如 `202605`
- 当前写入文本主键通常用 `YYYYMM-姓名`
- 相对时间必须在回复里写成绝对值，避免错月

### 2. 读取字段结构

先读字段，确认哪些列是输入列，哪些列是公式列：

```bash
lark-cli base +field-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID>
```

重点确认：

- 可写输入列：`文本`、`时间`、`姓名`、`基本薪资`、`应缴社保`、`个税`、`应上天数`、`实上天数`、`请假小时`、`加班天数`、`绩效奖金`、`补贴`
- 公式列不要手写：如 `基本实发薪资`、`加班奖金`、`实发薪资`

如果某列是公式列，只写它依赖的输入列。

### 3. 读取历史记录

拉全表或至少近几个月记录：

```bash
lark-cli base +record-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID> --limit 200 --format json
```

然后判断：

- 最近完整月份是谁
- 当前在职人员是谁
- 哪些字段应复制最近月
- 哪些字段要按本次规则重置

默认经验：

- `基本薪资` 常沿用最近月
- `应缴社保`、`个税` 通常先沿用最近月，除非用户另给口径
- `绩效奖金`、`补贴`、`加班天数`、`请假小时` 常按本次规则覆盖

### 4. 确定“全勤”规则

默认全勤：

- `请假小时 = 0`
- `加班天数 = 0`，除非用户另给
- `实上天数 = 应上天数`

`应上天数` 默认先按该月普通工作日计算。若用户明确要求按法定节假日/公司考勤口径，以用户口径为准。

不要把“普通工作日”和“法定应出勤天数”混为一谈。若工资敏感，先给草稿，提示用户确认这个值。

### 5. 应用本次覆盖规则

常见覆盖：

- “绩效都为 0”
- “某个人绩效 = 500，其他人 0”
- “补贴全部清零”
- “只生成某几个人”

原则：只改用户明确指定项。不要自行猜测奖金。

### 6. 先给草稿，不立刻写表

草稿里至少列出：

- 姓名
- 时间
- 基本薪资
- 应缴社保
- 个税
- 应上天数
- 实上天数
- 请假小时
- 加班天数
- 绩效奖金
- 补贴
- 预计实发薪资

其中“预计实发薪资”只是本地按公式估算，最终以飞书公式列重算结果为准。

推荐本地估算公式：

```text
预计实发薪资 = 基本薪资 * 实上天数 / 应上天数 + 加班天数 * 20 + 绩效奖金 + 补贴 - 应缴社保 - 个税
```

如果表里真实公式不同，以表字段表达式为准。

### 7. 用户确认后再写入

写入前先查目标月份是否已存在，避免重复：

```bash
lark-cli base +record-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID> --limit 200 --format json --jq '.data.data[] | select(.[<时间列索引>] == "<YYYYMM>")'
```

若已存在：

- 默认先停下
- 问用户要“更新已有记录”还是“新增”

若不存在：

- 用 `+record-batch-create`

```bash
lark-cli base +record-batch-create --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID> --json '<PAYLOAD>'
```

## 写入形状注意事项

飞书字段值形状必须匹配。常见坑：

- 文本列：字符串
- 数字列：数字
- 单选/多选列：通常直接传字符串数组
- 用户/群组/关联列：通常要 `[{\"id\":\"...\"}]`

如果“姓名”字段是 select，不要传：

```json
{"name":"<姓名>"}
```

应传：

```json
["<姓名>"]
```

## 写入后复核

写完必须再次读取目标月份记录，确认：

- 条数正确
- 绩效覆盖正确
- 公式列已自动算出
- 没有多写重复记录

示例：

```bash
lark-cli base +record-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID> --limit 200 --format json --jq '.data.data[] | select(.[<时间列索引>] == "<YYYYMM>")'
```

## 输出格式

默认按下面顺序输出：

### Goal

一句话说明本次要生成哪个月、哪张表、什么规则。

### Verify

列出已经确认的事实：

- 登录态是否可用
- 目标月份
- 历史基线月份
- 全勤规则
- 是否存在重复记录

### Next

如果还没写：

- 给草稿
- 明确等用户确认

如果已经写：

- 报写入条数
- 报复核结果

如果已经发送：

- 报发送条数
- 报接收对象
- 报是否逐条发送

### Blocker

仅在真实阻塞时写，如：

- `lark-cli` 不存在
- 权限不足
- 目标月份已有记录但用户未说明是更新还是新增
- 用户未确认敏感工资草稿

## 最小决策规则

- 能直接从表里验证，就不要猜
- 能复用最近月，就不要做复杂平均
- 用户只改绩效，就只动绩效
- 用户只要求从税务 `.xls` 更新社保和个税，就只动这两个字段
- 公式列自动算，就不要手填结果列
- 写入前必查重复
- 写入后必复核
- 用户要求“发送给我自己”时，优先用 `lark-cli auth status` 里的 `userOpenId`

## 发送工资结果

当用户要求“把这个月工资结果发给我自己”或“每条记录发一次”时，按下面做。

### 1. 先读最终记录

只从表里读最终结果，不要用旧草稿：

```bash
lark-cli base +record-list --as user --base-token <BASE_TOKEN> --table-id <TABLE_ID> --limit 200 --format json
```

筛出目标月份后，取最终字段值。

### 2. 用固定模板整理

如果用户给了模板，严格按用户模板排。不要擅自改标题、顺序、标点。

示例模板：

```text
【<姓名>｜YYYYMM】
基本薪资 <数字>
应上天数 <数字>｜实上天数 <数字>｜请假小时 <数字>｜加班天数 <数字>
绩效奖金 <数字>｜补贴 <数字>
应缴社保 <数字>｜个税 <数字>
实发薪资 <数字>

请核对以上工资明细，确认无误请回复「确认」；如有疑问请及时沟通。
```

格式要求：

- 每人一条完整消息
- 金额优先保留两位小数
- 天数/小时保留表内最终值
- 不要输出 JSON
- 不要把换行写成字面量 `\\n`
- 必须发送真实换行文本

### 3. 确认接收对象

如果用户说“发给我自己”：

1. 运行：

```bash
lark-cli auth status
```

2. 读取 `userOpenId`
3. 用 `lark-cli im +messages-send --as user --user-id <OPEN_ID>` 发送

### 4. 逐条发送

如果用户说“每条记录发一次”，就每人单独一条消息，不要合并。

命令形态：

```bash
lark-cli im +messages-send --as user --user-id <OPEN_ID> --text $'【姓名｜YYYYMM】\n基本薪资 ...\n应上天数 ...'
```

重点：

- 在 shell 里优先用 `$'...'` 传真实换行
- 不要把文本写成包含反斜杠的 `\n`
- 不要默认用 bot 身份，优先 `--as user`

### 5. 发送后确认

至少确认：

- 成功条数
- 目标 chat/user 是否一致
- 是否按“每条一发”执行

## 示例触发

**例 1**

用户：`参考前几个月数据，给我生成上个月工资，默认全勤`

动作：

- 读字段
- 读近几个月
- 产出草稿
- 等确认

**例 2**

用户：`绩效都设 0，<姓名> 500，其他 0，直接写入`

动作：

- 在草稿基础上只改绩效
- 查目标月份是否已存在
- 批量写入
- 复核

**例 5**

用户：`[202606_税款计算_工资薪金所得.xls] 把对应社保和税务部分填充到工资表`

动作：

- 从税款所属期确定 `202606`
- 将四项个人社保相加，个税取 `应补(退)税额`
- 按 `202606 + 姓名` 匹配已有工资记录

## 不要做

- 不要跳过草稿确认就写工资
- 不要手填公式列
- 不要默认覆盖已有月份记录
- 不要把用户未指定的绩效、补贴、加班自行脑补
- 不要用累计税额字段替代 `应补(退)税额`
- 不要因 `.xls` 多出姓名而自动新增工资记录
- 不要并行更新不同人员记录
- 不要只返回“已写入”，必须复核
- 不要把换行文本发成字面量 `\n`
