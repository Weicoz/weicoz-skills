# 收款计划格式与执行约定

三个脚本分别负责只读快照、离线校验、微信预检。真正写入继续使用 lark-cli；本工具不创建后台任务或自动执行支付。
所有金额为数字或十进制字符串，精确到分；流水时间使用带时区的 ISO 时间，例如 `2026-01-01T10:00:00+00:00`。虚构样例见 `scripts/test_receipt_guard.py` 的 `fixture()`，真实样本不进源码。

## 计划根对象

| 键 | 内容 |
|---|---|
| schema_before | 开始准备本批计划时快照的 `schema` |
| schema_current | 临写本批前重新读取快照的 `schema` |
| projects | 本次会修改的项目预期最终状态；不放无关历史项目 |
| flows | 本批准备新增的流水；已写部分移出此列表，不能重放 |
| existing_flows | 这些项目的完整可读历史流水，来自最新快照；含未关联流水用于去重 |
| expected_income_total | 本批未写入收入凭证合计，扣除用户明确排除项；不减返点支出 |
| excluded_source_ids | 用户明确排除的来源唯一键列表 |
| id_map | 可选；创建响应返回的 `计划项目ID: 飞书真实记录ID` 映射 |

快照保留服务端字段 ID、名称、类型、公式及选项；列序由各页 `fields` 决定，记录 ID 由 `record_id_list` 决定。缺少 ID 时脚本停止，不能按行号猜 ID。快照不包含 Base token、表配置或私有分成比例。

对快照全量读取一次，再在本机按付款方/项目索引筛选。后续只有新证据、用户编辑或写入前刷新才再次读，避免针对每家公司各发一轮 API。

## projects 中的单个项目

```json
{
  "id": "local-demo",
  "business": ["示例业务甲"],
  "received_before": "0",
  "received": "100.10",
  "contract_total": "200",
  "contract_source": "contract:示例合同#金额条款",
  "receivable": "99.90",
  "channel_paid": "10",
  "channel_due": "20",
  "other_paid": "3",
  "other_due": "4",
  "net": "63.10"
}
```

- `id` 使用已有记录 ID，或本批唯一临时 ID；新建成功后从响应取得真实 ID 写进 `id_map`。流水关联以该映射为准，不能按同名项目推断。
- `business` 使用项目表当前负责人，统一为姓名字符串列表。空负责人不能靠聊天对接人推断；用户修改项目负责人后须重新取快照，重新检查所有相关流水。
- `received_before` 用修改前累计已收，新项目为 0；本次新增收入之和加此值等于 `received`。若要更正旧账，先单独取得明确的更正依据与授权，不用改基线伪造对平。
- 四个 paid/due 值及 `received` 必须是确认数值；不能把历史空白自动补成 0。待付转已付时总应付不变，`net` 不变，且必须有相同项目的真实支出流水。
- 已付与 `existing_flows + flows` 中的该项目支出核对：`返点渠道` 对应 channel_paid，`转款莞云` 对应 other_paid。欠款不是已付，不创建支出流水。
- 合同总额已知时，`contract_source` 以 `contract:` 或 `user:` 开头，引用相对文件、条款或具体确认记录；银行到账不能自动当合同总额来源。
- 总额未知用 `contract_total: null, receivable: null`。当前待收公式若不保护空总额，先只记未关联流水，不创建这个项目。经用户授权调整空值保护后，目标公式可用：

```text
IF(ISBLANK([收款总额/项目金额]),"",[收款总额/项目金额]-[已收款项])
```

脚本不会改公式。其他等价写法先核对并扩充有证据的支持，不让大模型自行把公式判为等价放行。

## flows 中的单笔流水

```json
{
  "source_id": "bank:example.pdf#page1-row1",
  "project_id": "local-demo",
  "business": ["示例业务甲"],
  "date": "2026-01-01T10:00:00+00:00",
  "counterparty": "示例客户",
  "amount": "100.10",
  "type": "款项入账"
}
```

- 只支持 `款项入账`（正数）、`返点渠道`/`转款莞云`（负数）。其他分类由对应业务流程处理，不强行改名适配校验器。
- `source_id` 是稳定的凭证定位键，不是每次运行重建的随机数。既按来源键排重，也独立按时间、对象、金额、分类排重；不同对象同金额不算重复。
- 时间精确到凭证实际提供的秒并保留时区。如果只有日期或发送截图时间，单独记录证据精度与用户确认，明确时间语义后再生成计划；不能补一个看似精确的付款时间。
- 暂未匹配项目时 `project_id: null`。这种款项已到账但未归属，不能当已确认的项目绩效。
- 已关联项目的流水 `business` 必须与项目一致；公式结果的“示例业务甲、示例业务乙”与姓名列表按相同集合核对。该值是回读预期；若真实字段为公式，不把它作为普通单元格写入。单选手填列先核选项存在，不能因无选项就静默漏填。
- 快照的 `project_ids` 保留完整关联；多个项目会被 `--audit` 明确报告，不能当作未关联跳过。无项目的手填业务保持原值。
- 原件页码、消息 ID、付款截图和确认记录另留私有回执；本校验格式不需要把完整账号、聊天或口令送进模型。

## 执行

1. 只读快照 → 在本机生成计划，引用凭证合计和确认依据。
2. 临写前重新取快照，刷新 `schema_current`、`existing_flows`，运行 `receipt_guard.py PLAN`。字段变化则重新准备计划，不能把两份快照都改成新版本绕过语义核对。
3. 向用户展示具体字段及影响；已获同范围确认后，按 `lark-write.md` 执行本批批量写入，不重复问。
4. 保存每次响应和已创建 ID；错误或超时先查询，确定哪些生效后只续办未完成部分。只读限流可有限重试，写操作不自动重试。
5. `lark_snapshot.py` 取得写后快照，运行 `receipt_guard.py PLAN --after AFTER`。后快照金额、项目映射和流水交易指纹必须匹配，不能用先前计划冒充回读。

校验器不会证明凭证真实、合同正确或所有历史旧账都完整；只对输入的本批计划和来源范围作确定性检查。真实写入验收仍以服务端回读、原件和用户确认共同判定。
