# 可恢复的游戏模型与串流A/B测试操作规程

## 1. 范围与能力

先声明本次做计划还是执行。用户说“先告诉我、别开始”时只给流程。保存Skill不授权实测。已有明确测试授权则继续范围内工作，不每步重复确认。

不能把SSH可读等同于能控制游戏、能抓帧或能看到客户端。执行前验证主机控制、采集工具、画面可见性、客户端统计和恢复途径。有内置基准优先使用；无法可靠操作游戏时由用户走固定路线，Agent切换配置和收集数据。登录、验证码、账号授权由用户接手。

明确游戏、实际EXE、存档/场景、串流客户端、网络方式、分辨率/刷新率、可接受画质和目标真实帧。测试占用机器且临时修改配置；列出修改项及恢复点。缺工具先查已有能力，确需安装时说明具体组件与作用，按授权处理。

## 2. 备份与记录

记录日期、OS、CPU/GPU/显存/RAM、驱动和App版本、游戏版本/补丁、实际启动EXE和Profile；保留完整路径映射供本地使用。DLL分别记录名称、版本、路径，必要时校验哈希。应用默认模型可能已经由用户换过DLL，取消驱动覆盖并不恢复原装文件。

备份游戏相关设置文件和能可靠导出的驱动Profile，记录SR覆盖开关/模型/模式/比例、RR/FG、NIS锐化、限帧、电源、同步、Reflex、HDR。记录串流编码器、码率、输出与客户端刷新率、网络拓扑。原本缺失的键恢复为缺失，不能简单写0冒充恢复。导出范围若包含私人配置只留本地。

优先只改游戏Profile，避免影响桌面/其他应用。第一轮不升级驱动、不替换DLL、不加模组、不更换编码器。备份要能读回，恢复路径不能依赖正在被修改的唯一远程链路。

## 3. 场景与存档

使用可重复的内置基准，或同一存档同一路线的60–120秒片段。至少覆盖一个典型场景和一个实际战斗/城市场景；基准没有暴露的火焰、粒子和CPU负载必须另验。

确认自动保存行为，不推进关键剧情、消耗稀缺道具或覆盖用户原存档。必要时先备份并使用可恢复存档。无法保证时换安全场景，不擅自游玩推进。

固定视角、路线、时间/天气、游戏画质和输入模式。暖机及着色器编译完成后采样；首次冷跑单独记录，不混进稳定模型比较。保持后台任务、录屏和监控开销一致。

## 4. 验证真实模型

保存设置后重新启动游戏。检查启动EXE与Profile绑定；相同游戏的官方配置、自定义路径配置和启动器可能不一致。必要时只读查看进程实际加载的模块。

使用当前NVIDIA App提供的DLSS统计信息（历史入口Alt+Z→统计信息→统计视图→DLSS），检查SR覆盖活动、模型与模式。Off/Inactive/N/A不能判成已生效。确认不了就标该组“模型未确认”，不得据此宣称某模型更快。回读DRS只证明保存值。

## 5. 试验顺序

先用一款存在明确M/L覆盖且可重复的游戏建立流程。

| 组 | 改动 | 其他条件 |
|---|---|---|
| A | 当前模型 | 作为原始基线 |
| B | K覆盖 | 输入模式/分辨率、NIS、同步等保持一致 |
| C | 取消模型覆盖 | 使用当前游戏安装的默认实现，不称“出厂原版” |
| D，可选 | M覆盖 | 前三组结果值得进一步研究才执行 |

用户明确指定L/K比较时，建立明确的L、K两组；只有运行态确认当前为L时，A才兼作L组。其他指定模型组合采用同样原则，不擅自扩大默认范围。

顺序不是固定性能排名。每组预热后采集60–120秒三次；这属于实验设计，不是厂商要求。对比交错排序或末尾补跑A，排除温度、缓存与后台变化。游戏崩溃、严重画面异常、无法确认生效或持续热降频时停止该组，记录并回退。

先同模式K/M/L比较推理成本，再比较K＋质量/平衡与M＋性能的整体画质/帧率取舍。不要在同一轮同时改模型与模式。DSR倍率为像素量，不是长宽倍数；单列输入尺寸、逻辑输出、捕获输出与客户端物理屏幕尺寸。

## 6. 性能余量与日常串流分两轮

有FPS上限时可能所有组都碰顶。先备份并识别游戏/驱动/第三方限帧，短时移除相关上限以测成本；不要只改一个而遗漏另一个。日常轮恢复一致目标，确认主机与客户端的60、59.94等时基。不要无条件套“刷新率减3”。

串流保持同一编码器、码率、网络及客户端模式。编码前GPU资源争用、网络丢包和客户端解码必须分开。NVENC有专门硬件不等于捕获/复制/编码准备完全免费。

NIS/锐化先固定完成模型对比，随后用选中模型做NIS开关试验。缓存开关不证明发生双重缩放。只关额外锐化、不改模式与码率，才能判断哪一层改变画面。DSR/DLDSR和电源方案也是后续独立实验。

## 7. 采集与定义

| 数据 | 要求 |
|---|---|
| 平均FPS、1% Low | 同一工具、同一版本、同一统计定义；不要跨工具直接拼表 |
| 帧时间曲线和长帧 | 同一时长/路线，说明阈值与加载段是否排除 |
| GPU Busy、利用率、频率、温度、功耗 | 解释资源成本与热/功耗限制；不能只靠一个占用率判瓶颈 |
| 显存/RAM | 记录工具口径；分配、驻留、预算和标称容量有别 |
| 编码/网络/解码、丢帧和队列 | 从实际客户端采样；注明每项定义，不把局部延迟之和当精确端到端值 |
| 截图/动态片段 | 同位置、同路线；相同录制负载，注明压缩，保留参考帧 |
| 手感 | 用户在实际客户端反馈；截图不能证明响应，主机统计不能代替客户端体验 |

工具优先复用现有PresentMon/CapFrameX/FrameView或等效能力。按工具文档选择采集目标进程，区分Presented/Displayed/FG。没有硬件或可靠高速摄影测量时，不报告按键到屏幕的绝对延迟。

静态对比看纹理、字边与细线；动态看植被/毛发闪烁、移动拖影、遮挡边界、粒子、HUD及快速转向。只看480p视频或单张截图不评定微小4K差异。不要把主机录屏当串流端截图。

## 8. 结果判定

写每组三次数据与波动范围，以中位数等一致方法总结。不预设提升百分比门槛；差异落在噪声内就写“没有可靠差异”。优先稳定基础帧与可接受动态画质，不能仅以平均FPS选赢家。

K快且画质可接受则推荐K；M/L在目标帧下有可见收益则保留；默认实现更好就取消覆盖。主机稳定而客户端卡顿先处理串流；CPU/编译/存储瓶颈不继续盲降输入分辨率。

FG是另一项测试：先验证生成帧进入捕获/编码/客户端链路，再比较基础FPS、显示帧与输入响应。不把主机LSFG加入未验证的常用串流方案，也不把某版本失败泛化到所有原生FG。

## 9. 恢复与交付

没有明确保留授权时，测试后恢复原Profile、原限帧、NIS、同步及游戏设置，回读确认。中断或失败也执行恢复；无法恢复时明确列出剩余差异和所需动作，不声称完成。

交付逐游戏结果表、原始CSV/JSON、版本与配置清单、图像样本、运行态证据和恢复记录。记录“未验证”项及最小确认动作。测试耗时按现场估计，45–90分钟只可作首款安排示例，不保证。

新驱动、游戏补丁、DLL或客户端变化后，旧最佳配置只作起点，做小范围回归再沿用。
