# 玩法讲解稿

## 这份稿子是什么

读者是**用户本人**。用户拿着它给产品和开发讲，讲完对方要能：
1. 复述玩法闭环，推演一笔订单的钱怎么分；
2. 说出自己要做的工作；
3. 知道哪些规则还在等客户拍板、先按什么做。

所以它不是规则书、不是 PRD、不给客户看。好坏标准是“讲起来顺、听的人能复算”，不是“完整”。

## 出错后果与提问闭环（强制）

> **出错后果**：产品和开发按讲解稿开工。讲解稿写错会导致返工，并传导到客户交付；影响很大，会失去客户对我们的信任，所以不得出错。任何不确定点都必须问用户，不得用通用模式补规则、不得自己定“建议默认值”了事。

- 提问按 `weicoz-jy-design-demand-archive` 第 4 节「提问闭环」执行：先汇总所有问题，用宿主提问工具一次问完；每题首项是我方建议并标“(推荐)”，至少 5 个可选项（工具上限 4 个时加工具自带的 Other）；回答与之前前提冲突时以用户为准；多轮迭代到全部定值。单独调用本 skill 时同样执行。
- 只有用户回答“需和客户确认”的项可以留在稿子里，进模板「仍需客户拍板的点」，标明我方建议值和影响。
- 讲解稿是内部稿，不跑客户版禁词门禁。

## 与其他 Skill 的关系

- 本 skill 只读已有材料并输出讲解稿；不改沟通记录、功能清单、导图等既有产物。
- 项目落盘路径与命名以 `weicoz-jy-design-demand-archive` 为准；没有该约定时，存到客户项目目录，命名 `<项目名>-讲解稿-<YYYYMMDD>.md`。
- 若项目目录有 `AGENTS.md`、玩法知识库或交付规范，先读与本轮相关的段落，按其引用格式标注来源。
- 材料只有原始转写、还没有沟通记录或参数表时：先告诉用户缺定案依据，把规则理解和冲突点全部并入提问闭环问清，再写稿。

## 流程

1. **盘点材料**：列出项目目录文件和大小。优先读定案类材料（沟通记录 / 已确认参数表 / 定案表），再读功能清单，最后读客户方案原文。会议转写通常很大，只按关键词（核心术语、数字、“第几个”“确认收货”“退款”等）截取需要核对的段落，不整篇读入。
2. **定版本口径**：找出“会议 vs 文档”的差异和定案记录。采用哪一版要在稿子开头写一句。文件修改时间或“正式版”标题不能单独定案。
3. **找最难讲的那条规则**：通常是本项目区别于常规系统的定制点（例：按点位而非身份分佣）。回到转写原文核对客户原话，确认理解无误，它要用最多篇幅和例子讲。
4. **列未定点并问清**：逐条问自己“开发写代码时会在这里卡住吗？”。会卡住且材料没答案的，就是未定点。常见来源：复购是否同样计奖、资格未达标时奖励去向、计数从何时开始、团队层级范围、多级重复计提导致总拨出超预算、同一身份的两种叫法。第 2、3 步发现的版本差异、理解存疑也并入。不得用熟悉的通用模式补出客户没说的规则。全部汇总后按提问闭环一次问完，多轮迭代到全部定值。
5. **写稿**：按 `references/template.md` 的结构写；已确认的取值按定案写，不再标“建议”。
6. **自检**：
   - 每个算例手算一遍，档位边界（如 9.5 万落哪档）对照表格；
   - 结尾检查题的答案与正文一致；
   - 每条重要规则带来源（`文件章节` 或 `转写时间戳`）；
   - 稿子里没有用户能定、却没问的点；剩下的只有“需和客户确认”的项，每条给了“影响”和我方建议值，建议值明确标为建议、不冒充定案。

## 写法要点

- **先给一张总表**：几笔钱、各多少、给谁、什么时候算。再给一段可以照念的开场白。
- **规则用例子讲**：画一棵 A→B→C 的推荐树，用整数金额（如每单 2000 元）逐行算给谁多少。抽象公式放在例子前一句即可。
- **核心定制点配口诀**：一句话能记住的版本，方便现场复述。
- **流程用 ASCII 图**：身份阶梯、结算状态这类有先后的内容画出来，比段落好讲。
- **点明“和常规做法不同”的地方**：开发最容易按惯性实现错的就是这里。
- **分工按角色拆**：产品列待办；开发按模块列“关键工作 + 难点”，并与功能清单条目数对上。
- **范围外但要知道的事**单列一行（如支付对接、上线节奏、负责人和工期），避免被问到时答不上。
- 保留客户原称呼；口语转写里的同音错字（如“建推”= 间推）按上下文纠正，不照抄。
- 篇幅以“讲 20–30 分钟”为度。细节已在功能清单里的，引用条目，不重抄。

## 交付

- 写入文件后，回复里给出完整路径，概括稿子结构，并点出仍需客户拍板的点（没有就写“无”）。
- 说明哪些已核对（来源、算例），哪些未核对。不提交 Git，除非用户要求。
