# 规则说明

## 这份文档是什么

读者是**客户本人及其业务负责人**。客户拿它逐条核对，用笔标“对/不对”，签完回传即成为开发依据。

所以它读起来像**合同附件**，不像文章：每条一句规则，能独立成立，不依赖上下文，不出现“我来讲”“这里要注意”。

完成检查：客户只看这一段，能说出“谁在什么条件下做什么、得到什么、钱从哪来、什么情况停”。完成前必须过对抗式审查，客户版产物不走审查不算交付。

## 和相邻产物的分工

| 产物 | 读者 | 语气 | 用哪个 skill |
|:---|:---|:---|:---|
| 规则说明 | 客户，核对签字 | 条款陈述 | 本 skill |
| 需求分析报告 | 自己，判断能不能接 | 判断、风险、工作量 | `weicoz-jy-design-demand-archive` |
| 功能清单 | 客户，核对范围 | 表格条目 | `weicoz-custom-feature-checklist` |
| 思维导图 | 客户，快速看懂 | 短句层级 | `weicoz-demand-mindmap-organizer` |

同一项目的多份产物共享同一份业务基线，数值必须一致；改一处要同步其余。

## 三条硬规则

1. **一条规则只写一次**。同一口径散在三节里，客户改了第一节、漏了第二节。
2. **数字必须可复算**。每个比例、金额、档位配一个算例，算例用脚本核过再落笔，禁止心算。
3. **来源不写进正文，但要能指出来**。正文是客户看的，出处留在沟通记录；写作时每条规则心里要能对上原文哪一句或哪次答复。
4. **算例按当前口径重算，不抄源材料**。客户 PPT、旧文档里的算例可能用了已废弃的档位或比例，照抄会把错数字带进客户版。每个算例都从已确认参数表重新算一遍。

## 不进客户版的东西

客户版正文第一行是标题，下一行直接进业务，中间不隔任何说明。

- 版本号、用途、范围、用法、免责、签字区、确认栏，一律不写。日期可以写，放在标题下方一行即可。版本与出处留在沟通记录。
- 不设「确认」「调整意见」这类表格列。客户用笔在行上标对或不对，不靠我们预留栏位。
- 不写介绍自己的话：「本说明用于…」「以下规则请确认」「如有异议请批注」。

## 客户版措辞

- 陈述句，主语在前：`用户完成实名后才能下单`，不写 `系统应校验实名`。
- 一条一句，条件在前动作在后：`未签署授权书时，不得下单、不得签到`。
- 数字带单位与基数：`套餐总价的 20%`，不写 `20%`。
- 同一概念全文一个词，先用客户的原词，再在名词解释里下定义。
- 客户看不出结论的，加一句算例，不加形容词。

以下四类词不进客户版：`待确认`、`待定`、`暂定`、`参考`，以及任何“另行公布”“后续再定”式的推脱。原文没写死的口径，按我方理解写成定值，客户核对时自然改。

## 结构骨架

按项目裁，没有对应机制的小节直接去掉，不留空标题。

```markdown
# <项目名> 规则说明

日期、依据（列出读过的材料）、口径顺序（多份材料打架时谁优先）、用途一句话

## 一、这套系统做什么
   四到五件事的清单；明确的禁止项

## 二、参与角色
   角色图（ASCII）+ 角色表：角色 / 怎么获得 / 享受什么
   体系隔离规则（如果有多套互不读取的体系）
   交易资格（实名、授权、冻结等准入条件）

## 三、账户与资产
   前端可见 / 后台可见
   资产表：资产 / 面值 / 来源 / 用途
   资金硬约束

## 四、核心机制（每个机制一节）
   记分或触发表 → 结算流程（ASCII）→ 边界 → 算例
   有先后关系的画 ASCII，能列成表的用表

## 五、其他机制
   每种一节：规则一句话 + 分档表 + 一个算例 + 例外

## 六、财务口径
   比例表、金额底表、科目隔离、超限处置
   每个数字自己复算过

## 七、系统范围
   本期开发 / 本期不开发（不开发那列必须写替代方式）

## 名词解释（按项目需要）
```

## 执行流程

1. **找基线**。读同项目的沟通记录「已确认参数表」；没有就先按 `weicoz-jy-design-demand-archive` 落盘建基线，不凭印象写。
2. **定产物名**。`<项目名>-规则说明-<YYYYMMDD>.md`，放项目目录；项目目录与命名以归档 skill 为准。产物名、标题和正文统一用「规则说明」，产物名与标题里不出现「玩法」。
3. **写初稿**。照骨架填；每写一个比例或金额，立刻在旁边写算例并跑脚本核一遍。
4. **自检**。逐条走下面的检查表。
5. **过门禁**。跑归档 skill 的客户版门禁，带 `--consistency`；失败就回去改，不靠换词绕过。
6. **过对抗审查（强制）**。按归档 skill 第 7 节派子代理，一组一个范围，只读不改；结论逐条回原文核实，成立就改、误报留理由，改完重跑门禁，直到采倒数归零才交。

## 自检清单

- [ ] 全文没有一个“我来讲”“这里注意”“建议”。
- [ ] 同一口径只出现在一处；出现两次的，删掉一处改成引用。
- [ ] 每个比例和金额都有一个算例，且算例复算通过。
- [ ] 每个“不做什么”都写了替代方式。
- [ ] 角色表里每个角色都能回答：怎么获得、享受什么。
- [ ] 有先后关系的流程画了 ASCII，且每一步都写了“谁做什么→判断什么→得到什么”。
- [ ] 原文互相打架的地方，选了哪一份、为什么，写在开头的口径顺序里。
- [ ] 客户版禁词零命中，`--consistency` 通过。
- [ ] 和其他产物（导图、功能清单、报告）的同一数值逐项对过。
- [ ] 正文第一行标题后直接进业务，没有版本、用途、范围、用法、签字区。
- [ ] 没有「确认」「调整意见」列，也没有留给客户填写的空栏。
- [ ] 范围只含本次定案的模块；同一客户的其他期次不并进来。
- [ ] 每个算例都按当前参数表重算过，不是从客户材料里抄的。
- [ ] 已按归档 skill 第 7 节走完对抗式审查：三组并行、子代理只读、结论逐条回原文核对；采倒数归零，或只剩已写明理由的误报。
- [ ] 无子代理可用时，汇报里注明「未走独立审查」，不得把自审写成对抗审查。

## 失败分支

| 情况 | 处理 |
|:---|:---|
| 材料里同一规则有两种写法 | 按效力顺序选一个写进正文，把取舍写进开头的口径顺序；不写“两种都可以” |
| 客户原话只有结果、没有计算方式 | 不补公式，把已知的触发条件和结果写清楚，缺的算法在沟通记录里留问题 |
| 数字算例凑不上 | 说明数字本身有问题，回到沟通记录核对，不在正文里圆场 |
| 客户要求不加名词解释与范围节 | 按客户要求删，其余照旧 |
| 源材料算例与已确认口径不一致 | 按已确认口径重算，正文只放重算结果；差异写进沟通记录，不在正文解释 |
| 同一客户有多个已定项目 | 分开各出一份；客户版只写本次范围，不合并 |
