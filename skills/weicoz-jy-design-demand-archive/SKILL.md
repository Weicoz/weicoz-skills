# JY Design Demand Archive

## 功能边界
- 本 skill 负责把原始需求材料保存到 `jy-design`，并顺手产出匹配的交付物。
- 交付物可以是：沟通记录、功能清单、ASCII 导图、ASCII 功能清单、思维导图 Markdown、需求文档初稿、项目报价与第三方服务费用文档。
- 只要交付物里包含 `需求文档`，正文就必须带至少一段 ASCII 业务流程图。
- 报价、排期、服务器、第三方服务价格仅在用户明确要求时处理；此时必须调用 `weicoz-project-quote-estimator`，不在本 skill 内重复报价规则。
- 如果导图整理本身已超出本 skill 边界，优先调用 `weicoz-demand-mindmap-organizer`，不要重复发明导图规则。
- 「提问闭环与定案参数表（强制）」覆盖本 skill 全部交付物：沟通记录、需求文档、功能清单、思维导图、ASCII 版、Excel 版、报价文档；不只作用于导图。

## 适用场景
- 用户说“把这段沟通记录保存到 jy-design”。
- 用户说“根据这份内容出一份导图 / 思维导图 / ASCII 树状图”。
- 用户给一段会议纪要、语音转写、聊天记录，希望沉淀到 `jy-design` 项目目录。
- 用户要“先存档，再整理成客户可读材料”。

## 默认目标
- 优先保留原始材料，不丢原话；会议转写、聊天记录、客户原话必须完整落盘，不能只保存摘录、总结或整理版。
- 优先复用已有项目目录，不乱建新目录。
- 对于“会议纪要 / 语音转写 / 客户沟通 -> 再整理需求材料”的场景，默认同目录沉淀完整链路：`沟通记录` + `原始会议转写` + `需求文档` + `思维导图`。
- 不要把整理后的 `需求文档`、`思维导图` 落到别的工作仓库再回头搬运；如果用户点名 `jy-design`，这些产物默认就属于 `jy-design` 项目目录。
- 优先给出最小可交付物：`沟通记录` + `原始会议转写`；若用户已经要求“整理”“出导图”“出需求文档”，则继续在同目录补齐对应文件。
- 把不明确内容单独收口到 `待确认项`，不要脑补成已定方案。

## 目录与命名规则

### 项目目录
- 默认根目录：`$WEICOZ_JY_DESIGN_ROOT`
- 若用户已给项目名，直接落到对应目录。
- 若目录已存在，优先复用。
- 若是新建项目目录，目录名**日期在前、项目名在后**：`YYYYMMDD-项目名`
- 目录名与文件名定序方向相反，不得混用：目录 `YYYYMMDD-项目名`，文件 `项目名-类型-YYYYMMDD.扩展名`。日期在前方便按时间排序找项目，文件名在前方便识别文件归属。
- 不要再默认创建不带日期的新项目目录，避免同主题多轮沟通互相覆盖。
- 若项目名未给但主题清楚，用“业务对象 + 核心模块”命名，例如：
  - `YYYYMMDD-机关单位食堂支付分账`
  - `YYYYMMDD-企业采购分红结算`
- 不要为了同一主题重复创建多个近义目录。

### 文件命名
- 统一格式：`项目名-类型-YYYYMMDD.扩展名`。
- 所有归档文件必须带项目名前缀，同一项目目录内的文件名前缀一致，一眼看出属于哪次沟通。
- 沟通记录：`项目名-沟通记录-YYYYMMDD.md`
- 原始会议转写：`项目名-原始会议转写-YYYYMMDD.md`
- 思维导图：`项目名-思维导图-YYYYMMDD.md`，真实导图文件为 `项目名-思维导图-YYYYMMDD.xmind`
- ASCII 树状图（导图结构核对稿）：`项目名-ASCII树状图-YYYYMMDD.txt`；内容取自导图大纲，不是功能清单的模块树。功能清单的模块结构树内嵌在 `项目名-功能清单-ASCII-YYYYMMDD.txt`，不单独出文件。
- 功能清单（内部版）：`项目名-功能清单-初稿-YYYYMMDD.md`
- 功能清单（客户版，零待定）：`项目名-功能清单-客户版-YYYYMMDD.md`
- 功能清单 ASCII 版：`项目名-功能清单-ASCII-YYYYMMDD.txt`（与对应 Markdown 同版本）
- 功能清单 Excel 版：与对应 Markdown 同名，扩展名 `.xlsx`（客户版用 `-客户版-`）；用户要求表格版时产出
- 若用户明确要需求文档：`项目名-需求文档-YYYYMMDD.md`
- 若用户明确要报价、预算或完整项目评估：`项目名-项目报价与第三方服务费用-YYYYMMDD.md`
- 项目名以所在项目目录名为准，去掉开头 `YYYYMMDD-` 后使用；目录名与文件名前缀必须一致（目录 `20261028-某项目` 对应文件 `某项目-沟通记录-20261028.md`）。
- 历史目录仍为 `项目名-YYYYMMDD`（日期在后）时沿用原目录、不强制改名，项目名取去掉末尾 `-YYYYMMDD` 的部分。
- 这类归档文件默认都带日期，避免多轮沟通互相覆盖；不要再默认使用无日期文件名。
- 用户手上有历史无前缀文件时，同轮内一并改名，不留新旧两套。

### 同目录归档规则
- 只要用户意图是“保存到 `jy-design` 并继续整理”，则以下文件默认放在同一个项目目录：
  - `项目名-沟通记录-YYYYMMDD.md`
  - `项目名-原始会议转写-YYYYMMDD.md`
  - `项目名-需求文档-YYYYMMDD.md`
  - `项目名-思维导图-YYYYMMDD.md`
  - `项目名-功能清单-初稿-YYYYMMDD.md` 或 `项目名-功能清单-客户版-YYYYMMDD.md`（产出功能清单时，按交付对象二选一）
  - `项目名-功能清单-ASCII-YYYYMMDD.txt`（产出功能清单时必须同时给）
- 不要把 `沟通记录` 放在 `jy-design`，却把 `需求文档` 或 `思维导图` 放到其他仓库的 `outputs/`、`projects/`、`notes/` 目录。
- 如果本轮先误落到其他仓库，应直接迁移到 `jy-design` 项目目录，不保留重复副本。

## 材料落盘规则
- 原始材料优先保留以下结构：
  - 标题
  - 日期
  - 智能总结（如有）
  - 待办（如有）
  - 原文
- 若用户只给聊天原文，没有总结，可补一版简短总结，但不能替代原文。
- 原文必须完整保留，不能只存整理后的摘要、节选、摘录或“原话摘录”。
- 如果正式需求只需要抽取部分范围，仍必须在 `项目名-原始会议转写-YYYYMMDD.md` 中完整保存用户提供的全部沟通原文；需求文档再单独按范围抽取。
- 如果是会议纪要或语音转写，优先拆成两份：
  - `项目名-沟通记录-YYYYMMDD.md`：适合快速回看，保留总结、结论、待确认项。
  - `项目名-原始会议转写-YYYYMMDD.md`：完整保存智能总结、待办和逐字原文。
- 同一轮刚生成的文件，如命名错误或结构需补充，优先更新当前文件，不额外复制新版本。

## 原文归档质量阀门（强制）

适用于每次输入包含会议转写、聊天记录、客户原话或其他需归档源材料的任务。此阀门在所有文件写入后、最终回复前执行；未通过即任务未完成。

1. **先原文，后整理**：先创建 `项目名-原始会议转写-YYYYMMDD.md` 或等价原文文件，再创建沟通记录、导图、需求文档。不得用摘要、要点、改写稿替代原文。
2. **逐字完整性核对**：逐段核对输入首段、中段、末段的原句均已写入原文文件；输入包含明确时间戳、说话人、链接、待办时，必须保留，不能改写或省略。
3. **长度核对**：可取得原始文本字符数时，原文文件中“原文”正文字符数不得低于输入原文字符数；允许仅增加标题、日期、来源等元数据，禁止减少原文。
4. **反摘要检查**：原文文件不得出现 `摘要`、`摘取`、`抽取`、`节选`、`省略`、`...`、`详见会话`、`原话语义` 等替代完整原文的标记。出现任一标记即失败，除非该词本身在客户原文中出现。
5. **独立项目不截断来源**：即使需求只抽取会议中的一个模块，原始会议转写仍保存整场会议全文；模块范围限制只作用于沟通记录、导图和需求文档。
6. **失败处理**：任一检查失败时，不得声称“已归档”或“已完成”。删除错误的摘要型原文文件，或明确标记为非原文；补齐全文后重新检查。

### 最小验证命令

```bash
set -e
for RAW in *原始会议转写-*.md; do
  test -s "$RAW"                                   # 目录内每个原文文件都要校验，不能只取第一个
  SECTION=$(mktemp)
  awk '/^#{2,4} .*逐字原文/{flag=1;next} /^#{2,4} /{flag=0} flag' "$RAW" > "$SECTION"
  test -s "$SECTION"                               # 逐字原文段不能为空
  ! rg -n '详见会话|原话语义|以下省略|（略）|\.\.\.' "$SECTION"
done
```

只校验「逐字原文」段落：智能总结、章节概要里出现的「摘要 / 总结 / 省略」等词属正常内容，不作失败处理；「逐字原文」段为空或用一句话顶替全文，才判失败。命令仅防止明显伪归档，不能替代逐段人工核对。最终回复必须明确写出：原文文件路径、原文是否通过质量阀门；未通过则说明缺口，不能用其他产物掩盖。

## 交付物判定

### 只存档
- 如果用户只说“保存到 jy-design”，默认至少落：
  - `项目名-沟通记录-YYYYMMDD.md`
  - 若材料是会议纪要 / 语音转写，再补 `项目名-原始会议转写-YYYYMMDD.md`

### 存档 + 导图
- 导图默认按客户版产出：零待定项、参数齐全、含算例。
- 客户版导图必须依据「已确认参数表」生成；参数表没闭合时，先补问再出图。
- 如果用户说“根据内容出导图 / 思维导图 / 文字版导图”，默认产出：
  - `项目名-沟通记录-YYYYMMDD.md`
  - `项目名-原始会议转写-YYYYMMDD.md`（若源材料是会议/转写）
  - `项目名-ASCII树状图-YYYYMMDD.txt`：先出，内容取自导图大纲，作为导图结构核对稿（不是功能清单的模块树）
  - `项目名-思维导图-YYYYMMDD.md`
  - `项目名-思维导图-YYYYMMDD.xmind`：真实导图，默认交付物；重名时以本 skill 命名为准，覆盖 `weicoz-demand-mindmap-organizer` 的 `思维导图-YYYYMMDD.xmind` 默认名

### 存档 + 需求文档
- 如果用户说“整理成需求文档 / PRD / 功能文档”，在落沟通记录后，再补正式文档。
- 如果同一轮同时涉及“沟通内容 + 需求文档 + 导图”，默认三者都放进 `jy-design/<项目目录>/`，不要拆到不同仓库。
- 只要产出包含 `需求文档`，必须补一段或多段 ASCII 业务流程图，不能只有模块列表和文字说明。

### 存档 + 功能清单
- 如果用户说“出一份功能清单 / 定制功能清单 / 会议纪要转功能清单”，按交付对象产出：
  - 内部版：`项目名-功能清单-初稿-YYYYMMDD.md`
  - 客户版（零待定）：`项目名-功能清单-客户版-YYYYMMDD.md`
  - 两份都先给 `## 零 模块结构树`（text 代码块，与 ASCII 版同构），再按 `类型 | 类型描述 | 模块名称 | 功能描述` 给主表
  - 同时产出 `项目名-功能清单-ASCII-YYYYMMDD.txt`：纯文本树状核对稿，模块名下一行直接写功能描述，不排版宽表格
- 功能清单主表只写定制部分。内部版把现成能力与不确定项放进「待确认项」；客户版不设「待确认项」章节，改设「定案口径」表，逐条写死取值。
- ASCII 版与 Markdown 版必须同源同步：模块名称、功能描述、口径条目完全一致，改一处必须同改两份。ASCII 版按树排版，不按行对齐，因此不要求与 Markdown 行数相同。
- ASCII 版结构：标题行、元数据行、`一、模块结构树与功能说明`（树里每个模块名下一行缩进写功能描述）、`二、定案口径` 或 `待确认项`、`三、说明`。
- ASCII 版不排等宽表格：宽表格在终端里必然折行错位，核对价值低。等宽表格只在渲染 `.xlsx` 时由 Markdown 主表生成。
- 功能描述按显示宽度折行（中文按 2 列算），默认折到 72 列；折行时标点不落到行首，数字与百分号不得跨行断开。
- 用户要求 `.xlsx` 时，再产出与对应 Markdown 同名的 `.xlsx`：固定三张表 = `功能清单`（主表四列 + 项目信息区）、`模块结构树`（使用端 / 业务分类 / 功能模块，附文本树）、`待确认项`（内部版，序号 / 待确认项 / 状态）或 `定案口径`（客户版）；表头冻结、开筛选、描述列自动换行；行数与 Markdown 主表一致。宽表格只在 `.xlsx` 里出现，ASCII 版不复制。
- 模块结构树用 `├─` / `└─` / `│` 绘制：一级是使用端，二级是业务分类并标模块数，叶子是功能模块名；叶子数必须等于主表数据行数。
- 模块名称用客户听得懂的业务词：写“月度业绩统计”“分红明细导出与调整”，不写“归集”“触发”“拦截”“重算”“序次”这类系统内部用语；客户自己文档里的行业词（计提、扣回、核销）照用。
- 功能描述同样用业务语言：写“记入发放记录”“算出总份数”，不写“写入”“落库”“校验”“生成快照”这类实现词。
- 任何版本都禁止用省略号截断描述；`.xlsx` 的表格列宽按中文显示宽度折算，自动折行时不得让 `、，。；：` 等标点落到行首。

## 提问闭环与定案参数表（强制）

材料里常见只讲玩法、不讲参数的情况，两份材料互相冲突也很常见。参数缺口和冲突都不能靠猜，也不能留给客户版。

### 必问与免问

按影响面判定，不按"我有多确定"判定：材料没写、但我方很确定该怎么填的项，同样要问。

| 情形 | 处理 |
| --- | --- |
| 影响金额、比例、基数、门槛、归属、发放形式、结算节奏、退款扣回、身份权益、停止条件的取值 | 必问 |
| 两份材料写法冲突（会议 / 文档 / 聊天 / 系统现状） | 必问，附双方原文、我方倾向、按 A 或按 B 的后果 |
| 材料没写，需要我方补默认值 | 必问，给出默认值与影响 |
| 交付对象或范围变化（客户版还是内部版、含不含某模块、要不要需求文档或报价） | 必问 |
| 可逆、不改变业务含义的技术与表达选择（字段名、措辞、样式、文件名细节、表格折行） | 免问，按 skill 默认执行，交付说明里列一行"我按 X 处理" |
| 退款相关规则（是否扣回奖励、是否冲减业绩、是否影响身份或点位、退款流程本身） | 必问，并且逐个交付物确认：导图 / 功能清单 / 需求文档各自收不收录 |

免问类也要有把握才自行决定（默认 ≥95% 确定）；业务项一律走必问，与把握大小无关。

### 退款类内容怎么问
退款规则常和结算、奖励扣回、业绩冲减缠在一起，写不写进交付物由用户定，不默认收录，也不默认省略。

1. 先列退款点：退款扣回、业绩冲减、奖励追回、身份或点位回退、售后退款流程。
2. 说明默认处理：默认不进客户版；一旦收录就写完整规则，不写半句。
3. 逐个交付物问：导图收不收、功能清单收不收、需求文档收不收，三处可以不同。
4. 用户没确认前：内部版写进「待确认项」，客户版一律不写。
5. 确认收录后，导图、功能清单、需求文档三处的金额、比例、时点必须一致；只改一处视为缺陷。
6. 确认不收录时，在沟通记录里记一行"退款规则用户确认不写入交付物"，避免下一轮又被翻出来重问。

### 材料冲突怎么问
1. 列出冲突点：同一规则在两份材料里的不同写法。
2. 贴双方原文，标明出处（会议时间戳 / 文档章节）。
3. 给出我方倾向与理由。
4. 写明按 A 或按 B 会分别得到什么结果，用户只做选择题。
5. 冲突项进「差异对照表」，逐条闭环后才出客户版；不得用"以会议为准"一类规则自动裁决。

### 怎么问
1. 缺口和冲突整理成编号清单，一条一句，写明"按 A 会怎样、按 B 会怎样"。
2. 用提问工具一次问完，单批不超过 12 条，每条给推荐项；超过 12 条说明范围还没收口，先谈范围。
3. 分两级：阻塞型（不问不能出客户版）与非阻塞型（可先出内部版，交付前必须闭环）。
4. 仍有未答项就继续下一轮，直到全部有明确取值。不得用"平台另行公布""按行业惯例"顶替。
5. 用户回答后立刻回写「已确认参数表」：参数、定值、确认时间、来源（客户原话或本轮确认）、影响哪些产物。
6. 参数表落进同项目沟通记录，作为后续导图、需求文档、功能清单、报价的统一基线。

### 交付对象判定
- 默认按**客户版**处理；用户说"内部评估""先看工作量""我们自己看"时才是内部版。
- 客户版开工前先跑提问闭环，参数没闭合不出图、不写文档。
- 内部版必须在文件名或正文首行显式标注"内部版"，并写明还缺哪些参数。
- 客户版导图与客户版文档不得出现待定项；内部版可保留待确认项，但必须与参数表分开写。

## 客户版零待定门禁（强制）

对客户版产物（导图、功能清单、需求文档、报价）全文检索：

`待确认|待定|未定|暂定|客户需确认|参考|以最终为准|待客户|另行公布|后续再定`

白名单（属正常业务用词，不判失败）：订单状态 `待确认收货`、`待确认付款`、`待确认订单`；价格语境 `参考价`、`参考售价`。

命中白名单之外的词即视为未完成。处理方式是回到提问闭环把口径问清，不是换同义词绕开。`weicoz-demand-mindmap-organizer` 的「客户版零待定门禁」与本表一致。

## 参数基线与同步（强制）

- 每个项目只维护一份「已确认参数表」，落在同项目沟通记录里，作为唯一数据源。
- 导图、需求文档、功能清单、报价、ASCII 版的数值必须与该表一致；同一参数出现第二种写法即视为缺陷。
- 同轮产出三份以上文件时，优先用生成脚本从同一份数据生成 Markdown 与 ASCII，不手改多份。
- 口径变更后必须重跑两项检查：客户版零待定门禁；旧口径关键词检索（在全部产物中应为 0 命中）。

## 导图工作流
1. 先判断是整套模式导图，还是单模块规则导图。
2. 如果主题集中在分账、返佣、补贴、结算、核销、分润，优先按单模块规则导图整理。
3. ASCII 骨架仅在用户要求或复杂结构需要检查时生成；内部结构检查不构成用户审批点，不阻塞已要求的导图文件。
4. 再落一份 Markdown 导图文件，供后续继续补改。
5. 若有 `weicoz-demand-mindmap-organizer`，优先按其规则执行，不要写另一套导图标准。

## 单模块规则导图备用骨架（仅在导图 skill 不可用时使用）
- 可用 `weicoz-demand-mindmap-organizer` 时，一律按其主干规则出图，不使用本骨架，避免两套标准混用。
- `功能定位`
- `参与身份`
- `触发逻辑`
- `关系匹配`
- `计算规则`
- `结果记录`
- `后台配置`
- `待确认项`（仅内部版；客户版删除该分支）

## 执行流程
1. 判断项目目录是否已存在；存在则复用，不存在则创建。
   - 新创建时默认目录名为 `YYYYMMDD-项目名`（日期在前），文件名为 `项目名-类型-YYYYMMDD`（名称在前）
2. 先判断是否是会议纪要 / 语音转写 / 聊天整理；若是，按命名规则落 `项目名-沟通记录-YYYYMMDD.md`，并补 `项目名-原始会议转写-YYYYMMDD.md`。
3. 判断用户是否要求导图或文档。
3.1 判定交付对象（客户版 / 内部版）。客户版先跑「提问闭环与定案参数表」，参数没闭合不进入出图与写文档。
4. 若要求需求文档，直接在同目录落 `项目名-需求文档-YYYYMMDD.md`。
   - 并检查正文里是否已有 ASCII 业务流程图；没有就必须补上。
5. 若要求导图，优先用 `weicoz-demand-mindmap-organizer` 的规则整理，并在同目录落 `项目名-思维导图-YYYYMMDD.md` 与 `项目名-思维导图-YYYYMMDD.xmind`。
6. 无论最终是否落文件，只要有思维导图产出，就先给导图结构的 ASCII 版（来自导图大纲，不是功能清单树），再决定是否落 `.txt` 或 `.md`。
6.1 若要求功能清单，按交付对象落 `项目名-功能清单-初稿-YYYYMMDD.md` 或 `项目名-功能清单-客户版-YYYYMMDD.md`，并同时落 `项目名-功能清单-ASCII-YYYYMMDD.txt`；两份内容必须一致。
7. 若主题存在明显缺口，按「定案参数表与提问闭环」先问清；问清后把结果写成「已确认参数表」落进沟通记录。
   - 客户版导图与客户版文档不得留待定项；未闭合就不发客户版。
   - 内部版可留待确认项，但必须与参数表分开。
8. 执行“原文归档质量阀门（强制）”；未通过则回到原文文件补齐，不继续交付。
8.1 客户版产物再执行「客户版零待定门禁」：按词表全文检索，白名单外命中即不交付。
8.2 参数或口径变更后，按「参数基线与同步」同改全部产物，并重跑零待定门禁与旧口径关键词检索。
9. 返回时明确告知：
   - 保存路径
   - 生成了哪些文件
   - 当前材料已明确什么
   - 还缺什么
   - 原文质量阀门结果

## 失败分支
- 没有明确项目名：
  - 先按主题拟一个临时项目名并落盘
  - 在回复里显式说明本次使用的目录名
- 材料太短，无法展开：
  - 只落沟通记录
  - 导图只给最小骨架
- 已有同主题文件很多：
  - 优先更新本轮对应文件
  - 不再新建近似副本

## 报价扩展

当用户要求报价、预算、周期、服务器、云服务、第三方服务/API/SDK 价格、App Store/Google Play 上架费用或完整项目评估时：

1. 先完成沟通记录、原始会议转写和需求范围收口。
2. 读取 `$WEICOZ_SKILLS_ROOT/weicoz-project-quote-estimator/SKILL.md` 并按其流程执行。
3. 在同一个 `jy-design/<项目目录>/` 生成或更新 `项目名-项目报价与第三方服务费用-YYYYMMDD.md`。
4. 报价文档必须分开：功能模块逐项报价、第三方服务逐项单价/用量/公式、服务器配置/扩容费用、年度/月度/一次性费用、上架费用和责任边界。
5. 厂商价格无法查到或仅销售报价时，标注“待厂商书面报价”和所需参数；可以给预算区间，不得伪造固定合同价。

## 质量标准
- 客户版导图与客户版文档零待定项；参数缺口先用提问闭合，不在成品里留问号。
- 同项目必须存在一份「已确认参数表」，导图、需求文档、报价共用同一基线。
- `jy-design` 里一定有真实文件产物，不只是在聊天里总结。
- 原文被完整保留，摘要、节选、摘录不是唯一内容。
- `项目名-原始会议转写-YYYYMMDD.md` 必须包含用户提供的全部沟通原文；若只保存摘录，视为未完成。
- 每次归档后必须执行原文归档质量阀门；未通过时，沟通记录、导图、需求文档均不可作为完成交付。
- 会议类材料如果后续又整理出 `需求文档`、`思维导图`，这些文件也必须在同一个 `jy-design` 项目目录中。
- 任何 `需求文档` 类产物都必须包含 ASCII 业务流程图，方便客户和内部快速核对主链路。
- 任何 `思维导图` 类产物都必须先出 ASCII 版导图，再输出最终文件版。
- 任何 `功能清单` 类产物都必须同时产出 Markdown 版与 ASCII 版；两份的模块名称、功能描述、口径条目一致（ASCII 为树状核对稿，不按行对齐）。用户要 `.xlsx` 时，三份内容一致。
- 用户触发报价时，必须有独立报价文件；功能模块合计必须等于开发服务费合计。
- 报价触发时，第三方服务、服务器和上架费用必须逐项列出并可复算。
- 不在 `knowledge` 或其他仓库保留同主题重复副本，除非用户明确要求双份存放。
- 导图结构和材料复杂度匹配，不乱扩。
- 已明确事项和待确认事项分开；客户版产物在文件名或正文标注"客户版"，内部版标注"内部版"。
- 同一参数在所有产物中只能有一个取值；口径变更后旧写法应为 0 命中（见「参数基线与同步」）。
- 目录命名、文件命名稳定，可复查、可继续迭代。
