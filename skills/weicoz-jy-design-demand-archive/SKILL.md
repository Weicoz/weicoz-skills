# JY Design Demand Archive

本 skill 是 jy-design 项目的总入口，只管四件事：项目目录与命名、原文完整归档、已确认参数表、客户版门禁。具体交付物的格式交给专项 skill。

## 1. 委派（强制）

| 交付物 | 执行者 | 本 skill 只提供 |
| --- | --- | --- |
| 功能清单 | `weicoz-custom-feature-checklist` | 项目目录、交付对象、已确认参数表 |
| 思维导图 | `weicoz-demand-mindmap-organizer` | 项目目录、文件名、交付对象、已确认参数表 |
| 报价 | `weicoz-project-quote-estimator` | 项目目录、文件名、已归档范围 |
| 需求文档 | `weicoz-pm-requirements-from-docs` | 项目目录、文件名、交付对象、已确认参数表 |
| 讲解稿（内部） | `weicoz-briefing-script` | 项目目录、文件名、沟通记录与已确认参数表位置 |

- 同轮命中多个 skill 时，先加载专项 skill，再按本 skill 落盘。不得因为本文件提过某交付物就跳过专项 skill。
- 格式冲突以专项 skill 为准；目录、文件名、交付对象、参数基线、客户版门禁以本 skill 为准。
- 专项 skill 不可用时才用本文件第 6 节的备用规则。

## 2. 目录与命名

- 根目录：`$WEICOZ_JY_DESIGN_ROOT`。项目按收款合同及其范围划分；同一客户重新签约或单独报价、且用户明确作为新项目时，新建目录，引用旧项目资料，保留原项目。只有同一合同范围的续改才复用目录；归属不清时先问。
- 新目录：`YYYYMMDD-项目名`（日期在前，方便按时间找项目）。项目名未给时用“业务对象 + 核心模块”，例如 `YYYYMMDD-机关单位食堂支付分账`，并在回复中写明。
- 历史目录 `项目名-YYYYMMDD`（日期在后）沿用，不改名。
- 文件：`项目名-类型-YYYYMMDD.扩展名`（名称在前，方便认归属）。项目名取目录名去掉日期段，目录与文件前缀必须一致。

| 类型 | 文件名 |
| --- | --- |
| 沟通记录 | `项目名-沟通记录-YYYYMMDD.md` |
| 原始会议转写 | `项目名-原始会议转写-YYYYMMDD.md` |
| 需求文档 | `项目名-需求文档-YYYYMMDD.md` |
| 思维导图 | `项目名-思维导图-YYYYMMDD.xmind`，同名 `.md` 与 `项目名-ASCII树状图-YYYYMMDD.txt` |
| 报价 | `项目名-项目报价与第三方服务费用-YYYYMMDD.md` |
| 功能清单 | 按 `weicoz-custom-feature-checklist`，前缀与日期规则同上 |
| 讲解稿 | `项目名-讲解稿-YYYYMMDD.md` |

- 本表覆盖专项 skill 的默认文件名（例如导图 skill 的 `思维导图-YYYYMMDD.xmind`）。
- 版本标在文件名时放在类型后，例如 `项目名-思维导图-内部版-YYYYMMDD.xmind`。
- 同轮生成的文件命名或结构有误时，直接改当前文件，不复制新版本。目录里有本项目的无前缀历史文件时，同轮改名，不留两套。
- 全部产物放同一个项目目录。误落到其他仓库（`outputs/`、`projects/`、`notes/`、knowledge）的本轮产物直接迁回，不留副本；用户明确要求双份时例外。
- 外发前运行项目树门禁；它检查目录格式、文件前缀、项目日期、错误别名，以及同 SHA256 不同文件名的重复副本。payload、隐藏文件、脚本和子目录不参与检查。

```bash
python3 "$WEICOZ_SKILLS_ROOT/weicoz-jy-design-demand-archive/scripts/check_project_tree.py" \
  "$PROJECT_DIR" --external --json
```

## 3. 原文完整归档（强制）

目标：客户原话一字不丢。摘要、节选、改写稿不能代替原文。

1. **先原文，后整理**：先写 `项目名-原始会议转写-YYYYMMDD.md`，再写其他文件。结构：标题、日期、来源、智能总结（如有）、待办（如有）、`## 原文`（或 `## 逐字原文`）。时间戳、说话人、链接、待办原样保留。
2. **不重打原文**：源材料是文件时，用 shell 把元数据头和源文件拼成原文文件（`cat header.md "$SRC" > 原文.md`），不经模型重写。源材料贴在对话里时，整段写入一次；然后把同一段另存到 `$TMPDIR` 作为校验源。
3. **整场保存**：需求只涉及其中一个模块时，原文仍存整场会议；范围限制只作用于沟通记录、导图和需求文档。
4. **会议类拆两份**：`沟通记录` 放总结、结论、已确认参数表、待确认项，供快速回看；`原始会议转写` 放全文。只有聊天原文、没有总结时，可在沟通记录补一版简短总结。
5. **校验**：全部文件写完后运行；未通过即任务未完成，不得声称“已归档”。

```bash
python3 "$WEICOZ_SKILLS_ROOT/weicoz-jy-design-demand-archive/scripts/check_raw_transcript.py" \
  项目目录/*原始会议转写-*.md --source 源文件
```

`--source` 能给就必须给：它逐行核对源文是否按顺序完整出现在原文段。拿不到源文件时省略，脚本只查空段和“详见会话、以下省略、节选”等替代标记。失败时补齐全文后重跑；错误的摘要型文件删除或改标为非原文。

## 4. 交付对象与提问闭环（强制）

> **出错后果**：功能清单、导图、需求文档（含商业模式与玩法）、讲解稿、报价里任何一处写错，影响都很大，会失去客户对我们的信任。所以不得出错：内容必须明确，不得含糊；任何不确定点都必须问用户，不得自行猜测、补默认值或用模糊说法带过。

本节是提问闭环的唯一完整定义。专项 skill 只引用本节，不另立口径。

### 先确认，再统一出稿

- 在生成任何功能清单、思维导图、需求文档、讲解稿或报价前，先读完本次相关材料，把这些产物共用的业务规则、关键参数、流程、边界和冲突一次梳理完整。不得先做功能清单，再把已可发现的算法或异常问题推迟到导图、需求文档或开发阶段才问。
- 每条写成定案的业务结论都必须有可定位的原文或用户明确答复支撑，且把握度**严格超过 90%**。把握度 ≤90%（含恰好90%）、材料冲突、指代不明或需要补默认值的，先列入问题清单；高把握度不能替代缺失的业务授权。
- 把握度是对证据和理解的逐项判断，不是随口报一个百分比。核对对象、基数、公式、计算顺序、时间、归属与例外，并用正常及关键边界案例推演；用户答复含糊或推演仍有分歧时继续问。
- 读完材料后集中用提问工具问完。回答引出新缺口时，再集中补问；每轮回写同一份参数表，直到每项已明确且理解把握度 >90%，或按下方「保留未知继续」明确登记为例外。
- 确认完成后，按同一份业务基线一次生成用户要求的后续产物；切换专项 skill 时复用确认记录，不重复问已回答且未变化的规则，也不自动扩大交付物范围。

### 交付对象
- 默认**客户版**。用户说“内部评估”“先看工作量”“我们自己看”时才是内部版。导图会外发但用户没说清时，按客户版处理并在回复里说明。
- 客户版：面向客户直接收件，文件名、标题及工作表名使用正式业务名称；“客户版”仅为内部分类，不出现在对外交付名称中。正文零待定项、参数齐全，涉及金额比例时含算例；按「保留未知继续」登记的例外进「方案确认项」，不冒充已定规则。内部文件可保留版本标记，与实际外发文件区分。
- 内部版：文件名或正文首行标注“内部版”，并写明缺哪些参数；待确认项与已确认参数表分开写。内部版同样先跑提问闭环；用户明确说先出内部版时，未答项留在待确认项。

### 必问与免问
先复用来源明确且理解把握度 >90% 的已确认信息；其余按下表问清。材料没写、但我方很确定该怎么填的业务项，同样要问；已排除的范围不为补齐模板而扩问。

| 情形 | 处理 |
| --- | --- |
| 金额、比例、基数、门槛、归属、发放形式、结算节奏、身份权益、停止条件的取值 | 必问 |
| 商业模式与玩法：钱从哪来、谁付给谁、循环怎么闭合、名词含义 | 必问 |
| 两份材料写法冲突（会议 / 文档 / 聊天 / 系统现状） | 必问：附双方原文与出处、我方倾向、按 A 或按 B 的结果；进「差异对照表」逐条闭环；不得用“以会议为准”自动裁决 |
| 材料没写，需要我方补默认值 | 必问，附默认值与影响 |
| 交付对象或范围变化（客户版/内部版、含不含某模块、要不要需求文档或报价） | 必问 |
| 退款相关（扣回奖励、冲减业绩、身份或点位回退、售后退款流程） | 必问，见下方退款规则 |
| 只涉及表达和格式、不改变业务含义的选择（字段名、措辞、样式、文件名细节、折行） | 免问；有一点不确定会改变业务含义就转必问；交付说明逐条列“我按 X 处理” |

### 退款规则
默认不收录，也不默认省略，由用户逐个交付物决定：导图、功能清单、需求文档三处可以不同。未确认前，内部版写进待确认项，客户版不写。确认收录时写完整规则，三处金额、比例、时点一致。确认不收录时，在沟通记录记一行“退款规则用户确认不写入交付物”，下一轮不重问。

### 怎么问
1. **先汇总，一次问完**：读完全部材料，把所有不确定点整理成一份完整问题清单，再一次性提问。不得边做边零散地问，不设单轮条数上限。
2. **用提问工具**：按当前宿主实际暴露的 schema 构造参数，核对题干字段和选项类型，不复用其他宿主的结构。调用宿主自带的提问工具（Claude Code 为 `AskUserQuestion`）。工具单次题数有上限（例如每次 4 题）时，同一轮连续调用直到问完，中间不插入其他工作。宿主没有提问工具时，用编号文本清单一次列完。
3. **每题的格式**：题干写清问题，以及按不同选项分别会怎样。每题至少 5 个可选项：首项是我方建议答案并标“(推荐)”。工具每题最多 4 个选项时，给满 4 个，加上工具自带的“Other/其他”自由输入，共 5 个；文本清单至少列 5 个。客户才能定的项，选项里必须有“需和客户确认”。
4. **冲突以用户为准**：用户的回答和我方之前问题的前提、推荐冲突时，以用户回答为准。受影响的问题与推荐全部作废，按新前提重写。
5. **多轮迭代**：把回答新引出的缺口、作废后重写的问题、仍未答的问题汇总后再问；按前置确认门槛收口。不得用“平台另行公布”“按行业惯例”顶替。
6. **回写**：每轮答完，立刻回写「已确认参数表」：参数、定值、确认时间、来源、影响哪些产物；尚存疑点单列，不能与定值混写。

### 保留未知继续

- 保留现有例外：用户明确说“我不清楚”“需和客户确认”，或明确要求“不清楚的先按现在了解到的继续”“先出内部版/草稿，不等答复”时，按其授权范围继续，不反复追问同一未知项。沉默、催交或仅请求某种文件格式不构成该授权。
- 记录具体未知项、用户原话、已知依据、我方理解或建议及影响。已知且有依据的部分照常产出；未知项仍是未知，不因用户允许继续就升级为定案或视为把握度 >90%。
- 客户版用「方案确认项」集中保留这些例外；内部版/草稿放入对应待确认章节。各产物共享同一问题与口径，不能一份写成定案、另一份仍待拍板。
- 只在有依据时给建议值，并明确标为建议；没有足够依据时，保留已知功能与问题引用，不编金额、比例或算法，也不输出依赖该未知规则的确定收益算例。

### 方案确认项（客户版）
只放按「保留未知继续」获准保留的具体业务项。不得用它绕过尚未提问的缺口。

- **位置**：Markdown 用标题 `## 方案确认项`，放在正文最后；导图用一级分支 `方案确认项`，`.md` 和 ASCII 稿同步生成；功能清单 xlsx 用单独的 sheet `方案确认项`。
- **条目格式**：每条以 `第N条` 开头，N 从 1 连续编号。条目内依次写：问题、选项（用 A/B/C 标，不用数字）、我方建议、选不同选项的影响。
- **正文写法**：正文写我方建议值并引用编号，写法固定为 `建议值，见方案确认项第N条`，例如 `直推奖励 10%（建议值，见方案确认项第3条）`。
- 无依据给出建议值时，正文只保留已知功能并引用 `方案确认项第N条`，确认项中列清缺口和影响，不伪造一个数值凑格式。
- **门禁**：确认页内不查禁词。正文引用的编号与确认页条目必须一一对应：不得缺条、多条或重复编号。
- 客户答复后：回写参数表，把正文的建议值改为定值，删掉对应条目和引用。全部答完后，删除整个确认页。

## 5. 参数基线与客户版门禁（强制）

- 每个项目只有一份「已确认参数表」，放在最新沟通记录里。导图、需求文档、功能清单、报价、ASCII 稿的数值都从这里取；同一参数出现第二种写法即缺陷。
- 用户声明业务数字可自定义时，在基线中区分初始值、可配置参数和计算规则；各产物统一表达，不能把初始值写成固定限制，也不能用“后台可配”代替尚未确认的基数、公式或计算顺序。
- 同轮产出多份同源文件时，用脚本从同一份数据生成（导图用 `build_xmind.py --ascii --markdown` 一次出三份），不手改多份。
- 客户版交付前、以及任何口径变更后，对全部客户版产物运行门禁（支持 `.md .txt .csv .xlsx .xmind`）：

```bash
python3 "$WEICOZ_SKILLS_ROOT/weicoz-jy-design-demand-archive/scripts/check_client_ready.py" \
  --external 实际外发文件... [--old-term 旧口径词 ...]
```

- 同时运行第 2 节的项目树门禁；文件名、目录名或重复副本任一失败，不得外发。

- 禁词：`待确认|待定|未定|暂定|客户需确认|参考|以最终为准|待客户|另行公布|后续再定`。白名单：订单状态 `待确认收货`、`待确认付款`、`待确认订单`；价格 `参考价`、`参考售价`。词表改动时同步脚本与 `weicoz-demand-mindmap-organizer`。
- 「方案确认项」章节、分支或 sheet 不查禁词；脚本同时核对正文 `方案确认项第N条` 与确认页 `第N条` 是否一一对应。
- 命中即回到提问闭环处理，按本节确认项规则保留已获授权的例外；不得换同义词绕过门禁。
- 门禁只扫客户版文件；沟通记录、原始会议转写、内部版不扫。
- `--external` 另查实际外发文件名及可见标题中的内部版本标记。功能清单 XLSX 还须按专项 skill 对最终文件运行模板检查；文字门禁通过不代表模板通过。
- 修改本节确认流程时，按 `references/behavior-checks.md` 做隔离行为评测；脚本测试只证明格式与门禁，不冒充模型行为验证。

## 6. 各交付物要点

### 只存档
用户只说“保存到 jy-design”：落沟通记录；源材料是会议或转写时再落原始会议转写。不主动生成导图、需求文档、功能清单、报价。用户说“整理成需求材料”但没点名交付物时，默认补需求文档与思维导图。

### 思维导图
- 按 `weicoz-demand-mindmap-organizer` 执行，文件名按第 2 节。
- 先判整套模式导图还是单模块规则导图；主题集中在分账、返佣、补贴、结算、核销、分润时，按单模块规则导图整理。
- 每次出导图都同时落 `.xmind`、同名 `.md` 和 `ASCII树状图.txt`，三份由同一份大纲脚本生成。ASCII 稿供核对结构，不是审批点，不等用户确认。
- 导图 skill 不可用时的单模块规则备用骨架：`功能定位 / 参与身份 / 触发逻辑 / 关系匹配 / 计算规则 / 结果记录 / 后台配置`，内部版再加 `待确认项`。

### 需求文档
- 用户要“需求文档 / PRD / 功能文档”时，按 `weicoz-pm-requirements-from-docs` 执行，落 `项目名-需求文档-YYYYMMDD.md`；调用时明确告诉它交付对象和参数表位置。
- 客户版不含「待确认重点」「PM 判断」和报价节；同时要报价时，报价另出文件。
- 门禁加跑 `--old-term 需确认`（该 skill 内部版的兜底标记），命中逐条核对。
- PM skill 不可用时的备用规则：正文必须含至少一段 ASCII 业务流程图（自上而下：谁做什么 → 判断 → 结果），不能只有模块列表；数值取自已确认参数表。

### 功能清单
按 `weicoz-custom-feature-checklist` 执行，落同项目目录。调用时明确告诉它交付对象（客户版/内部版）和参数表位置。

### 讲解稿
- 用户要给产品/开发讲清玩法与分工时，按 `weicoz-briefing-script` 执行，落 `项目名-讲解稿-YYYYMMDD.md`；调用时告诉它沟通记录与已确认参数表位置。
- 讲解稿同样先跑第 4 节前置确认；用户获准保留的未知项按共享例外处理，已知规则与建议分开写。不跑客户版禁词门禁。

### 报价
仅用户明确要求时调用 `weicoz-project-quote-estimator`。先完成原文归档和范围收口，再生成报价；报价内部规则以该 skill 为准。

## 7. 执行流程

1. 定位或创建项目目录（第 2 节）。
2. 写原始会议转写（第 3 节），再写沟通记录。
3. 按第 4 节一次梳理共用业务基线，集中提问；完成条件为各项有依据、理解把握度 >90%，或已明确登记用户允许保留的未知项。其余缺口未闭环时只交付问题清单与我方倾向。
4. 按第 1、6 节调用专项 skill，复用同一基线生成所需交付物；新发现或变更的业务问题才重新问，已获准保留的未知项按当前已知内容继续。
5. 跑原文校验；客户版再跑文字门禁和项目树门禁（第 5 节）。任一未通过回到对应步骤。
6. 回复：保存路径、生成的文件、已明确事项、方案确认项条数、“我按 X 处理”的免问项、两项校验结果（命令与通过/失败）。

## 8. 失败分支

| 情况 | 处理 |
| --- | --- |
| 没有项目名 | 按主题拟临时名落盘，回复写明目录名 |
| 材料太短 | 只落沟通记录；导图只给最小骨架 |
| 同主题文件很多 | 更新本轮对应文件，不建近似副本 |
| 用户催交但参数未闭合 | 催交不替代业务答复；用户明确允许带未知继续时按第4节处理，不擅改交付对象 |
