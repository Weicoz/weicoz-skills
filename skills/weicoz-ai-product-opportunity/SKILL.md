# AI Product Opportunity

## Purpose

把一个模糊的 AI 产品想法压缩成可验证的商业判断：谁在什么场景下，为什么现在愿意付钱，以及最小闭环怎么跑。

不要从“我能做什么功能”开始。先找购买理由，再设计 MVP，再决定是否开发。

## Core Rule

每次判断都先回答这道填空题：

```text
什么人，
在什么场景下，
愿意花多少钱，
解决什么问题？
```

如果四格填不实，默认不是产品机会，只是 demo 想法。

## When To Use

- 用户有一个 AI 产品 / SaaS / 工具站 / 插件 / 新词站 / 出海产品想法，想判断能不能做。
- 用户想从抱怨、搜索词、新闻热点、新模型、新技术、竞品差评或服务平台里挖 idea。
- 用户想把一个大方向收窄成小而美 MVP。
- 用户想做 GO / NO-GO / HOLD 判断，而不是泛泛 brainstorm。
- 用户想像素级模仿一个已赚钱产品，拆出购买理由、收费点、流量入口和技术闭环。

## Operating Principles

- 产品 = 购买理由的封装。没有购买理由的软件最多是 demo。
- 需求只能发现，不能发明。用户夸“产品很好”没有价值，愿意付钱才有价值。
- 先有核心需求点，再有产品设计、产品开发、独特渠道。
- 新手先守，再破，再离：先像素级模仿已验证闭环，再做差异化壁垒，最后积木式创新。
- 小而美不是没野心，而是第一刀切小但切准。
- Alpha 窗口真实存在。需求爆发、供给没跟上时，速度本身就是优势。

## Default Workflow

### 1. Define The Buying Reason

先把 idea 改写成购买理由，而不是功能描述。

检查：
- 用户是谁：必须是一类具体人，不是“所有人”。
- 场景是什么：必须是具体触发场景，不是泛泛日常。
- 付费意愿：最好有现有支出、替代方案、预付、迁移或明确损失证据。
- 问题是什么：必须能落到一个可交付结果。

输出一句 sharp promise：

```text
帮 [具体人群] 在 [具体场景] 用 [更快/更便宜/更简单/更安全] 的方式得到 [具体结果]。
```

### 2. Find Demand Evidence

按场景选择来源，优先找已经发生的行为，不找口头意见：

- 抱怨型：差评区、一星评论、小红书/知乎/微博/抖音吐槽、Reddit、X、客服记录、社群讨论。
- 搜索型：Google Trends、Semrush、Ahrefs、关键词魔法工具、相关问题和长尾词。
- 热点型：新闻窗口、平台政策变化、产品发布、账号迁移、接口变化、工作流中断。
- 技术型：Hugging Face Trending、开源项目、论文、模型发布、开发者社区。
- 竞品型：TrustMRR、Toolify、TAAFT、Product Hunt、插件商店、G2/Capterra/Trustpilot。
- 服务型：Fiverr、Upwork、淘宝/闲鱼等已有人工服务订单。

真实信号优先级：

1. 已付费或预付。
2. 正在花钱找替代方案。
3. 高频抱怨同一件事。
4. 主动搜索解决方案。
5. 只说“我会用”但不付钱，低置信度。

### 3. Score Supply-Demand Imbalance

判断机会是否来自供需失衡：

- 需求已经存在吗？
- 现在的供给是否太慢、太贵、太复杂、太差、太不方便？
- 市场是否突然变化，导致需求短期暴涨？
- 你能不能把某个环节做得更快、更便宜、更简单、更具体？
- 这个需求是偶发，还是可以持续滚大？

没有失衡，就不要硬做。

### 4. Choose Opportunity Pattern

给机会归类，只选最贴近的一类：

- 幸福方式：来自自己、朋友、同行、熟悉圈层的长期抱怨。
- 搜索词机会：明确搜索词，高意图，竞争可切入，能设计产品和收费方式。
- 新闻窗口：变化刚发生，用户需要立刻完成某个动作，2-3 天可上 MVP。
- 新技术包装：技术强但普通用户不会用，需要场景化界面或更低门槛入口。
- 暗影复刻：找已验证 SaaS，只做用户最痛的 20%，再补一个竞品迟迟不做的点。
- 服务产品化：把已有热门人工服务中 60%-80% 的重复步骤软件化。
- 新词站：围绕新词快速建立承接入口，变现高意图流量。

新词站判断额外问五句：

- 这个词是不是刚出来，搜索斜率明显上升？
- 搜这个词的人是想“用”，还是只想“看”？
- 官方供给是不是贵、难、慢、不方便？
- 48 小时内能不能做出可承接 MVP？
- 背后有没有订阅、credits、转售或持续使用空间？

商标/版权高风险的新词，不做长期 EMD 品牌站；若用户坚持做，只能按短窗口风险方案单独标注。

### 5. Design The Smallest Paid Loop

MVP 只保留能验证“用户是否愿意付费”的核心流程。

必须包含：
- 输入：用户给什么材料、账号、文件、关键词或需求。
- 处理：系统如何完成关键任务，可以人工、半自动或 API 混合。
- 结果：用户拿到什么具体交付物。
- 付费点：免费给到哪一步，什么时候收费，为什么卡在这里合理。
- 反馈：如何拿到真实用户、真实使用、真实付费或预付。

不要一开始做大而全、一站式、所有场景。先交付一个值得付钱的小结果。

### 6. Build Traffic And Monetization Hypothesis

流量入口必须和用户行为匹配：

- 搜索词机会：SEO 页面、工具页、模板页、对比页、替代页。
- 新词站：关键词域名/相关域名、承接页、内页、外链、快速部署。
- 抱怨机会：社群、垂直社区、KOL、内容演示、案例传播。
- 服务产品化：Fiverr/Upwork 需求页、服务关键词、交付案例。
- 暗影复刻：竞品替代页、差评痛点页、迁移工具、垂直渠道。

商业化方式从需求频率选择：

- 低频高价值：一次性收费、服务费、模板包。
- 高频刚需：订阅。
- 消耗型任务：credits。
- API/批量任务：按量计费。
- 复杂交付：软件 + 人工修正的混合模式。

### 7. Decide GO / NO-GO / HOLD

默认必须给结论：

- GO：购买理由清晰，有证据，MVP 可在 2-7 天内验证，获客路径可执行。
- HOLD：需求可能存在，但付费、渠道、交付或合规仍缺关键证据，需要一个小实验补证。
- NO-GO：用户不具体、问题不痛、付费意愿弱、供给已充分、MVP 太重或合规风险不可接受。

结论必须带下一步：
- GO：7 天 MVP 实验计划。
- HOLD：最小补证实验。
- NO-GO：放弃原因和可保留的学习。

## Output Format

默认用这个结构输出：

```markdown
## 购买理由

## 目标用户 / 场景 / 付费 / 问题

## 需求证据

## 供需失衡

## 机会类型

## MVP 最小闭环

## 流量入口

## 商业化方式

## 主要风险

## 结论：GO / HOLD / NO-GO

## Next
```

如果信息不足，不要编造证据。明确写“当前证据不足”，然后给最小验证动作。

## Quality Bar

- 不接受“AI 提效”“一站式平台”“所有人都能用”这类空泛定位。
- 不把用户夸奖当需求验证。
- 不把搜索量大等同于可赚钱。
- 不把技术可行等同于商业成立。
- 不建议新手一上来做大词、大平台、大而全产品。
- 每个 GO 结论至少要能说清：购买理由、获客入口、收费点、MVP 交付物。
