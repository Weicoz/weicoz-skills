# 通用验证约定

一句话：**验证靠一条命令的结论行，不靠模型自述**。这里只定义约定；具体怎么启动、操作、观察应用，由适配器负责。

本约定从小游戏套件（`weicoz-game-flow`、`weicoz-cocos-run`）抽出，游戏和其他项目共用同一套状态词、档位和规则。

## 1. 项目验证约定

每个项目在根目录 `AGENTS.md` 写一节 `## 验证约定`，模板见 `references/project-section.md`。其他 skill 只读这一节，不猜命令。

缺这一节时：

1. 先查项目已有入口：`package.json` 的 scripts、`Makefile`、CI 配置里实际执行的命令、已有 git 钩子。已有检查优先复用，不另造。
2. 按项目类型选适配器（第 8 节），按模板补写这一节，标“待用户确认”，然后继续工作。
3. 补写属于低风险可逆改动，不需要先停下来问。

## 2. 结论行

项目的验证命令必须满足：

- 最后一行只能是下面三种之一：
  - `结论：通过`
  - `结论：不通过（失败：<项>、<项>）`
  - `结论：未验证（缺：<缺什么>）`
- 退出码：通过 0，不通过 1，未验证 3。
- 前面逐项一行，以 ✅ / ❌ / ⚠️ 开头，失败项附一行原因或证据路径。

只照抄结论行和失败项，不得自己推断“应该没问题”。命令没有结论行时，按退出码判断，并在汇报里写“验证命令无结论行，待补”。

## 3. 三档

| 档位 | 什么时候跑 | 跑什么 |
| --- | --- | --- |
| 秒级检查 | 编码途中随时 | 编译、类型检查、lint，以及与改动相关的单个测试文件（红绿循环里每步都跑） |
| 快检 | 一轮改动写完后 | 与本次改动相关的单测，加核心流程的快速试跑 |
| 全检 | 阶段门、合并前，各跑一次 | 全量测试、端到端流程、目标平台或正式构建检查 |

- 编码途中不得跑全检。每改一小处就跑测试，时间会耗在等待上。
- 只有全检能支撑“可以合并”或“可以交给用户试用”。
- 命令检查的子进程带环境变量 `VERIFY_TIER=quick|full`，属性测试按它定迭代数。

## 4. 失败处理

1. 按失败项逐个修，修完重跑**同一条命令**。
2. 同一项连续 2 次修不好，或整个任务累计 5 轮验证不通过：停下，报告该项的输出和已尝试的做法，不扩大改动范围。
3. 不得删除、跳过、放宽测试或断言来让它通过；不得修改评分标准（见第 6 节）。
4. 只有环境导致的超时（本机负载高、端口被占）可以重跑 1 次，并在报告里记“首轮环境超时，已重跑通过”。逻辑失败不得重跑碰运气。
5. 判断某个失败与本次改动无关时，必须附基础分支上同命令同失败的证据：用 `wt` 建干净 worktree 复现，不得 stash、reset 或回滚当前代码。没有证据不得写“无关”。
6. 跑重型检查前看本机 1 分钟负载（`uptime`）和 CPU 核数（macOS `sysctl -n hw.ncpu`，Linux `nproc`）。负载高于核数时，在报告首行注明，超时类失败优先怀疑环境。

## 5. 四级验证状态

逐级累积，不得越级：

1. **构建已验证**：产物生成（构建、编译、打包成功）。
2. **已启动**：应用或服务真的起来了，有首屏截图、健康检查响应或启动日志为证。
3. **核心流程已验证**：用户的关键流程走通，每一步都有证据（状态、响应、截图）。
4. **目标环境已验证**：在目标平台、真机或部署环境上跑通第 3 级。

各适配器对“核心流程”“目标环境”的具体含义见第 8 节。脚本断言全部通过、只剩视觉巡检待看图时，可以判第 3 级，视觉巡检写进“未验证”；看图发现阻塞或高级缺陷时降级。有界面的项目没看联系图时，汇报首行写“第 3 级（视觉未验证）”，不得说“可以交给用户试用”。看图必须先尝试本机看图能力（模型自带视觉或 modlens）；都不可用才可写“视觉未验证”。没跑的检查写“未验证”并写明缺什么。“代码看起来对”“构建通过但没打开”“日志里没报错”都不算证据。

## 6. 防自评

- 执行方自述不算通过。验收方必须自己重跑验证命令，看结论行。
- 审查标准从**基础分支**读，不从当前改动读：`git show <基础分支>:CODING_STANDARDS.md`（或 `REVIEW.md`）。
- “评分标准”包括：审查规范文件、`AGENTS.md` 的验证约定节、各适配器配置（`web-verify.config.json` 等）、基线/快照/阈值文件、`package.json` 里的验证命令。执行者不得为过关改它们。
- 确需改评分标准时，把改动单独列出交用户确认，本轮仍按基础分支的版本判定。验收时给运行器带 `--base <基础分支>`。
- 运行器只自动比对：`AGENTS.md`、`CLAUDE.md`、`package.json`（web 另含 `tests/e2e/web-verify.config.json`，并比对 `verify:*` 脚本；含未跟踪的新文件）。有改动，结论记“未验证（缺：评分配置改动待用户确认）”。基线、快照、阈值文件靠审查：`weicoz-code-review` 把它们列为必看。
- 测试本身也要审：它能不能区分“正确实现”和“看起来对但错了的实现”？只 mock 内部依赖、断言自己算出来的值、靠固定 sleep 等待的测试，按缺陷报告。
- 高风险改动（项目约定里的高风险目录、数据格式、鉴权、并发、对外接口）交给上下文干净的独立审查者。

## 7. 证据格式

- 汇报必须原样带上运行器打印的联系图路径和结论行。`temp/` 是临时证据，下次运行会覆盖。
- 阶段门、合并、发版的证据：结论行原文写进提交说明或任务文档；联系图交给用户或按项目约定存放，不默认入库。

每条验收写成一行：**步骤 → 期望 → 证据（命令输出、状态 JSON、截图路径）→ 通过 / 失败**。

- 有界面的项目，把关键截图拼成一张联系图，按 `references/visual-checklist.md` 巡检。断言只能证明状态对，画面问题只能看图发现。
- 每发现一类画面或行为缺陷，同时加一条脚本断言或检查，让同类回归以后不看图也能被抓住。
- 体验类问题（手感、节奏、顺不顺手）不靠截图下结论：抄下指标（帧率、步数、耗时），交给用户判断。

缺陷分级：

| 级别 | 含义 |
| --- | --- |
| 阻塞 | 启动不了、主流程走不通、崩溃、数据丢失 |
| 高 | 主流程能走，但用户频繁遇到错误或看不懂 |
| 中 | 可见 bug、反馈不清 |
| 低 | 外观、文案、不影响使用的清理 |

修复后重跑原失败场景，再跑一个相邻场景，并写明哪些没重测。

## 8. 适配器

| 项目类型 | 适配器 | 核心流程指 | 目标环境指 |
| --- | --- | --- | --- |
| Cocos 小游戏 | `weicoz-cocos-run` 的 `cocos-verify.mjs` | 首次操作、进度变化、胜负与重开 | 微信开发者工具或真机 |
| Web 应用 | 本 skill 的 `scripts/web-verify.mjs`，用法见 `references/adapter-web.md` | 关键页面打开、主操作走通、无控制台报错 | 部署环境或生产构建 |
| 其他（后端、命令行、脚本） | 项目自建一条命令，满足第 2 节 | 关键接口或命令的真实调用结果 | 部署环境 |

**找脚本路径**：文中 `<weicoz-cocos-run>`、`<本 skill 目录>` 等指该 skill 的实际目录。`~/.agents/skills/<名>` 可能是分层工具生成的短桩，完整文件按下面顺序找第一个存在的：

```bash
for d in ~/.agents/skill-tiers/library/<名> ~/.agents/skills/<名>; do [ -d "$d/scripts" ] && { readlink -f "$d"; break; }; done
```

适配器会在项目里写构建产物和截图（如 `build/`、`temp/`），这些目录应已被项目 `.gitignore` 忽略；没有时补一行，不提交产物。

自建命令时，优先把已有检查串起来（测试、类型检查、构建、健康检查），输出第 2 节的格式；不要为此引入新依赖。shell 骨架见 `references/custom-adapter.md`。

Web 适配器用了 `--no-checks` 或 `--script` 就是部分验证：档位行写“部分（<开关>）”，全过也只出“未验证（缺：完整快检/全检，…）”，退出码 3。`--base-url`、`--no-start` 不降级。当前档没有命令检查（`checks` 为空或写错键）且未用 `--no-checks`：记“⚠️ 命令检查：未配置”，结论未验证。

## 9. 选什么测试

动手前先写好“怎样算成功”：一条端到端流程、一条必须成立的性质，或与旧系统的比对。选法见 `references/oracles.md`。

为项目新写或补写端到端测试，按 `references/e2e-authoring.md` 的流程：功能地图 → 选流程 → 定位方式 → 写流程 → 证明能抓错 → 跑稳 → 分档登记。

## 10. 汇报

```markdown
**验证状态**：<四级之一>（<适配器与命令>）
**结论行**：<原样照抄>
| 项 | 结果 | 证据 |
| --- | --- | --- |
| <项> | 通过/失败 | <命令或路径> |
**未验证**：<哪些没跑、为什么、需要谁做什么>
```

## 11. 接入方式

验证是否发生，不能只靠 agent 自觉。三种接法，可叠加：

| 方式 | 做法 |
| --- | --- |
| 链式（本体系默认） | 由 `weicoz-implement-verified`、`weicoz-game-flow` 在完成前调用本约定 |
| 内嵌 | 项目 `AGENTS.md` 的“验证约定”写明命令，任何 agent 进项目都读到 |
| 硬门禁 | git `pre-push` 钩子跑快检，CI 跑全检，不靠作者自觉 |

- 硬门禁先观察后强制：先只报告不阻断；稳定一周且无误报，再改为阻断。流程没稳定前不上硬门禁。
- 装不装钩子由用户决定，不替用户装。

`pre-push` 示例（`.git/hooks/pre-push`，观察期把 `exit 1` 改成 `exit 0`）：

```bash
#!/usr/bin/env bash
set -o pipefail
out=$(pnpm verify:web:quick 2>&1); code=$?
printf '%s\n' "$out" | tail -5
if [ "$code" -ne 0 ]; then
  echo "pre-push：快检未通过，已阻止推送" >&2
  exit 1
fi
```

## 12. 合并与上传门（通用）

- 何时生效：仓库 `AGENTS.md` 有“## 验证约定”。没有就不拦。只在“合并到主分支”和“上传”两点拦，日常提交不受影响。
- 戳记：适配器全检结束时调用 `scripts/stamp.mjs`（开始 `start`，结束 `finish --tier full --code <退出码> --base <分支> [--narrowed]`；shell 自建适配器见 `references/custom-adapter.md`）。同时满足才写 `git-dir/verify-stamp.json`（含 commit、tier、base、clean、verdict、at）：tier=full、退出码 0、范围未缩小、base 非空、开始与结束时 `git status --porcelain` 都为空、HEAD 前后一致。否则删除旧戳记，结论行前一行写明原因。
- 构建：构建脚本前调 `stamp.mjs build-start --dir <产物>`，成功后调 `stamp.mjs build --dir <产物> --platform <名> [--release]`，写 `.build-commit.json`（commit、dirty、platform、release）。
- 门：`node scripts/verify-gate.mjs --project <目录> [--base <分支>] [--build <产物目录>[:<平台>]]... [--allow-debug]`。检查：戳记存在、commit 等于 HEAD、tier=full、verdict=通过、戳记 base 等于 `--base`（缺省按 develop、main、master 取第一个存在的）、工作区干净；每个产物 commit 等于 HEAD、dirty 为 false、release 为 true（`--allow-debug` 放宽）、平台一致。最后一行“结论：通过/不通过（缺：…）”，退出码 0/1。
- 用户级安装（装不装由用户决定）：`~/.config/worktrunk/config.toml` 的 `[pre-merge]` 引用 `bash <本目录>/scripts/wt-pre-merge.sh {{ target }}`（`target` 是 wt 在 merge 时提供的合并目标分支）；Claude Code 的 SessionStart 钩子引用 `scripts/session-reminder.sh`。不支持钩子的 harness 靠本节规则自觉执行。
- 合并用 `wt merge --no-squash --no-ff`；rebase 之后必须重跑全检，旧戳记的 commit 已不等于 HEAD。
- 上传：任何方式（上传脚本、开发者工具 CLI、`tmg upload`）之前都先运行 `verify-gate --build <产物>`，结论“通过”才上传，回报里贴戳记提交号。
- 已知绕过：手写戳记、`--no-hooks`、直接 `git merge`、`skip-worktree`、构建后改产物。门拦不住这些，靠审查与回报里的戳记提交号发现。
- 对抗式审查（定义见 `weicoz-code-review`）不是每次都做，只在触发条件命中时做：①改动触及验证约定里的高风险目录，或存档与数据格式、鉴权、支付、并发、对外接口契约；②发版或上传给用户之前，每个发版批次一次；③改的是验证或门本身（评分配置、验证脚本、钩子）；④用户明确要求。文档、文案、数值调参、样式、高风险目录以外且快检能覆盖的小修、纯测试补充不做，走常规审查或只跑快检。
