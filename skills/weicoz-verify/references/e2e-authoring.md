# 为项目写端到端测试

目标：写出 agent 能自己跑、能当“做完了没有”判据的端到端流程。网页项目用 `web-verify.mjs` 跑（写法见 `adapter-web.md`），Cocos 小游戏用 `cocos-verify.mjs` 跑（写法见 `weicoz-cocos-run` 的 `references/playtest-hook.md`）。本文只讲两者共用的写法流程。

端到端测试不看内部结构，只看用户能看到的结果。agent 和单测共享同一个误解时，单测会一起错，端到端测试骗不过。但它慢、容易抖，所以只覆盖少量高价值流程。

## 0. 先确认有“手和眼”

agent 必须能自己启动、操作、观察应用，否则后面都写不成：

| 项目类型 | 启动 | 操作 | 观察 |
| --- | --- | --- | --- |
| 网页 | `start` 配置或已有服务 | Playwright | 截图、控制台、网络请求 |
| Cocos 小游戏 | `cocos-preview.mjs` | 测试钩子 `globalThis.__game` | 钩子状态、截图、帧率 |
| 桌面 / 移动端 | 项目启动脚本、模拟器 | 自动化接口或测试钩子 | 截图、日志 |
| 后端 / API | 服务启动命令 | 真实 HTTP 请求 | 响应、数据库只读查询、日志 |

缺哪一项，先补那一项（启动脚本、登录方式、测试钩子），再写流程。测试运行时不得抢桌面焦点、不得弹系统权限框、不得读写用户真实数据、不得调用真实外部服务或发真实消息。

## 1. 写功能地图

从用户角度列出功能，存到 `tests/e2e/FEATURES.md`。每行：

| 功能 | 用户怎么到达 | 预期结果 | 定位方式 | 坑 |
| --- | --- | --- | --- | --- |
| 例：查看知识库详情 | 侧栏“知识库” → 点某个库 | 看到文件列表与知识条目数 | 链接角色 + 库名文本 | 列表异步加载，先等骨架消失 |

- 写不出“预期结果”的功能，先问用户，不要猜。
- “坑”写 agent 容易踩的：异步加载、弹窗遮挡、权限、多语言、空数据。
- 功能地图同时是给以后的 agent 的导航，改了交互要同步更新。

## 2. 选流程（少而准）

按“坏了的影响 × 用户使用频率”排序，先选 3–5 条：

1. 主流程：没有它产品就不能用（登录后进入主界面、核心操作、通关）。
2. 最近出过事故或回滚的流程。
3. 跨模块的流程：单测覆盖不到的拼接处。

每条流程写成一句可判定的话：“做 X 之后，用户能看到 Y”。不选：只有内部状态变化、用户看不到的行为（用单测或属性测试）；好不好用、顺不顺手（交给人试用）。

## 3. 确定定位方式

按优先级选，第一个可用就停：

1. 角色加可见文字：`getByRole('button', { name: '保存' })`、`getByRole('link', { name: 库名 })`。
2. 标签与占位符：`getByLabel`、`getByPlaceholder`。
3. 专用测试标识 `data-testid`：需要改产品代码，先问用户。
4. 游戏：测试钩子暴露的状态和命令，不点像素坐标。

不用 CSS 层级路径和自动生成的类名：一改样式就断。

## 4. 写流程

每一步：**操作 → 等待可见结果 → 断言 → 关键处截图**。

- 断言用户看得到的结果：文字、元素可见、数量、地址变化、钩子状态。不断言内部函数调用和数据库实现细节。
- 期望值来自独立来源（需求、功能地图、已知数据），不照代码再算一遍。断言须来自功能地图的“预期结果”，不得只断言“页面非空”。
- 等待某个状态出现（`waitFor`、`networkidle` 加超时兜底），不用固定 sleep。
- 失败信息要能直接定位：步骤名写清楚做了什么；等待超时要改写成“N 秒内没等到 X”，例如 `.waitFor(...).catch(() => { throw new Error('30 秒内没等到标题“待审核知识块”'); })`，不要只留框架的 Timeout 报错。
- 需要登录时，整次运行只登录一次并复用会话：频繁登录会被限流。
- 默认只读。必须写数据时，只写测试专用数据，流程结束时清理，并在功能地图里注明。
- 经常要手动调试的复杂操作（上传文件、多步向导），封装成带参数的辅助函数或命令行脚本，下次直接传参调用，不再逐步点。

## 5. 证明它能抓错

新流程第一次跑通后，必须证明它会失败：

1. 能改实现时：临时改坏一处（删掉按钮的处理、改错返回值），跑流程，确认失败且失败信息指向这一步；再改回去。
2. 只能对部署环境跑时：临时把断言的期望改成错的值，确认失败；再改回去。
3. 测不出错的流程是假测试，重写断言，不能提交。常量为真、与被测值无关的 `check`（如 `check('x', true)`）也属这类：改坏实现后它仍通过，这一步会暴露它。

改坏的代码不得提交；做完用 `git diff` 确认已全部还原。

## 6. 跑稳

写流程时用 `--script <流程名> --no-checks` 反复试跑，省掉单测等命令检查；这是部分验证，结论行是“未验证（缺：完整…）”，退出码 3，不能当通过。定稿后再跑一次不带这两个开关的完整快检或全检。

- 连续跑 3 次，结果一致才算稳。时好时坏的流程先修（多半是没等到状态），修不好就移出主测试集，不得留在快检里。
- 手机和桌面两种视口都跑；只针对一种设备的流程在功能地图里注明。
- 一条流程控制在几十秒内；太慢的拆开，或只放进全检。

## 7. 分档登记

- 最核心的 1–2 条进快检（`quickFlows` 或 `--quick` 跑的试玩脚本），每轮改完都跑。
- 其余进全检，阶段门和合并前跑。
- 把流程清单和档位写进项目 `AGENTS.md` 的“验证约定”；功能地图路径也写进去。

## 8. 持续维护

- 看联系图发现的画面问题，补成断言（元素可见、数量、文本），以后不看图也能抓住。
- 线上回滚或人工发现的漏网问题，先补一条能复现它的流程，再修。缺陷修复同理：先写能复现的失败流程或测试，确认它失败，再修（Addy）。
- 功能下线或交互重做时，同步删改流程和功能地图；长期不再失败、也不再覆盖关键路径的流程可以删，删前列清单问用户。`weicoz-govern` 体检只提示零断言流程和缺功能地图，哪些流程长期不再失败要人工核对。

## 交付

新增或修改端到端流程时，按 `SKILL.md` 第 7 节汇报：功能地图改动、新增流程与档位，另必附原文：

1. 改坏处的一行 diff 摘要。
2. 改坏后该流程的失败结论行与失败步骤行。
3. 还原后 `git diff --stat` 为空的输出。
4. 连续 3 次运行的结论行。
5. 联系图路径。
