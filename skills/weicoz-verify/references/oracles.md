# 选什么测试（oracle）

测试是 agent 判断“做完了没有”的依据。先定成功标准，再写代码。

## 四类，按场景选

| 类型 | 回答什么 | 适合 | 工具 |
| --- | --- | --- | --- |
| 端到端（E2E） | 用户真的能走通吗 | 主流程：注册、下单、通关、提交表单 | 浏览器自动化、游戏试玩脚本、真实 API 调用 |
| 属性 | 什么情况都不能发生什么 | 解析/序列化、计算、生成器、迁移、状态机 | fast-check（JS/TS）、Hypothesis（Python）、proptest（Rust） |
| 差异 | 新版和旧版行为一致吗 | 重写、迁移、换库、引擎升级、性能优化 | 同一批输入喂新旧两边，比对输出 |
| 示例 | 这个输入应得什么 | 规则明确的单点行为、回归用例 | 项目已有单测框架 |

只能选一类时选端到端：它不看内部结构，agent 和测试共享同一个误解时也骗不过它。端到端慢且易抖，所以只覆盖关键流程，不追求路径全覆盖。

## 属性测试：常用性质

- **往返**：编码后解码、序列化后解析，结果与原值相同。
- **不变量**：排序不改变元素个数与内容；余额不为负；进出账相等。
- **幂等**：迁移、归一化、重试执行两次与一次效果相同。
- **等价**：优化后的实现与简单正确的实现结果相同。
- **生成器可解**：任意种子生成的关卡，回放官方解都能通关；指标落在目标范围。

起步做法：

1. 从小而纯的函数开始（解析器、格式化、价格计算、关卡生成器）。
2. 先用一句话写出性质，再写成代码。
3. 工具找到的最小反例存成固定回归用例。
4. 让 agent 写性质，不只写例子。agent 自己挑的例子往往按自己的理解挑，性质逼它面对任意输入。

## 差异测试：要点

- 旧系统就是标准答案，不必把每个边界情况讲给 agent。
- 输入用随机生成或回放真实流量样本，不只用手挑的例子。
- 比对前先归一化无意义的差异（时间戳、无语义的顺序），否则误报不断。
- 有意改变的行为记进“已批准差异”清单，逐条写原因；清单外的差异一律当缺陷。

## 快且确定

测试慢或时好时坏，agent 会学到“重跑碰运气”而不是修问题，而且外表看不出来。

- 快检要能每轮都跑，核心循环最好在秒级。
- 随机数带固定种子，时钟可冻结，网络受控，状态隔离。
- 时好时坏的测试立刻移出主测试集，单独修；主测试集里留一个，所有结果都不可信。
- 输出只报失败项和原因，不刷屏报通过项。
- 测试不得抢桌面焦点、弹系统权限框、读写用户真实配置或数据、调用真实外部服务。

## 测试自检（写完或审查时）

1. 把实现故意改错一处，这个测试会失败吗？不会就是假测试。
2. 期望值来自独立来源（已知正确的字面量、需求、手算例子），而不是照实现的算法再算一遍吗？
3. 只断言对外行为，不断言内部调用顺序或私有状态吗？
4. 没有固定长 sleep 吗？
5. “1+1=2”式只测语言本身或框架本身的测试，删掉。
